# RLS Audit — 2026-05-31

**Scope:** the Supabase database-linter RLS cluster on prod (`xsazcoxinpgttgquwvuf`)
**plus** the three functional bugs whose root cause is also RLS (FIX-412, FIX-413,
FIX-415). One coherent pass, two lenses:

- **Over-exposure / mis-config** (what the linter catches): RLS off, no policy,
  definer views, sensitive columns.
- **Under-exposure** (the linter does *not* catch this): a policy that is too
  restrictive and silently hides rows the app needs — the source of FIX-412/413.

**This is report-first. Nothing was applied to local or prod.** Migration files are
staged but un-applied. Prod was queried **read-only** only (REST, `source
.env.local.prod`, GET requests). One decision (the `is_active` gate, §3) is the
user's to make before any remediation lands.

**Ground-truth method:** every policy claim below was confirmed against live
`pg_policies` / `information_schema` on local Docker (migrations applied) and
reconciled against the prod REST surface + the prod linter. Where local and the
migration files disagree, that divergence is called out — the *running database* is
treated as ground truth, not the prose in the prompt or in CLAUDE.md.

## 3. The open decision — `is_active` anon RLS gate

**Question (the user's to decide):** should anon be able to read `is_active = false`
officials / governing_bodies / agencies?

### Live policy state (confirmed against `pg_policies`)

| Table | Policy | `USING` clause | anon-visible / total (prod) | hidden |
|---|---|---|---|---|
| officials | `public_officials_select` | `is_active = true` | 27,078 / 28,875 | **1,797** |
| governing_bodies | `public_governing_bodies_select` | `is_active = true` | 424 / 626 | **202** |
| agencies | `public_agencies_select` | `is_active = true` | 101 / 101 | **0** |
| jurisdictions / proposals / votes / financial_relationships / entity_connections / … | `*_select` | `USING (true)` | all | 0 |

(Only officials/gb/agencies kept the `is_active` gate + the `public_*` name; the
others were renamed off the `shadow_*` prefix at promotion and use `USING(true)`.)

### What the hidden rows actually are (prod admin-lens samples)

**Inactive governing_bodies (202) — all legitimate Legistar bodies:**
`type='other'`, all 202; every structured type (`legislature_*`, `municipal_council`,
`judicial`, `executive`) is 100% active. Samples: *Finance and Culture Committee,
Taxi Commission, Board of Supervisors Joint, Retirement System, Health Service
System, Select Committee on Civic Arenas* (Seattle/SF). These are **real civic
bodies** marked inactive.

**Inactive officials (1,797) — a mix, all `tier=elected`:**
- **518** Legistar-sourced municipal council members — legitimate, mis-flagged
  (e.g. Jennifer Samuels "Council Member", Dylan Orr "Council Member"). These are
  the **FIX-412** victims.
- **1,072** with **no source and no governing_body** — bulk-imported federal
  EOP/White-House staff, ALL-CAPS names ("SPECIAL ADVISOR", "SENIOR ADVISOR",
  "DEPUTY ASSISTANT SECRETARY", "DIRECTOR OF SCHEDULING"). Mix of legitimate formers
  (e.g. Jessica Rosenworcel, former FCC chair) and stale noise.
- **207** other-sourced (congress/fec/wikidata) inactive electeds.

So "inactive" is **partly legitimate formers, partly mis-flagged current municipals,
partly source-less staff noise** — not a clean "former officials" set.

### FIX-412 reproduced (verified)

```
anon  GET officials?id=eq.b60016bb-…&select=id   → []        (RLS hides the row)
admin GET officials?id=eq.b60016bb-…             → [{is_active:false}]
```
`getCachedOfficial` (apps/civitics/app/officials/_lib/get-official.ts:41-48) uses
`createPublicClient()` (anon) → `.eq("id", id).single()`. A PK `.eq` can match ≤1
row, so the only way `.single()` returns PGRST116 is **RLS hiding the row**. The
loader's `if (!data) return null` → `notFound()` → 404. **Confirmed: the gate, not
an embed fan-out.**

### Options

- **Option A — relax to `USING (true)`** on officials + governing_bodies + agencies;
  move active/"former" handling to the display layer (badges, default filters).
  - Fixes FIX-412 + FIX-413 (+ the latent agencies gate) cleanly; matches the
    "all civic data is publicly readable, always" mission comment.
  - Exposes 1,797 inactive electeds + 202 inactive gbs. **Does not** expose the
    candidate pollution (already visible). The 1,072 source-less EOP staff are the
    main "is this noise we want public?" question.
  - **Enables the `institutions` `security_invoker` flip safely** (see §5).
- **Option B — keep the gate, curate `is_active`** by flipping legitimately-displayable
  rows to `true` (the FIX-413 audit-half). Narrower exposure; leaves the gate as a
  latent 404 trap and needs per-row curation of 1,797 + 202 rows.
- **Option C — per-table mix**, e.g. relax officials + governing_bodies to
  `USING(true)` (the two with real victims) but keep agencies gated (0 rows hidden
  anyway, so this is cosmetic), or any other split.

### Decision (2026-05-31): **Option A selected.**

The decision migration `20260531000100_rls_isactive_decision.sql` has been finalized
to Option A (live DDL: relax the three gates to `USING(true)` + `institutions`
`security_invoker` flip) and remains **staged, not applied**. Follow-up: display-layer
"Former/Inactive" badge + default active-only filter (separate, non-blocking).

### Recommendation (rationale behind the choice)

**Option A**, with one guard: the 202 inactive gbs and the 518 municipal officials
are unambiguously legitimate civic data and should be visible; the mission comment
already says so. The only real hesitation is the 1,072 source-less EOP staff — but
they are *civic* (federal appointees), display layer can badge them "Former / Inactive,"
and they are far less of a quality problem than the 13,159 already-visible candidate
rows. Relaxing the gate also removes a whole class of latent FIX-412-style 404s (any
future inactive-entity detail page). Pair Option A with a follow-up display-layer
"active/former" badge + default filter so the hub UIs don't read as if everyone is
current. **The `is_active` migration stays a commented stub until you pick A/B/C.**

## 5. Per-object detail + evidence

### 5.1 The anon-write hole (🔴 — biggest over-exposure, under-rated by the linter)

`information_schema.role_table_grants` shows **anon holds `INSERT/UPDATE/DELETE/
TRUNCATE`** (a blanket `GRANT ALL`) on all 7 RLS-disabled tables. With RLS **off**,
PostgREST honors those grants. Proven on **local** (zero data impact — DELETE with a
non-matching filter):

```
anon  DELETE /rest/v1/industry_codes?code=eq.__zzz__   → HTTP 204   (authorized)
anon  DELETE /rest/v1/irs990_filings?ein=eq.__zzz__    → HTTP 204   (authorized)
anon  DELETE /rest/v1/proposals?id=eq.000…00 (RLS on)  → HTTP 401   "permission denied"
```

So an anonymous caller can today `TRUNCATE`/`DELETE` the IRS-990 corpus and
`page_views` on prod. **Enabling RLS + a SELECT-only `USING(true)` policy neutralizes
this** (RLS with no write policy makes anon writes affect 0 rows), and the migration
additionally `REVOKE`s the surplus write grants for defense-in-depth. No legitimate
anon/authenticated writer exists — every writer uses `createAdminClient()`
(service_role, `rolbypassrls=true`), so SELECT-only public-read changes nothing those
writers see or do.

### 5.2 `page_views` → LOCK (safe)

- Readers: `api/claude/status/_lib/sections.ts:127,948,953` — all `admin`.
- The one anon-reachable popularity read (`proposals/page.tsx:135`) targets
  `proposal_popularity_24h` (a **materialized view**, separate object with its own
  anon grant) — **not** the base table; MVs don't enforce base-table RLS.
- Writer: `api/track-view/route.ts:46-48` — `createAdminClient()` → service_role →
  bypasses RLS. **Locking the base table does not break tracking.**

> The classify pass flagged a "CRITICAL: locking breaks the writer" risk. That is
> **wrong** and was overridden: the writer is service_role (`rolbypassrls=true`,
> verified), not anon. Enabling RLS leaves the insert unaffected. Clears both the
> `rls_disabled_in_public` and `sensitive_columns_exposed` (session_id) linter errors.

### 5.3 `pipeline_state` → narrow key-scoped policy (🟢)

28 read sites, 15 write sites. **Exactly one** is anon-reachable:
`institutions/[id]/page.tsx:488` (`createServerClient`, in `AgencyView`) reading
`key='plum_book_state'` via `.maybeSingle()`. Because RLS is on with no policy, this
**silently returns 0** for every anon visitor (verified: prod anon REST →
`pipeline_state` = 0 rows) → `plumState` null → the plum "last change" date never
renders. Fails-open (no crash). Everything else (`kill_switches`,
`cost_config_overrides`, `cost_alert_latest`, `platform_plan`, `manual_trigger_*`,
watermarks) is `admin`-only and **sensitive** — so a blanket `USING(true)` is wrong.
Fix: either a key-scoped `USING (key = 'plum_book_state')` SELECT policy (exposes only
that benign date) or switch that single read to `createAdminClient()` (the page is
already `force-dynamic`). Migration proposes the key-scoped policy.

### 5.4 `external_source_refs` (xsr) → codify the out-of-band policy (🟡)

Live local: RLS on + `xsr_public_read USING(true)` for anon/authenticated. **That
policy is in no migration** — `20260421000007_stage1_08_rls.sql:49` explicitly says
xsr is "RLS enabled… with no policies." Prod anon **can** read xsr (REST →
1 row; 178,979 total) and the prod linter does **not** flag xsr as
`rls_disabled` → therefore prod has RLS on **+ an anon SELECT policy too** (same
out-of-band drift). It is load-bearing: `packages/db/src/attribution.ts:59`
(`createServerClient`) and `api/attribution/[type]/[id]/route.ts:120`
(`createPublicClient`) read it on the request path for entity attribution. All 19
writers are `admin`. **Action:** codify `xsr_public_read` idempotently so a rebuild
keeps it. This is the durable form of the FIX-398 workaround — drift-capture, not new
access.

### 5.5 `institutions` view → `security_invoker` flip is DECISION-GATED (couples to §3)

Currently SECURITY DEFINER → **bypasses** the `is_active` gate → the hub and detail
pages show **all** institutions incl. the 202 inactive gbs. Consumers (6, all
anon-reachable): hub `institutions/page.tsx:100`; detail
`institutions/[id]/page.tsx:219,253,980`; `meetings/[id]/page.tsx:131`;
`proposals/[id]/page.tsx:254`. The detail pages do **not** filter `is_active` — they
rely on the definer view returning the row.

- Flipping to `security_invoker` **applies** the underlying RLS. **Under the current
  gate (Option B/C-keep)** this would **hide** the 202 inactive gbs and **404 their
  detail pages** — a new FIX-412-class regression. So **do not flip under Option B.**
- **Under Option A** (`USING(true)`) the flip is safe — the gate is permissive, so the
  view shows the same rows as today, now consistently coupled to table RLS.

→ The flip lives in the **decision** migration, only enabled if A is chosen.

### 5.6 `proposal_comment_stats` view → `security_invoker` flip is SAFE (🟡)

Aggregates `civic_comments WHERE is_deleted=false`. The `civic_comments` anon policy
is `USING (is_deleted = false)` — the **same** filter. So under `security_invoker`,
anon evaluates the aggregate over exactly the rows the definer view already returns →
**identical counts**. One reader (`proposals/page.tsx:164`, `createPublicClient`).
Flip clears the linter `security_definer_view` for this view with zero behavior
change. → safe migration.

### 5.7 leave-locked (enrichment_queue, external_relationships, external_relationships_review_queue)

All reads/writes go through `createAdminClient()`; **zero anon/SSR read paths**
(confirmed by exhaustive grep + adversarial re-grep). RLS-on-no-policy is the correct
state (the `rls_enabled_no_policy` INFO is acceptable). Migration adds `COMMENT`s
documenting intent so the INFO is understood, not "fixed" by a needless policy. Note:
the public `/api/claude/status` endpoint surfaces aggregate `enrichment_queue` counts,
but via `createAdminClient()` — a deliberate public-health-metric design choice, not
an anon DB read path.
