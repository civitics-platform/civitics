**What this read does NOT establish, stated plainly.** The EC arm's derived work

```
{"run": false, "reason": "cycle_cooldown",

```

So the 19:30 firing was a **cooldown skip**, not a caught-up unit — and by
FIX-1111's deliberate logging asymmetry (only `backoff` writes a
`data_sync_log` row; blackout and cooldown are counted and RAISEd) it wrote no
row at all, which is why the `entity_connections_rebuild` pipeline shows a gap
at 19:30 where `financial_entity_totals_refresh` shows `complete`. The skip is
recorded where the asymmetry says it is: `pipeline_state.ec_crawl.skips` reads
`cycle_cooldown: 1067` with `last_skip_at: 2026-09-19T19:30:00.312636+00` and
`last_skip_reason: cycle_cooldown`.

The arm's next cycle opens ~**21:14 UTC**, and the 46,790 moved FR rows sit
above the `entity_connections_donations` watermark, which is still
`2026-09-17 23:20:27` across all sixteen windows. So the EC drain is **pending
by design**, not complete, and not stalled.

Two consequences worth carrying:

- The "EC units back to baseline" half of the drain-and-wait convention is
  **not a reliable completion signal for this arm**. A sub-second `ec-crawl`
  unit reads identically whether the arm is caught up or in a six-hour cooldown,
  and the cooldown case writes nothing to the log a reader would consult. The
  satisfiable form is the **gate's own vocabulary** — `ec_crawl_gate()->>'reason'`
  plus the watermark — which is rule 137 applied to the instrument this
  convention actually depends on.
- The second prod op this run performs (the `cron.alter_job` migration push) is
  a catalogue write of microseconds, not a load event, so it does not stack on
  the pending drain. That is the reason it proceeds while the EC work is still
  owed, and it is stated here rather than assumed.
