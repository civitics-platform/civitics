## 2. Set 1 — the apply

Command, run from the PRIMARY checkout (the worktree has **no**
`.env.local.prod` at all, so the `:prod` script cannot run there):

```
pnpm --filter @civitics/data data:merge:official-dupes:prod -- \
  --manifest ../../docs/audits/2026-09-16-fix1187-shared-id-manifest.tsv \
  --defer-tails --apply
```

**The prompt's path would have failed.** `pnpm --filter` runs with cwd
`packages/data`, and `readManifest` is a plain `fs.readFileSync` of the given
path, so `docs/audits/...` resolves to `packages/data/docs/audits/...` — which
holds only the three FIX-1106 residue TSVs. `../../docs/audits/...` is the form
that resolves, confirmed by local dry run before any prod contact.

**Wall: 00:23:36 -> 03:53:00 UTC = 3 h 29 min 24 s.** Exit 0.

### 2.1 Where the time actually went — the finding of the run

| phase | wall |
|---|---:|
| `_pair_before` conservation snapshot | ~4 min |
| **`_collision` build (ANALYZE + CREATE TEMP TABLE AS)** | **~97 min** |
| all six write steps combined | **~7.5 min** |
| conservation "after" + COMMIT | ~8 min |
| phase 2 tail (three manifest-scoped rollups) | **~94 min** |

cc-128 projected 16-52 min and named `FR move to_id -> survivor` as the step to
watch past ~45 min, because it was 96.3 s of the clone's 155 s. **On prod that
step took 265.8 s and was never the problem.** The cost is the `_collision`
detection join, which on the clone disappears inside a 2m35s total and is
therefore untimed in the rehearsal.

**Why it is expensive, and it is a shape problem.** `_collision` (`:2341-2354`)
drives `_manifest` -> **survivor** FR rows -> dup FR rows. The survivor side is
the large one: these are 151 sitting members, several holding tens of millions of
dollars. The read-only gate query in section 1.3 computes the same join driving
from the **stub** side (99,217 rows) and finishes in minutes. The
`ANALYZE _manifest` FIX-1165 added fixes the cardinality estimate; it does not
change which side is materialised. The backend sat on `IO / DataFileRead` for the
whole 97 minutes, consistent with prod's 256 MB `shared_buffers`.

### 3.2 Attempt 2, 04:05:54 — ran 77 min, then cancelled on operator decision

Launched by a poller that waited for zero live writers. It reached the merge
steps and its numbers match the rehearsal exactly:

It then entered `FR move to_id -> survivor` and **stalled**: 66 minutes on a

**The cause was a collision with the deferred vacuum.** `ec-vacuum-analyze` fired

**87,206 dead `entity_connections` tuples set 1 had just deferred into that

| pid | statement | elapsed at 05:20 |
|---|---|---:|
| 191875 | set 2 `UPDATE financial_relationships SET to_id = ...` | 66.5 min |
| 193725 | `VACUUM (ANALYZE) public.entity_connections` | 51 min |

**Front-door impact, 05:05-05:20 UTC:** 14 x `500` and 1 x `401` out of 29
requests — **51.7 % error rate** — with cancellations at **2.800/min, ~85x
baseline**. `ec-vacuum-analyze` itself took **3,147.9 s (52.5 min)** against a
normal few seconds, and **`fe-vacuum-analyze` failed at 04:50 with `job startup
timeout`** — pg_cron could not fork a worker. That failure mode is recorded as
~0 % in the 18:00-05:00 UTC band, so it is attributable to this contention, not
background noise.

**Decision.** Craig called the error rate; the operator decision was to cancel
set 2 and keep the vacuum. `pg_cancel_backend(191875)` at **05:22:12**. The
transaction **rolled back atomically** — `Rolled back due to error: canceling
statement due to user request`, exit 1, **nothing written**. Set 1 is committed
and unaffected.

This departs from the prompt's "do not cancel a running merge transaction from
outside". It was taken deliberately, with the operator, on three grounds: the
front door was at 51.7 %; the 05:45 UTC blackout was 23 minutes away and set 2
could not have finished; and a cancel of an uncommitted transaction is atomic, so
the only cost is the elapsed time.

## 4. The vacuum debt `--defer-tails` leaves behind

Post-set-1, deferred to scheduled owners:

| table | dead tuples | all-visible | owner | collected? |
|---|---:|---:|---|---|
| `entity_connections` | 87,206 -> **0** | 83.9 % -> **100.0 %** | `ec-vacuum-analyze` daily 04:30 | **yes, 05:19:41** (52.5 min, contended) |
| `financial_entities` | 85,556 | 99.9 % | `fe-vacuum-analyze` daily 04:50 | **no — failed, job startup timeout**; next 04:50 tomorrow |
| `officials` | 312 | 87.8 % | `officials-vacuum-analyze` **Mon 01:30** | no |
| `financial_relationships` | **204,091** | **82.7 %** | `fr-vacuum-analyze` **Mon 01:00** | **no — and autovacuum will not fire** |

**FR is the problem.** Its per-table `autovacuum_vacuum_scale_factor = 0.02`
puts the autovacuum trigger at `50 + 0.02 x 14,469,877 = 289,448` dead tuples;
it sits at **204,091**, below threshold. Its scheduled owner is **weekly, Monday
01:00** — four days away. So a bulk FR rewrite performed on any day but Sunday
leaves the table at ~82.7 % all-visible for up to six days, with nothing able to
collect it. That is the exact FIX-884 index-only-scan degradation (all-visible
loss -> per-row heap fetches) that FIX-943's standing rule — *any script that
bulk-rewrites a table ends by vacuuming what it rewrote* — exists to prevent, and
`--defer-tails` routes around it by construction.

The script's own banner says a script-run VACUUM of these tables is itself a
front-door incident (FIX-1144), so "just run it inline" is not the answer. The
gap is that FR's deferred owner is weekly while EC's and FE's are daily.

## 5. What contradicted the design

1. **The projection named the wrong step.** `FR move` was expected to dominate
   and to be the thing to watch past 45 minutes; it ran 265.8 s. `_collision` —
   untimed on the clone — took ~97 of set 1's 115 transaction minutes, because it
   materialises the survivor side of the join.
2. **There is no single prod/clone multiplier, and cc-128 was right to refuse
   one.** Set 1's merge transaction ran **~44x** the clone's whole-run wall; its
   write steps ran ~3x; set 2's `FR move` ran ~110x under contention.
3. **The clone's colliding/non-colliding split had drifted** — 339 rows changed
   class — moving every row count while leaving the money identical.
4. **The tail is where the front-door cost lives**, not the transaction: 3
   cancellations across 120 minutes of merging, ~15 across 94 minutes of rollups.
5. **"Manifest-scoped" does not mean "small".** 151 rows -> 430,411 donors -> 94
   minutes. The cost table prints a class, not a magnitude.
6. **Deferring a tail relocates its cost into a window the interlock cannot
   coordinate.** Set 1 deferred 87,206 dead EC tuples into the 04:30 vacuum slot;
   set 2 ran into that slot; vacuum jobs carry no FIX-950 guard; the result was
   51.7 % front-door errors and a pg_cron fork failure.
7. **Two sets cannot run back-to-back.** The consumers the first set defers
   resume immediately on release and refuse the second set's claim.
8. **The interlock cannot be labelled per-set.** `runUnderProdSession` composes
   its label from script + argv and takes no label argument.
9. **The prompt's manifest path does not resolve** under `pnpm --filter`, whose
   cwd is `packages/data`.
10. **The prompt quoted clone figures as prod** for the five survivors' totals;
    prod is materially higher (Schiff $33.13 M vs $28.91 M).

## 6. Post-landing: the derived EC drain, and recovery

Set 2 was cancelled at 05:22:12, but the front door did **not** stay recovered.
Measured 05:29-05:44 UTC: **19.5 % errors** (19 x 500, 12 x 504 of 164
requests), and 05:39-05:49: **25.0 %** — with nothing from this run still
writing.

The cause is set 1's **derived** work. `entity_connections_rebuild` has to
re-derive the 87,206 edges set 1 deleted and the 40,649 rows it moved, one
bounded unit per `ec-crawl` firing: 04:00 `partial` 131 s, 04:30 `skipped`
(interlock), **05:30 `partial` 956 s** — longer than the job's own 15-minute
interval, so pg_cron queues behind its own overrun.

That saturation stopped pg_cron forking at all: `cron-job-budget-watchdog` and
`derived-mvs-unit-watchdog` both failed with **`job startup timeout`** at 05:36,
05:38, 05:42 and 05:44, the same mode that failed `fe-vacuum-analyze` at 04:50.
**Budget enforcement was offline while a landing's aftermath ran** — and the
budget watchdog is the only in-backend bound for a COMMITting pg_cron procedure.

**It drained.** The 05:30 unit finished ~05:46. Measured 05:49-05:54: **253
requests, 0 errors (0.0 %), 0 cancellations**, no failed cron job since 05:46.
So the degradation was bounded by the drain rather than open-ended — but it ran
at ~19-25 % errors for about 25 minutes after set 2 was already gone, entirely
on set 1's account. Filed as FIX-1194.
