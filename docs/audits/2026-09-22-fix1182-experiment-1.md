**Run** cc-144, 2026-09-22 04:17–04:51 UTC, prod reads under `--allow-prod`.
**Set A** the committed 2026-09-14 manifests (the only surviving copy — see §5).
**Set B** the 2026-09-22 re-cut against the emit set completed 2026-09-21.

FIX-1106 read one run's anti-join as "these rows are residue, delete them".

have been in it. Two complete runs are the smallest instrument that separates

## 2. The expectation was inverted

FIX-1182's own append predicted class (ii) for indiv ≈ **34 officials / 18,533
rows / $30,261,581** — the twin-less cohort. Measured, that cohort is class
**(i)**: 35 / 18,722 / $30,526,063. Class (ii) is **one official**.

The prediction had the right cohort and the wrong class. It assumed the
twin-less officials would turn out to be retractions once a second run existed.
They are the opposite: they are the recipients *both* complete runs declined to
emit, which is precisely the class FIX-1182 was filed to protect from deletion.
A single-run apply would have deleted them; the second run's evidence is what
says not to.

**The applicable class, in full** — three (recipient, source) pairs, two
officials:

| source | official | rows | $ | in set A | `last_write` |
|---|---|---:|---:|---|---|
| indiv | Everton Blair | 675 | $604,079 | PARTIAL (22 residue, **653 emitted**) | 2026-09-01 01:17 |
| pac | Everton Blair | 7 | $21,500 | absent (no residue ⇒ fully emitted) | 2026-09-01 00:30 |
| pac | Britta Aguirre | 1 | $654 | absent (no residue ⇒ fully emitted) | 2026-08-08 03:34 |

Blair's indiv row is the cleanest possible instance: `emitted_rows` went
**653 → 0** between the two runs. Run A emitted 653 of his rows; run B emits
none. That is a retraction with a witness, not an inference.

Against the $1,481,928,516 FIX-1106 originally claimed, the two-run evidence
supports **$626,233** — 0.04 %.

## 4. ITC did not move at all

`fec_bulk_indiv_to_committee` returns **626 / 106,278 / $536,845,833** — every
figure identical to 2026-09-14, across two complete emit runs eight days apart.
Classes (ii) and (iii) are both exactly empty.

An identical-to-the-row result is not "stable residue". A residue set that
shrinks is a set the source is still writing; a set that does not move by a
single row is a set nothing in the emit path ever reaches. That is FIX-1203's
claim — no committee-to-candidate binding is persisted anywhere — arriving
independently as a measurement rather than an argument. The 626 are not
decaying residue awaiting a sweep; they are structurally unemitted, and a
second run has now said so.

ITC is excluded from every apply (cc-139 §3, FIX-1203). This experiment adds
the reason rather than the exception.

## 5. Provenance — why "absent from A" is not enough

"Not in A's DROPPED-OUT list" has three causes and only two are retraction:

- (a) A emitted it fully → retraction
- (b) A emitted it partly (`PARTIAL` in A) → retraction, and still a retraction
- (c) **the rows did not exist when A was cut** → proves nothing

(c) is the trap: a recipient created between the two runs and not yet emitted
looks exactly like a retraction under a naive set difference, and would be
deleted. The classifier separates it on the row's own `last_write` — if every
row predates set A's generation timestamp, the rows were there for A to judge
and A did not call them residue. Anything younger is demoted to UNPROVEN.
All three pairs in §2 clear it with 13–45 days of margin.

This check caught a real defect in its first run. `last_write` is Postgres's
`2026-09-01 01:17:41.714183+00`, whose `+00` is **not** valid ISO 8601 —
`new Date()` returns Invalid Date. Every candidate retraction therefore failed
the provenance check and the experiment reported class (ii) as empty for
exactly the right-looking reason. A fail-closed check that fails closed for a
parse bug is indistinguishable from a true negative, so the parser now has its
own test.

## 6. Set A exists only on disk, and that is the design

`fec_emit_runs` and `fec_emit_keys` are UNLOGGED **deliberately and together**
(`20260909000000_fix1106_fec_emit_set.sql:32-40`): crash recovery truncates
them, which "is the FAILURE MODE WE WANT" — a truncated ledger makes the audit
REFUSE (no runs row) rather than anti-join a prefix and classify live rows as
residue. The 2026-09-15 crash recovery took set A's rows exactly as intended.

cc-141 §5.1's "somebody should file" about this is a rediscovery of a documented
choice, not a defect. **No FIX is filed.** The rule that comes out of it:

> A two-run comparison keys on the COMMITTED manifests, never on the database's
> emit ledger. The ledger is deliberately volatile; the manifests are the
> durable record, and committing them is what makes experiment (1) possible at
> all eight days later.
