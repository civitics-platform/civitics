# FIX-1180 / FIX-1181 — the anon-vs-authenticated cancel split for `get_official_page`, and how two `service_role` RPCs ran past 8 s

cc-137, 2026-09-19 03:06–04:10 UTC. Reads only on prod (Logs API + `db-query
--prod`); all EXPLAIN work on the local prod-clone. No migration, no prod write,
no `cron.job` change.

**Both bullets' central premises turned out to be wrong, in different ways.**
FIX-1180 asks for an anon-vs-authenticated split that cannot exist, because the
page has no authenticated caller. FIX-1181 asks why two RPCs complete past 8 s,
and they no longer do — the behaviour ended at a Postgres restart, and the repo
has no site that could have caused it. Neither closes on this evidence; both get
a much sharper statement of what they are.

## 1. Read 2 — what a cancellation row actually carries

### 1.1 The parsed shape

`select p.*` returns `Backend error! Retry your query`. `select p` returns the
whole struct and works. **25 fields**, every one confirmed present:

```
application_name  backend_type  command_tag  connection_from  context
database_name     detail        error_severity  hint          internal_query
internal_query_pos  leader_pid  location      process_id      query
query_id          query_pos     session_id    session_line_num
session_start_time  sql_state_code  timestamp  transaction_id  user_name
virtual_transaction_id
```

On a PostgREST-originated `57014` row, populated: `query` (the full ~600-char
`WITH pgrst_source AS (…)` envelope), `user_name`, `application_name`
(`postgrest`), `backend_type` (`client backend`), `command_tag` (`SELECT`),
`connection_from`, `database_name`, `session_id`. There is **no duration field**,
which matters in §3.4.

### 1.2 Two limits the API does not enforce for you

**The 24-hour clamp.** A window longer than 24 h is answered from the day
containing `iso_timestamp_start`, and `iso_timestamp_end` is ignored. No error,
no warning, no short result — a full, plausible 24 h of rows that are the
**oldest** day of the range asked for. Measured, each request made at
2026-09-19T03:07Z:

| lookback asked | rows | rows actually covering |
|---|---|---|
| 1 day | 3,790 | 2026-09-18T03:08 → 2026-09-19T03:06 (the whole window) |
| 2 days | 4,824 | 2026-09-17T03:08 → 2026-09-18T03:06 (**oldest day**) |
| 3 days | 3,857 | 2026-09-16T03:08 → 2026-09-17T03:06 (**oldest day**) |
| 4 days | 3,897 | 2026-09-15T03:08 → 2026-09-16T03:06 (**oldest day**) |
| 7 days | 3,874 | 2026-09-12T03:08 → 2026-09-13T03:06 (**oldest day**) |

A prompt asking for "the longest window the API keeps" — which is what cc-137's
D2 asked for — would have got day 1 of 7 and quoted it as seven. The census now
refuses above 1440 minutes rather than under-reporting.

**Retention is 7 days.** A window starting 7 days back returns rows; 8, 9 and 10
days back return zero. (11–13 were not measured: the API answered
`ThrottlerException: Too Many Requests`. It rate-limits, which is why the
attribution mode reads one window per invocation rather than looping days.)

### 1.3 The finding that decides FIX-1180's shape

**`user_name` on a PostgREST cancel row is always `authenticator`.** PostgREST
logs in as `authenticator` and then `SET ROLE`s to `anon` / `authenticated` /
`service_role`; the Postgres log records the **login** role, not the current one.
Grouped over 24 h of prod:

```
── 57014 attribution ── by user_name
   2026-09-18T03:22:09Z → 2026-09-19T03:22:09Z
   group           count  share
   authenticator      38  100.0 %
```

38 of 38. Zero rows carrying anon, authenticated or service_role.

Meanwhile `pg_stat_statements` **does** record the impersonated role (its
`userid` is the effective user), so completions are split by role and cancels are
not. The two instruments cannot be joined on role, and there is no duration field
to infer it from (§1.1). **The anon-vs-authenticated split is not readable from
this instrument.** §3.1 shows the question is moot anyway.

## 2. Item 1 — the attribution mode

### The SQL, as sent

```sql
select
  coalesce(regexp_extract(p.query, r'"public"[.]"([a-z0-9_]+)"'),
           substr(regexp_replace(coalesce(p.query, t.event_message), r'\s+', ' '), 1, 60)) as g,
  count(*) as n
from postgres_logs t
cross join unnest(t.metadata) as m
cross join unnest(m.parsed) as p
where p.sql_state_code = '57014'
  and p.query like '%<like>%'      -- only when --like is given
group by g
order by n desc
limit 20
```

Grouping is on the **function name pulled out of the envelope**, never the
envelope: PostgREST's wrapper differs per bind-parameter shape, so grouping on
raw text returns one row per shape and blows the ~100-row cap while saying
nothing. A table-level query with no function in it falls back to its first 60
characters. Server-side aggregate, `limit 20` — at most 20 rows however busy the
window.

`--by` is allow-listed against the probed field list (it is interpolated into
SQL); `--like` is restricted to `[A-Za-z0-9_. :/-]`, 1–120 chars.

### The two runs

```
── 57014 attribution ── by user_name
   2026-09-18T03:22:09Z → 2026-09-19T03:22:09Z
   group           count  share
   authenticator      38  100.0 %
                      38  total

── 57014 attribution ── by query · query like %get_official_page%
   2026-09-18T03:22:21Z → 2026-09-19T03:22:21Z
   group               count  share
   get_official_page      10  100.0 %
                          10  total
```

Unfiltered over the same 24 h, **`get_official_page` is the single most-cancelled
statement on prod** — 10 of 38, ahead of `enrichment_queue` (9) and
`check_senate_reference_cohort` (7). `link_officials_to_districts` appears with 1.

Three refusals behave: `--minutes 10080` (names the clamp), `--like` without
`--by`, and an unknown `--by` (lists the known fields). All exit 2.

## 3. Read 4 + D2 — `get_official_page`

### 3.1 It has no authenticated caller. The split does not exist.

The page calls the RPC at `apps/civitics/app/officials/[id]/page.tsx:353`
through `createPublicClient()` — the **publishable key**, `persistSession:
false`, no cookie handling (`packages/db/src/client.ts:84`). It is not
`createServerClient(cookies())`. **Every visitor is anon, logged in or not.**

pgss corroborates exactly: over 3.50 days, `get_official_page` has **366 calls
under `anon` and zero under `authenticated`**.

So FIX-1180's framing — "anon visitors get a cancel where authenticated ones do
not" — is wrong, and not because the cancel does not happen. There is simply no
authenticated path to compare against. Every visitor is on the 3 s bound.

### 3.2 Grants, proconfig, bounds

`EXECUTE` to `PUBLIC`, `anon`, `authenticated`, `postgres`, `service_role`.
`prosecdef = false`, language `sql`. `proconfig` is `{search_path=public,
extensions}` only — FIX-1128's `RESET` of the decorative `statement_timeout`
holds, confirmed on prod.

`pg_db_role_setting`, prod, 2026-09-19 03:09 UTC:

| role | setting |
|---|---|
| `anon` | `statement_timeout=3s` |
| `authenticated` | `statement_timeout=8s` |
| `authenticator` | `session_preload_libraries=safeupdate`, `statement_timeout=8s`, `lock_timeout=8s` |
| `postgres` (IN DATABASE postgres) | `statement_timeout=3h`, `work_mem=256MB` |
| `supabase_admin` | `statement_timeout=0` |
| **`service_role`** | **no row** |

### 3.3 The split, replaced by the number that matters

pgss, `anon`, since the epoch: **366 calls, mean 321.4 ms, max 2,858.3 ms,
stddev 639.0 ms.** The max sits 142 ms under the 3 s bound — the signature of a
distribution truncated by a cap, not of a fast function.

Cancels, from the Logs API, in windows aligned to the pgss epoch so the two are
comparable:

| window | all 57014 | `get_official_page` |
|---|---|---|
| 09-15 15:09:48 → 09-16 15:09:48 | 41 | 10 |
| 09-16 15:09:48 → 09-17 15:09:48 | 568 | 47 |
| 09-17 15:09:48 → 09-18 15:09:48 | 179 | 16 |
| 09-18 15:09:48 → 09-19 03:12 (11.7 h) | 19 | 7 |
| **total (3.50 days)** | **807** | **80** |

> The 568-cancel window is an event, not a baseline; 91 of those were
> `get_jurisdiction_page` and 71 `jurisdictions`. It is included because it is
> inside the pgss window and excluding it would flatter the rate.

**Cancel rate for anon `get_official_page` = 80 / (80 + 366) = 17.9 %.**
Excluding the event window it is 33 / (33 + ~261) ≈ 11.2 %. Either way this is
branch **(ii)** by any threshold — roughly one in six to one in five official
page-views loses its sections.

### 3.4 What the visitor sees

`withDbTimeout(sb.rpc(…), 5000, "officials:page-rpc")` is a **client-side
`Promise.race`** (`apps/civitics/src/lib/supabase-check.ts:66`) — it issues no
SQL. Its 5 s is longer than the server's 3 s, so the server always wins, and the
wrapper's `{ data }` destructure turns the cancel into `data: null`. The page
then shims every section to `[]` / `null` / `0`. **A cancelled page renders as a
real official with an empty record — no error, no 500, nothing in the logs but
the 57014.** That is the harm, and it is silent.

### 3.5 Where the time actually goes — measured, and not where the bullet implies

All EXPLAIN on the clone with `max_parallel_workers_per_gather = 0`. Quoting
**buffers**, not ms: a warm re-run of the same section fell from 1,294 ms to
13 ms, so ms here measures cache state, not work.

The prompt's cohort was "the ten heaviest by `official_donor_totals`". That is
the wrong axis — **this RPC has no donor section** (donors come from
`official_donor_rollup_mv`, read separately). Full-RPC buffers:

| official | votes | donations | RPC buffers |
|---|---|---|---|
| Kamala Harris | 0 | $268.6 M (rank 1) | **3,670** |
| Mark Kelly | 1,871 | $42.0 M | 14,709 |
| Ted Cruz | 1,875 | $36.6 M | 13,295 |
| Raphael Warnock | 1,875 | $69.8 M | 13,274 |

The #1 donor official is the **cheapest of the four**. Cost tracks **vote count**.

Per-section, Warnock (1,875 votes), of 13,272 buffers:

| section | buffers | share |
|---|---|---|
| `recent_votes` (LIMIT 100) | **6,034** | 45.5 % |
| `all_votes` (LIMIT 500) | 3,556 | 26.8 % |
| `spending` (global top-10) | 56 | 0.4 % |
| `vote_count` | 24 | 0.2 % |
| the other five sections | ~3,600 | ~27 % |

`spending` was the obvious suspect — it scans `financial_relationships` with **no
official filter at all**, identical for every official, and the body says so. It
is **not** the problem: `financial_relationships_amount` makes the global top-10
an index scan, 56 buffers and 22.5 ms. Measured, not assumed.

### 3.6 The actual defect: a `NULLS LAST` the column does not need

`recent_votes` returns 100 rows and costs more than `all_votes`, which returns
500. Its plan explains why:

```
Sort  (Sort Key: v.voted_at DESC NULLS LAST, top-N heapsort)   Buffers: 5,634
  └─ Nested Loop Left Join  (rows=1875)                        Buffers: 5,631
       └─ Bitmap Heap Scan on votes  (rows=1875, Heap Blocks: exact=1855)
            └─ Bitmap Index Scan on votes_official
```

It fetches **all 1,875 of the official's votes**, joins every one to `proposals`,
then top-N sorts down to 100. The `LIMIT 100` saves nothing; the work is
proportional to the official's whole voting history.

An index that would serve it already exists — `votes_official_voted_at` on
`(official_id, voted_at)` — and cannot be used, because **`DESC NULLS LAST` is
not the reverse of `ASC NULLS LAST`**. Scanning that index backwards yields
`DESC NULLS FIRST`, so the planner gives up and sorts. (This is
`project_consolidating_rpc_null_ordering` again, from the other side: there the
fix was to write `DESC NULLS FIRST` in the reader.)

**`voted_at` has no NULLs at all** — 0 of 969,302 on the clone, 0 of 982,966 on
prod — so the two orderings select and order identically today. The column is
not `NOT NULL`, so the planner cannot prove it.

Three measurements on the clone, all with the outer
`jsonb_agg(… ORDER BY rv.voted_at DESC NULLS LAST)` retained so output order is
unchanged:

| `recent_votes` variant | plan | buffers |
|---|---|---|
| today (`DESC NULLS LAST`) | Bitmap Heap Scan 1,875 rows + top-N heapsort | **6,034** |
| inner `ORDER BY voted_at DESC` | Index Scan Backward, 100 rows | **736** |
| today's text + index on `(official_id, voted_at DESC NULLS LAST)` | Index Scan, 100 rows | **731** |

Whole-RPC effect of the index (probe index built and dropped on the clone; 16 MB
against a 338 MB `votes` heap):

| official | votes | RPC buffers today | with the index | change |
|---|---|---|---|---|
| Warnock | 1,875 | 13,274 | 7,989 | **−40 %** |

(13,274 here against 13,272 in the per-section table: two runs of the same
measurement, two buffers apart. Both are quoted as read.)
| worst case on the clone | 2,530 | 14,882 | 7,702 | **−48 %** |

The affected cohort is not small: **408 officials have more than 1,000 votes**,
521 more than 500, 558 have any, and the maximum is 2,530.

### 3.7 D2 — the proposal, and the decision that is Craig's

Branch (ii) fires. But the fix shape the bullet assumes — "materialization or
moving the heavy part off the request path" — is **not** what the measurement
supports as the first move. The first move is much smaller:

- **(A) Add `votes (official_id, voted_at DESC NULLS LAST)`.** Exact semantics,
  no RPC change, correct even if a NULL `voted_at` ever appears. ~16 MB on prod
  and one more index on the vote-writer path (13 exist today). Halves the RPC on
  the cohort that is being cancelled.
- **(B) Drop `NULLS LAST` from the inner `ORDER BY`** and use the existing index.
  Zero new bytes, zero write cost. Identical results while `voted_at` has no
  NULLs; if one ever appeared it would be picked into the top-100 rather than
  excluded.
- **(B′) (B) plus `ALTER TABLE votes ALTER COLUMN voted_at SET NOT NULL`**,
  making (B) exact by construction. Needs a full validation scan.

**Recommended: (A).** It is the only one of the three that cannot change which
rows a page shows, and 16 MB is cheap against 983k rows.

`all_votes` (3,556 buffers, 500 rows fetched per page-view so the app can tag
issues client-side) becomes the largest section after (A) and is the *second*
lever — and that one genuinely is a materialization question. Not proposed here.

**FIX-1180 stays OPEN.** A measurement does not earn `Fixes:`, and the build is
out of scope for this run.

### 4.2 Every `statement_timeout` / `set_config` site in the repo, classified

Session-scoped `SET statement_timeout` (no `LOCAL`): `direct-pg-upsert.ts:48`
and `:75`, `heavy-rebuild.ts:115/155/224/285/313/351`, `prod-session.ts:533`,
`session-lock.ts:102`, `littlesis/matcher.ts:171`.

**Every one of them is on a `pg.Client`/`Pool` the code constructs itself and
closes in a `finally`.** None is a PostgREST connection; node code cannot reach
PostgREST's pool with a `SET` at all — it is a separate process.

Transaction-scoped, correct as written: `fr-rewrite-drain.ts:95`
(`SET LOCAL statement_timeout`), `moderation-harness/index.ts:176`
(`set_config(…, true)`, and for `request.jwt.claims`, not a timeout).

`apps/civitics/app/**` contains **zero** executable `SET`/`set_config` sites —
comments only. `withDbTimeout` is a client-side `Promise.race`; it issues no SQL.

**So the bullet's candidate — "a pooled `authenticator` connection on which
something issued a non-`LOCAL` `SET statement_timeout`" — is refuted. No such
site exists, and no site in this repo could reach that pool.** Item 2 of cc-137
is therefore not built, and FIX-1181 earns no `Fixes:`.

### 4.3 The bound is real, and `service_role` inherits it

`service_role` has **no** `statement_timeout` of its own (§3.2). Its effective
bound is `authenticator`'s 8 s, taken at login and unaffected by `SET ROLE` —
which is what FIX-1128's probe measured on 2026-09-13 and recorded as
"authenticator 8s, inherited by impersonated service_role (MEASURED)".

### 4.4 It stopped happening, and the restart is when

| function | epoch | calls | mean ms | max ms | over 8 s? |
|---|---|---|---|---|---|
| `link_officials_to_districts` | pre-restart (09-13 audit) | 5 | 9,895.4 | **12,402.8** | every call |
| `link_officials_to_districts` | post-restart (3.50 d) | 1 | 7,419.1 | **7,419.1** | no |
| `refresh_primary_source_for_entities` | pre-restart | 479 | 107.4 | **9,835.7** | yes |
| `refresh_primary_source_for_entities` | post-restart | 240 | 166.7 | **7,577.0** | no |

**241 service_role completions since the restart, not one past 8 s**, both maxima
sitting a few hundred ms under it — and `link_officials_to_districts` appears in
the cancel log in the same period, so it is being bounded now.

A pgss row is genuinely a completion, not a recorded cancel. Measured on the
local clone: `SET statement_timeout='1s'` then `SELECT pg_sleep(3.5)` is
cancelled and leaves **zero** pgss rows. So the pre-restart numbers were real
over-bound completions, not an artefact.

Two mechanisms were tested against the functions themselves and **both refuted**:

- *A caught `query_canceled` disarms the timer for the rest of the statement*
  (the CLAUDE.md rule) — would produce exactly this signature. **None of the
  three functions has an `EXCEPTION` block**, no `WHEN OTHERS`, no mention of
  `query_canceled`. `pg_proc.prosrc`, prod.
- *A loosening proconfig* — FIX-1128 already measured that a proconfig cannot
  loosen, and in any case only `search_path` is set.

### 4.5 The remaining explanation, and the read that would confirm it

`statement_timeout` for `authenticator` comes from `pg_db_role_setting` and is
applied **at login**. PostgREST holds a long-lived connection pool, so a backend
that logged in before that setting existed — or under a different value — keeps
the old bound for its whole life, and nothing in-database will show the
discrepancy. A restart recycles every backend at once. That is
`reference_pooler_hides_new_role_gucs` ("role-GUC change reads OLD via pooler"),
and it fits every measured fact: over-bound completions before 2026-09-15
15:09:48, none after, no repo site, no function-level mechanism.

It cannot be *confirmed* retroactively — pgss was wiped by the same restart, and
`pg_db_role_setting` keeps no history. The read that would settle it going
forward is cheap and is the one FIX-1181 should carry: **pgss by `userid` for
these two functions, re-read weekly.** A service_role completion past 8 s
appearing again *without* an intervening restart refutes the account; a clean
week with the pool churning normally is the receipt. Monday is the first.

The competing explanation that cannot yet be excluded: the platform changed
`authenticator`'s setting at or near the restart, in which case the pool is
incidental. Distinguishing them needs a `pg_db_role_setting` value from before
2026-09-15, which nothing retains.

## 5. Read 6 — the FIX-1128 probe

**`public._fix1128_probe_sleep` no longer exists on prod.** `pg_proc` returns no
row for it (the same query returned all three of the other functions, so this is
absence, not a failed query). The optional re-measurement sanctioned by cc-137's
prod-access section could not run and was not run; nothing was created to
replace it. The 2026-09-13 bounds table remains the only measured calibration,
and §4.3 leans on it rather than on a fresh probe.

## 6. What this changes

- The census can now name the statement behind a 57014. `get_official_page` is
  the top one on prod, which nothing before this could have said.
- FIX-1180 is a real, quantified defect — **17.9 % of anon official-page RPCs
  cancelled** — with a cause one index removes half of, and a harm (silent empty
  sections) worse than the bullet describes. Its stated *framing* is wrong: there
  is no authenticated cohort.
- FIX-1181 is not a live bug. The bound works, the repo is clean, and the
  behaviour ended at a restart. It needs a watch, not a fix.
