# FIX-902 — unbounded `.in()` id-list audit

**Date:** 2026-08-13 · **HEAD at census:** `037beb1a` · **Scope of code change:** `apps/` only (see *Why not `packages/`*)
**Environment:** local Docker clone only. Zero prod connections were made for this audit.

---

## The class, restated

`supabase-js` encodes an `.in()` filter into the request URL. Past roughly **200 uuids** the
URL exceeds Kong's header limit and the gateway answers **414 `URI too long` before PostgREST
ever sees the query**. `withDbTimeout` turns that into `{data: null}`, and the near-universal
`?? []` / `data?.x` at the call site turns a hard failure into an **empty result on an HTTP
200**. Nothing logs, nothing 500s, the page renders — just missing.

**The bound is URL LENGTH at ~200 ids. It is NOT the 1,000-row `max_rows` cap.** A list of 400
ids is well under the row cap and still dies. Do not reason about this class in row counts.

Prior instances, each found by accident: FIX-509 (414 verified at ~356 uuids), FIX-514,
FIX-774 (established the 200 bound), FIX-899 (officials directory rendered zero tag pills for
months). FIX-901 shipped `fetchChunkedByIds`; FIX-926 capped its concurrency. This audit is
the sweep.

### Drift vs the bullet's estimate

The bullet estimated "on the order of 96–108 pass an id-list VARIABLE and are not obviously
chunked". The measured figure is **114** (166 id-list-variable call sites minus the 52 already
chunked) — a modest undercount, mostly because the strict single-line regex misses multi-line
builders and `.map()`-inline id lists.

The bullet's substantive prediction held: **"most are probably bounded — classifying them is
the whole job."** Of the 114, **67 (59%) are bounded** and needed only a recorded bound;
47 were genuinely growth-prone. Classification was roughly 80% of the work, migration 20%.

### The sub-class worth naming: **chunked, but chunked too wide**

Three sites (7, 8, 9) were already looping in batches — at **300, 300, and 500**. All three are
*above* the 414 threshold, not below it. They read as "someone thought about this", which is
exactly why they survived four prior sweeps. FIX-509 verified the 414 at ~356 uuids and FIX-772
at ~234, so a 300-wide chunk sits inside the failure window and a 500-wide chunk is past it.

A fourth (`sunburst:351`, `BATCH = 300`) was harmless only because its feeder is capped at 200 so
the loop never splits — a correct-looking number waiting to be copied to a site with an uncapped
feeder, which is precisely what had happened at sites 7 and 8. Pinned to `ID_CHUNK_SIZE`.

**Takeaway for the next auditor:** a batch loop is not evidence of safety. Read the constant.

## Why not `packages/` — and what was found there

Two structural reasons, both from decision 2:

1. `fetchChunkedByIds` lives in `apps/civitics/src/lib/paginate.ts`, and **packages cannot
   import from apps**. Chunking a `packages/` site requires relocating the helper into a
   package first — its own decision, with its own blast radius.
2. `packages/data` code runs in the pipelines, and **Sunday 2026-08-16's nightly is an evidence
   run (FIX-1014/936/937 first exercise) that must execute known code.**

`packages/` is in much better shape than `apps/` — 22 of its 36 id-list call sites are already
chunked at ≤200, because the pipelines learned this lesson repeatedly and wrote it down
(`RESOLVE_IN_CHUNK`, `EDGAR_IN_CHUNK`, `DELETE_CHUNK`, `IN_CHUNK`). The 13-site remainder is
filed as **FIX-1037**; see that bullet for the worklist and the helper-relocation question.

The two highest-value items, both in `packages/db` and both reachable from request-path `apps/`
code:

- **`fetchEntityIdsByIndustryTag`** (`entity-industry.ts:46`) has no `.in()` at all, so it does
  not appear in this census — but it is the *feeder* for migrated sites 10 and 11, and it is
  **silently truncated at PostgREST's 1,000 rows** out of 8,908 `health`-tagged entities.
  Demonstrated live during this audit: `GET /api/graph/treemap?entityId=…&industry_filter=health`
  returns `[]` even though the official has a real health-industry donation, because the one
  qualifying donor is not among the arbitrary 1,000 returned. The same call with
  `industry_filter=retail` (a sub-1,000 tag) returns 16 KB of correct rows. **Chunking the
  callers fixed the 414; it does not fix the truncation.**
- **`financial-relationships.ts:55,85`** — `getTopDonorsByOfficial` builds up to 1,000 distinct
  donor ids into one `.in()`; `listDonationsByDonor` feeds it an uncapped `ilike` result.

## Explicitly out of scope

Per decision 6, and recorded here so the next auditor does not re-open them:

- **A lint rule or codemod banning raw `.in()`.** Tempting, and this audit strengthens the case
  — but the discrimination it needs is exactly the (a)-vs-(c) judgment that took this whole
  audit to make, and 47 of 254 lines are legitimate small literal enums. It would have to
  distinguish an id list from an enum list, which is a design question of its own.
- Any `packages/` code change (decision 2). Filed as FIX-1037.
- Any change to `withDbTimeout`.
- Anything donor-rollup / MV / canary.
- Prod connections of any kind.
