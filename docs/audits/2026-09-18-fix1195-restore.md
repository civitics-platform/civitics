## 1. The defect, exactly

`promote_candidate_to_elected()` merged the two rows' `source_ids` as:

```sql
  -- Merge source_ids: jsonb || jsonb keeps the right operand on key conflict,
  -- so we want (candidate || elected) — candidate's fec_candidate_id is
  -- preserved, elected's congress_gov is appended.
  SELECT (c.source_ids || e.source_ids)
```

The comment states the rule correctly and the code does the opposite of what the
comment concludes. `a || b` keeps **b** on conflict, so `(c || e)` keeps the
**elected** row's keys. The elected row is then DELETED. So on every promotion
the surviving candidate row came out holding the deleted row's
`fec_candidate_id` instead of its own, and the candidate's own id ceased to
exist anywhere in the table.

That is the FIX-240 binding — the id every IE relationship hangs off — which is
the reason the promotion keeps the candidate's UUID in the first place. The
function preserved the UUID and destroyed the identity it was preserving it for.

**Callers.** One: `promoteCandidatesDirect()` in `packages/data/src/lib/heavy-rebuild.ts`,
called only from `runCandidateToElectedPromotion()` in
`pipelines/congress/promote-candidates.ts` (the nightly).
`merge-same-person-official-dupes.ts` names the RPC only in a comment, to say it
goes the other way. `v_merged_source_ids` is written to `officials.source_ids`
and echoed in the returned jsonb as `merged_source_ids`; nothing downstream
reads that return value's arrays.

## 2. Which array actually restores a claim (read 3)

The restore's array choice was decided by reading the parsers, not from memory.
Measured across `packages/data/src/pipelines/fec-bulk/{claims,index,candidates}.ts`:

| array | claimed by `buildMatchIndex` pass 1 | blocks the cn{yy} re-mint |
|---|---|---|
| `fec_candidate_id` | **YES** | **YES** |
| `prior_fec_candidate_ids` | **YES** | **YES** |
| `merged_fec_candidate_ids` (and the `_id` scalar) | **NO** | **NO** |

Both readers — `buildMatchIndex` pass 1 (`index.ts:553`) and
`loadOfficialsByFecIds` (`candidates.ts:478`), which is the map both
`candidates.ts` and `mint-ie-targets.ts` consult before minting — call
`authoritativeClaims()`. That function returns `fec_candidate_id` plus
`priorClaims()`, then **filters out anything the row has retired** (FIX-955).

So `merged_fec_candidate_ids` is not a weaker claim, it is the *absence* of one.
An erased id filed there stays exactly as re-mintable as an erased id left
erased. **All three ids therefore go to `prior_fec_candidate_ids`**, including
the two same-chamber cases. That array is explicitly not role-gated
(`claims.ts`), and these are genuinely different seats: `H4NC08066`/`H6NC09200`
are NC-08 and NC-09; `H2NJ08232`/`H2NJ13075` are NJ-08 and NJ-13.

This is the one place the run departed from cc-131's design, which filed a
same-office loser as merged. See §7.

## 6. The script's post-check was wrong, and said so loudly

The apply **committed correctly and then exited 2.** Its second verification
block counted a retired marker on *any* row as a holder, so it read:

```
── Previously-live ids, unchanged ───────────────────────
  H4NC08066  live=1 prior=0 merged=1 fec_id=0   ← 2 holders
  H2NJ08232  live=1 prior=0 merged=1 fec_id=0   ← 2 holders
  H6KS01179  live=0 prior=1 merged=1 fec_id=0   ← 2 holders
✗ 3 id(s) do NOT have exactly one holder after the write. Investigate.
```

The three `merged=1` markers are on set 1's merge stubs — `63740b8b` (Harris),
`b7da3e46` (Menendez), `ce2b114f` (Marshall), each carrying
`{"merged_fec_candidate_ids": ["<the id>"]}` and nothing else. That is the
**correct** post-merge shape: the stub records the id it gave up while the
survivor holds it live. `authoritativeClaims()` filters it out, which is the
whole reason §2's table says merged is not a claim — so a check that counts it
as one contradicts the rule the same script is built on.

Fixed in the same commit as this audit: the post-write check now uses an
authoritative-claim census (`AUTH_CENSUS_SQL`), and reports retired markers
separately as expected context rather than counting them. The pre-write census
keeps the strict all-surfaces form, which is right there — an id about to be
restored must be unheld *everywhere*, retired included.

Two smaller notes from the same run:

- Writing that census as `NOT (a ? x OR b = x)` drops **every** row when `b` is
  NULL: `NULL = 'X'` is NULL, `false OR NULL` is NULL, `NOT NULL` is NULL. The
  first version of the ad-hoc query returned 0 holders for all six ids for
  exactly this reason. `COALESCE(b = x, false)` is load-bearing.
- Exiting non-zero after COMMIT skips the interlock's release line. The advisory
  lock still dropped with the connection — `prod_session_state()` read
  `held: false` with a stale label, which the next claim clears — so nothing was
  blocked, but the console gives no "released" line to read.

## 7. What contradicted the design

**cc-131 S2(ii) would have re-created the defect for two of the three rows.** It
routed a loser whose office prefix matches the winner's into
`merged_fec_candidate_ids`, on cc-128's semantics (prior = another office,
merged = a same-office duplicate). Harris and Menendez are both H→H, so both
would have gone there.

Read 3 — which the prompt itself commissioned to settle exactly this — shows
that array is filtered out of `authoritativeClaims()`, claimed by neither pass 1
nor `loadOfficialsByFecIds`, and therefore no bar to the cn re-mint. Filing the
two ids as retired would have left them with zero authoritative holders going
into Sunday, which is the state the restore exists to leave behind.

The naming intuition is not wrong about what the arrays *mean*; it is wrong
about what they *do* when the other row is being deleted. Retirement is safe in
a merge because the survivor keeps the id live. In a promotion nothing else
holds it. So the run took the prompt's stated principle — "never drop it" — over
its stated mechanism, filed all three as prior, and applied the same rule inside
the migration. `prior_fec_candidate_ids` is not role-gated, so nothing structural
objects.

Beyond that, nothing contradicted the design. cc-130 §4's table, the 0/0/0
census, the clone's pre-promotion rows and Marshall's 4,867 FR rows all read
exactly as predicted.
