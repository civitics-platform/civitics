## 10. Issues observed during the run

1. **CRITICAL — 8 GB NODE_OPTIONS ceiling insufficient for presidential cycle indiv when FIX-236 is active.** Documented in CLAUDE.md but [.github/workflows/nightly.yml:40](../.github/workflows/nightly.yml) is still set to 8192. Standard Sunday cron is safe (current-cycle only = 2026 midterm, smaller) but any manual or one-shot run that includes 2024 indiv will OOM. See Section 11 FIX candidate.
2. **`data_sync_log.fec_bulk` row left in `status='running'`.** When Node SIGABRTs on OOM, the pipeline can't reach `completeSync()` or `failSync()`. Future `pnpm data:status` or dashboard reads will see this row as "in flight forever." Either a SIGTERM/SIGSEGV handler or a stale-row reaper is needed. See Section 11 FIX candidate.
3. **R2 cache miss on `indiv24.zip`** (source=fec in download log) even though FIX-192 added R2 caching. Probably the indiv24.zip Last-Modified header changed since the prior run, OR the R2 mirror hasn't been seeded for indiv24 specifically. The pas224.zip download in the same stage DID hit R2 (source=r2). Likely a per-file watermark gap. See Section 11 FIX candidate.
4. **PostgREST upsert chunk 119500-120500 returned HTML error during PAC relationship batch upsert** — 500 rows failed in that chunk (0.37% of the stage). Suggests a transient pooler hiccup during a long-running session. Not catastrophic but worth a retry-with-backoff. See Section 11 FIX candidate.
5. **Pre-existing DC jurisdiction duplicate row** caused PGRST116 ("Results contain 2 rows...") on jurisdiction upsert at run start. Non-fatal — pipeline continued. Predates this run.
6. **The 2026-05-11 manual fec_bulk runs are not annotated** — three runs at 05:11/05:14/05:44 UTC produced 240K-253K rows each in 3-5 min. These were almost certainly partial runs with `FEC_INCLUDE_INDIV=false` (which would skip indiv and run only PAC+IE), explaining the existing `ie_support=3315`/`ie_oppose=1396` rows on prod. Worth recording in done.log retroactively.
7. **No Vercel egress, Supabase bandwidth, or spend-cap alerts fired** during the run. Cost-shape estimate stays within nominal — only 4 GB FEC egress in + ~135K Pro writes.

## 12. Open questions

Is the breaking point a function of donors-aggregated (memory) or lines-streamed (CPU)? 2. **Why did `pas224.zip` hit R2 but `indiv24.zip` miss?** R2 caching has per-file watermarks; the indiv file may have its own freshness gate that the pas2 file doesn't. Or the indiv mirror is empty.
3. **What's the actual indiv24 size delta since the last successful prod ingest?** The Last-Modified watermark should be in pipeline_state but I didn't find an entry keyed off `fec_bulk_indiv_<cycle>`. May be using a different scheme.

The question is whether the PAC stage should also stay current-only or include 2024 — FIX-236 needs the 2024 file to capture super-PAC contributions from the recent presidential cycle. Worth confirming the intended cron-time cycle list.
5. **Is the 500-row chunk failure during PAC upsert reproducible?** Single transient pooler 502 or a sign of intermittent overload? Single-run sample isn't enough to tell.
