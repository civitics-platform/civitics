# FIX-1128 Half 2 — the pg_cron job census, the budgets, the cancel handlers, and why the command-string bound cannot be built

Run: cc-125, 2026-09-14 UTC. Prod reads via `scripts/db-query.mjs --prod`
(read-only); every mechanism probe ran on the LOCAL clone's live pg_cron
scheduler and was torn down afterwards. No prod writes.

**Headline: H1 is unbuildable.** `SET statement_timeout = '<N>'; CALL
public.<proc>(...)` in a pg_cron command string does not bound the six census
procedures — it *prevents them from running at all*. Every one of them COMMITs
internally, and a multi-statement pg_cron command runs in an **implicit
transaction block**, where a procedure cannot COMMIT. Measured below (section 4).
cc-124's experiment 6 was right about its own object — a `SELECT` of a
non-COMMITting SQL function — and does not generalise to the objects Half 2
targets.

---

## 4. Why H1 cannot be built — four cases on the clone's live scheduler

Probe procedure `_fix1128_probe_units(p_units, p_unit_seconds)`: a unit loop
whose body is `pg_sleep`, wrapped in `EXCEPTION WHEN query_canceled` that records
and sets a flag, a `COMMIT` after each unit, `EXIT WHEN` the flag is set, then a
terminal row. That is the C1 shape in miniature. Each case below is a real
`cron.job` row fired by the real scheduler.

| # | command string | result |
|---|---|---|
| B1 | `SET statement_timeout = '3s'; SELECT public._fix1128_probe_sleep(20);` | **failed at 3.006 s** — `canceling statement due to statement timeout` |
| B2 | `CALL public._fix1128_probe_units(3, 1);` | **succeeded, 3.027 s** — all three units ran, terminal row written |
| B3 | `SET statement_timeout = '10s'; CALL public._fix1128_probe_units(5, 4);` | **failed at 0.008–0.018 s** — `invalid transaction termination` |
| B4 | `SELECT 1; CALL public._fix1128_probe_units(3, 1);` | **failed at 0.013 s** — `invalid transaction termination` |

- **B1 reproduces cc-124 experiment 6 exactly.** The bound is real — for a callee
  that never COMMITs.
- **B2 is the control.** The same procedure as a single-statement command runs
  fine, under the role's 6 h: the probe log's first row reads
  `start (timeout=6h, pid=678)`.
- **B3 is the design's proposal.** It does not bound the procedure; it stops it
  running. Zero units executed — the run dies at the procedure's first `COMMIT`,
  about 10 ms in, and the opening INSERT rolls back with it. Three consecutive
  firings, identical.
- **B4 is the clincher: it is not the `SET`.** Any pg_cron command with more than
  one statement puts the `CALL` in an implicit transaction block, and `COMMIT`
  inside one raises `invalid transaction termination`.

Two escapes were tried; both fail identically (`invalid transaction
termination`, 0.020–0.028 s):

```
BEGIN; SET statement_timeout = '3s'; COMMIT; CALL public._fix1128_probe_units(10, 1);
SET statement_timeout = '3s'; COMMIT; CALL public._fix1128_probe_units(10, 1);
```

An explicit transaction boundary inside the command string does not release the
trailing `CALL` from the implicit block.

**This is the same rule as cc-124's experiment 2, on a different surface.** The
design already recorded that "a routine with ANY `SET` clause runs in an atomic
context and cannot COMMIT — which is why the census has 91 functions and no
procedure". Atomic context implies no COMMIT, and an implicit transaction block
is an atomic context. Experiment 6 tested a FUNCTION; the generalisation to
PROCEDUREs was never re-measured.

### What else was tried

- **Per-job role carrying the bound as a role-level GUC** — `ALTER ROLE r SET
  statement_timeout`, then `cron.alter_job(jobid, username := r)`. This keeps the
  command a single statement, so the procedure may still COMMIT, and a role-level
  GUC demonstrably *does* arm for a whole `CALL`: that is exactly what the
  `postgres` role's 6 h is, and it is what ended FIX-1123's 21,638 s run.
  **Refused: `ERROR: must be superuser to alter username`.** `postgres` is not
  superuser on Supabase (`pg_user.usesuper = f`, local and prod).
- **dblink per firing** — a single-statement command calling a function that
  opens one connection and issues `SET ...; CALL ...` as separate statements
  would work, at the cost of one extra backend per firing. `dblink` is available
  but **not installed** on either database, and installing it is a
  security-surface decision, not a Half 2 cleanup.

### What remains

The FIX-1063 watchdog is the **only** per-job bound available, and it works
(section 3; `cron_job_budget_action` has 11 recorded cancels). The one in-backend
mechanism that survives is **role-level and therefore global**: `ALTER ROLE
postgres IN DATABASE postgres SET statement_timeout`, today 6 h. Every healthy
census run fits under 7,125.6 s and every incident starts at 12,546.6 s, so a 3 h
ceiling would separate them cleanly — but it applies to every `postgres`-role
statement, migrations and interactive sessions included. Out of scope here;
filed.

## 5. The cancel handlers — already record-and-STOP

H2's premise is that some handler catches `query_canceled` and continues to the
next unit. **It does not. All three C1 procedures already stop**, and the three
C2 procedures have no handler at all.

`refresh_derived_mvs` — catches by name at the unit, then, after the COMMIT:

```
    IF v_canceled IS NOT NULL THEN
      -- The timer that fired is disarmed once it has thrown, so the bookkeeping
      -- UPDATE below still runs. Continuing the loop would not: the next unit
      -- would be starting on a box that has already proven it cannot finish one.
      IF i < array_length(v_units, 1) THEN
        v_skipped := v_skipped || v_labels[i + 1 : array_length(v_labels, 1)];
      END IF;
      EXIT;
    END IF;
```

That comment is experiment 5's finding, already written down and already acted
on. The terminal row carries `status='partial'`, `metadata.canceled=true`,
`metadata.skipped_units`, `metadata.units_ok`, `metadata.unit_seconds`, and an
`error_message` naming the cancelled unit. `'partial'` deliberately does not
raise, so pg_cron is not told the job errored when the bound worked as designed.

`run_entity_connections_rebuild` — the same shape at every level: the donations
window loop (`IF v_canceled IS NOT NULL THEN EXIT; END IF;`, commented "stop the
sweep. The box has just proven it cannot finish one window"), the arm loop
(`EXIT WHEN v_canceled IS NOT NULL;` as its first statement), the fingerprint
probe, the stats-arm window loop, and a terminal `'partial'`.

`run_rule_taggers` — one unit per cadence, no loop. After the handler there is
nothing but the terminal UPDATE and the advisory unlock.

`refresh_contract_flow_rollups`, `refresh_platform_counts`,
`run_group_donor_rollup_refresh` — **no `EXCEPTION` block of any kind**. A cancel
propagates and aborts the single transaction, rolling the whole run back. Their
budget notes already say so: "A cancel here is SAFE: the procedure is one
transaction, so a cancelled run rolls back whole."

So H2 has nothing to build. Prod evidence that it works: `ec-crawl` runid 26047,
2026-09-01 12:45 — cancelled at 2086.9 s, terminal row at 13:20:15.86 naming the
cancelled window, CALL returned at 13:20:16.51 and pg_cron recorded `succeeded`,
and the next firing at 13:20:17 logged `skipped` on the advisory lock. Record,
stop, return.

## 7. Would the watchdog still have matched?

Moot now, but recorded because it nearly shipped unexamined.
`enforce_cron_job_budgets` extracts its target with `substring(command from
'CALL\s+([a-zA-Z0-9_."]+)')` and then requires `pg_stat_activity.query ILIKE '%'
|| target || '%'`. The extraction survives the multi-statement form — run against
the B3 command text it returns `public._fix1128_probe_units`. The
`pg_stat_activity` half was never observable, because every B3 and B4 run died in
about 10 ms.
