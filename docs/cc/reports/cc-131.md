## 1. Reads 2–3: the RPC line, the callers, and which arrays actually claim

The defect is one line, under a comment that states the correct rule and then
draws the opposite conclusion
(`supabase/migrations/20260706020000_fix761_promote_fk_surface_extension.sql:108`):

```sql
  -- Merge source_ids: jsonb || jsonb keeps the right operand on key conflict,
  -- so we want (candidate || elected) — candidate's fec_candidate_id is
  -- preserved, elected's congress_gov is appended.
  SELECT (c.source_ids || e.source_ids)
```

`a || b` keeps **b**. So `(c || e)` keeps the **elected** row's keys — and the
elected row is deleted four statements later. `v_merged_source_ids` is written
to `officials.source_ids` and echoed in the return as `merged_source_ids`;
nothing downstream reads that return value.

**Callers: exactly one.** `promoteCandidatesDirect()` in
`packages/data/src/lib/heavy-rebuild.ts:341`, called only from
`runCandidateToElectedPromotion()`. `merge-same-person-official-dupes.ts` names

Both readers call `authoritativeClaims()`, which returns `fec_candidate_id` plus

## 7. What contradicted the design

**S2(ii) would have re-created the defect for two of the three rows.** It routed
a loser whose office prefix matches the winner's into
`merged_fec_candidate_ids`. Harris (H4NC08066 / H6NC09200) and Menendez
(H2NJ08232 / H2NJ13075) are both H→H, so both would have gone there — and read
3, which the prompt itself commissioned to settle exactly this, shows that array
is filtered out of `authoritativeClaims()` and read by neither
`buildMatchIndex` pass 1 nor `loadOfficialsByFecIds`. Two of the three ids would
have entered Sunday's drop with zero authoritative holders and been re-minted as
though never restored.

The naming intuition is right about what the arrays *mean* and wrong about what
they *do when the other row is being deleted*. Retirement is safe in a merge
because the survivor keeps the id live; in a promotion nothing else holds it. So
the run took the prompt's stated principle — **"never drop it"** — over its
stated mechanism, filed all three as prior, and applied the same rule inside the
migration. `prior_fec_candidate_ids` is explicitly not role-gated, and these are
genuinely different seats (NC-08/NC-09, NJ-08/NJ-13), so nothing structural
objects.

**The restore script's own post-write check was wrong, and a correct restore
exited 2.** It counted a retired marker on *any* row as a holder, so it reported
"2 holders" for the three previously-live ids. Those markers are set 1's merge
stubs — `63740b8b`, `b7da3e46`, `ce2b114f`, each carrying only
`{"merged_fec_candidate_ids": [<id>]}` — which is the *correct* post-merge shape
and exactly what `authoritativeClaims()` filters out. A check that counts it as
a holder contradicts the rule the same script is built on. Fixed in `5f4b7948`:
the post-write check now uses an authoritative-claim census and reports retired
markers as context; the pre-write census keeps the strict all-surfaces form,
which is right *there*, since an id about to be restored must be unheld
everywhere.

**`financial_relationships` reads `vacuum_count = 0` and `last_vacuum` NULL, and
that is not a missing vacuum.** The postmaster restarted **2026-09-15 15:09:48
UTC**; `pg_stat_statements_info.stats_reset` carries that exact timestamp while
`pg_stat_database.stats_reset` reads NULL. `fr-vacuum-analyze` last ran 09-14
01:00 (200.7 s, succeeded) *before* the restart, and EC's `vacuum_count = 2`
(09-16, 09-17) and FE's `= 1` corroborate the epoch. Believing the counter would
have filed a false alarm against FIX-1191.

**Three smaller notes.**

- A SQL census written as `NOT (a ? x OR b = x)` returns **zero rows** when `b`
  is NULL — `NULL = 'X'` is NULL, `false OR NULL` is NULL, `NOT NULL` is NULL.
  The first authoritative census returned 0 holders for all six ids for exactly
  this reason. `COALESCE(b = x, false)` is load-bearing.
- The prompt's posture excludes a prod dry run because "DRY-RUN executes then
  ROLLBACKs". That is the *merge* script's shape. `restore-fec-ids`' dry run
  runs census SELECTs and prints a plan — no transaction held, no write — so one
  was run against prod before the apply. Flagging the distinction rather than
  assuming it.
- Exiting non-zero after COMMIT skips the interlock's "released" console line.
  The advisory lock still dropped with the connection (`prod_session_state()`
  read `held: false` with a stale label the next claim clears), so nothing was
  blocked — but the console gives no release line to read.
- The prompt names manifests `2026-09-19-*`; they were written on 2026-09-18 and
  are named for the day they were actually produced, matching every neighbouring
  file in `docs/audits/`.

**Nothing else contradicted cc-130's diagnosis.** Its §4 table, the 0/0/0
census, the clone's pre-promotion rows, Marshall's 4,867 FR rows, read 5's four
rows with their exact FR counts and survivor UUIDs — all read as predicted.
