## 4. What contradicted the design or this prompt

1. **Contract-flow DID carry a SET clause.** The prompt (B4) said "a PROCEDURE with COMMIT needs NO SET clause — it has none". Prod's `pg_proc.proconfig` is `{search_path=public, pg_temp}`, the same since `fix838`. A routine with any SET clause runs atomic and cannot COMMIT (FIX-1128), so the `running` row D1 asked for was impossible without removing it. I removed it rather than stopping the item. That is the prompt's own rule (109/fix1128), and the body names nothing unqualified: every relation and function is `public.`-qualified or pg_catalog, as in the two COMMITting siblings, which never carried one. The clone run proves the COMMIT works with no proconfig (`proconfig` empty after migrate; running row visible mid-run). If Craig wants the search_path pin back, the alternative is an in-body `SET search_path` statement. It is session-scoped, but a pg_cron run is its own session.
2. **The xact → session lock.** The prompt predicted this and the clone confirms it. A bare `DO` block on the clone takes `pg_try_advisory_xact_lock`, then reads `before COMMIT 1, after COMMIT 0`. The new body holds an advisory `ExclusiveLock` (session) mid-run, after the running row's COMMIT, and holds 0 after both the complete exit and the cancel exit.
3. **`prod_op_gate` does NOT call `box_is_saturated`.** It reads the walls itself (`c_wd_max_wall_s`). No caller anywhere in prod's pg_proc or cron.job, and the app only names it in comments. The 3-arg overload was dropped in the same migration, so a bare call is never ambiguous. The probe test's three-positional-arg call resolves to the 4-arg function, and its wall cases still read `watchdog_wall`.
4. **A `running` row does not change `enforce_cron_job_budgets`'s selection.** That function reads `cron.job_run_details` (`status='running'`, `job_pid`, a live `pg_stat_activity` row whose query matches the CALL target) and cancels with `pg_cancel_backend`. It never reads `data_sync_log`. The cancel being a *cancel*, not a terminate, is what lets the new `query_canceled` handlers fire. The clone's `pg_cancel_backend` run proves the handler path.
5. **What the clone's box read during its own rollup runs.** 08:12–08:27 UTC covered the old-body baseline and every new-body run. Both `*/2` watchdog walls peaked at **0.019 s / 0.022 s** (8 runs each, 0 over 1.0 s, 0 startup timeouts); the quiet hour before peaked at 0.046 / 0.079 s. So the wall rule would NOT have tripped on the clone. The clone is not prod's box: prod's walls reach 1.3 s under a bounded op (cc-151), which is exactly why D2 keeps the wall out of the gate. One probe run on the clone walled 3.9 s; that was my own `box_health` row hold during the stale seeds, not load.
6. **The ring's 24 h swap-in distribution.** p50 18.2, p95 506.4, max 1,584.7 pages/s, so p95 is ~28× the median.
