## 4. What contradicted the design

- **`prunable` on git 2.53.0 matches cc-190 exactly.** The full block is
  `worktree`/`HEAD`/`branch`/`prunable gitdir file points to non-existent
  location`. One detail the prompt did not state: `git worktree prune -n`
  writes its listing to **stderr**, not stdout. A log line that printed only
  stdout would have shown an empty dry run. Reading the git source,
  `worktree_prune_reason()` returns NULL for a locked tree, so `prunable`
  never appears on a locked entry. In this tree, then, `prunable` implies
  the bare prune will act on that entry. That is reasoned, not measured.
- **`fixes-integrity.yml` lists suites one by one and never calls
  `fixes:test`.** D3's primary premise ("`fixes:test` is what the workflow
  calls") was false. The fallback branch was taken (a new step), and the
  suite was also put into `fixes:test`. Side observation, not acted on:
  `test-trunk-guard.mjs` is in `fixes:test` but in no workflow either.
- **Read 2's own command tripped a bug** (FIX-1282). The prompt runs `pnpm
  session:worktree 9999` from inside the worktree, which is the normal place
  for a /cc run to be. `create()` anchors on `--show-toplevel`, so the tree
  nests one level deep and gets no `.env.local`. `done()` makes the same
  computation from the same place, which is why the rehearsal (run from the
  same worktree) still found it. From the primary checkout it would have
  looked in the wrong place. This is not destructive, and it is the only
  thing this run left behind (the empty nested dir).
- **The two claim cases under concurrency.** No refusal was seen in read 3
  or in D4. Both runs were alone on the clone. Before landing, the
  writers-live case ran in the default run and was not refused either. The
  FIX-1263 class did not show itself in this window, which proves nothing
  about it either way.
- **Open-count arithmetic.** 33 at `session:check` (04:06Z). This run:
  −2 (FIX-1276, FIX-1275) +1 (FIX-1282) = **32**, read at 04:15Z as `32 open
  of 1269 known ids`. The prompt expected 31 from this prompt alone, because
  it planned no filing; rule 106 added one. Concurrent sessions: at 04:16Z
  only `cc-200.running` exists (fix-1278, started 04:06:05Z), and there are no
  reports yet for cc-198, cc-199 or cc-200. Their stated deltas (198 −1, 200
  −1, 199 ±0) would put Tuesday's end at **30**, not the prompt's 29, again
