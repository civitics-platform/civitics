## 4. What contradicted the design

- **D1(b)'s "`newEntries` only" scope could never fire under the pre-push hook.** `newEntries` is computed after the off-trunk filter. Under `--check-trunk` the commit being pushed is by definition not yet an ancestor of `origin/main`, so it is dropped, and the planted-branch verification would have passed silently. As built, (b) reads the unlogged rows of two sets: `newEntries` (on trunk), plus the commits **HEAD carries ahead of `origin/main`** (`git rev-list origin/main..HEAD`, empty when trunk is not judgeable). Using HEAD and not `git log --all` keeps one session's stale unpushed branch from refusing another session's push. History stays out of scope, as the prompt wanted. The real push's hook table shows the 4 outgoing completions evaluated.
- **(b) does not catch the collision the prompt names as its fixture.** cc-184's `c2c968af` has the subject `fix(data): FIX-1265 — …` and the trailer `Fixes: FIX-1265`, which agree. What collided was the **bullet**. **(a)** is the guard that catches it: on rebase, cc-185's and cc-184's appended bullets both carry `<!--id:FIX-1265-->`. (b) catches the half-done re-allocation instead: marker re-numbered, trailer or subject not. FIX-1238 (cc-166) never reached a commit at all. The suggested `trailerSubjectMismatches(completions, bulletsById)` signature lost its second argument, because the check never consults the bullet. Subjects do not carry titles, as the prompt itself noted.
- **`Reopens:` included: yes.** No commit in history has ever carried a `Reopens:` trailer, so including it costs nothing. A reopen row's note is `reopened by <sha> <subject>`, so the bare subject now rides the completion object (`subject`, not a column).
- **Historical commits that would fail (b) if scoped wider.** A naive exact-tag match fails **66** of 428 tagged-subject commits; there are 1,018 commits with a trailer. Counting shorthand siblings (`FIX-1044/1045/1046`, `FIX-1014, 936, 963`, `FIX-826..829`, `FIX-036 through FIX-041`) brings that to **37**. Since 09-01 it is **7**; since 09-20 it is **1**: `999c2644 fix(fec): FIX-1106 — …` closed FIX-1074 without naming it. The remaining 37 are subjects that cite a *different* FIX for context ("FIX-983's own branch would have frozen…" closing FIX-1140). Going forward that is a refusal, and the remedy is to name the closed id in the subject. The cc-template subjects already do; 105 of 105 trailer commits since 09-20 have a tagged subject.
- **The prescribed teardown command used `$(…)`.** The prompt's `cd "$(dirname "$(git rev-parse --git-common-dir)")"` uses command substitution. Command substitution has historically forced a permission prompt here (memory: feedback_avoid_command_substitution), which would undo "needs no approval" in an unattended run. So `--done` prints the **absolute primary path** instead (`cfg.mainCheckoutRoot`), and Step 4 says `cd <primary checkout>`. `session:worktree:done` must run from the primary checkout anyway: its `repoRoot()` is `--show-toplevel`, so from inside a worktree it would resolve `civitics-worktrees/civitics-worktrees/fix-<id>`.
