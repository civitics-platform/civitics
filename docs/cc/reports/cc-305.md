## What contradicted the prompt

- **The tail table never printed the IE-totals step NOT SCHEDULED.** `printTailTable` already rendered it `gha / gate` through `GHA_OWNERS`. The NOT SCHEDULED came from the **heavy deferred-tail banner** (`printDeferredTail("heavy")`, merge :1667, plus the two `remediate-*` heavy sites). Its `TAIL_OWNERS` entry spelled the owner `"fec-bulk pipeline"`, which no set knew. That was read 0's first hypothesis, and it held. D5 was applied there.
- **"The registry is read first" is about which table decides, not the order of the statements.** The registry decides first, but the cron statement runs first and the registry query second. A failed statement inside a caller's open transaction aborts it, and D2 requires a registry failure to fall back to the cron read. Running cron first keeps that fallback possible. Every `printTailTable` caller reads before its manifest `BEGIN` (pinned by `remediation-manifest.test`), but the banners are also reached on resume paths.
- **The four MV/rollup owners were wrong too, not only the four vacuum owners.** On LOCAL they rendered `<parked cron> [INACTIVE]` (guarded `yes`) and now read `dispatched: by …`. `job_registry` is in `public`, so the clone's rows mirror prod's as of the last clone. `cron.job` is local history (FIX-946). So the after-table's registry half is likely prod-faithful, but that is the owed receipt's to confirm.
- **`pnpm build` was a turbo cache hit.** The changed files are not inputs to `app-civitics`'s build.
