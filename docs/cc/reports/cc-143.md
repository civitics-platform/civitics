## 3. Item 1 — the three predicates, the strand-proof, the guard, and the measurements

### The predicates, read twice

```sql
-- _delete: population UNCHANGED from today's, only the kept subset is new
DELETE FROM public.entity_tags t
WHERE t.entity_type = 'financial_entity'
  AND t.generated_by = 'rule'
  AND t.tag_category = 'internal'
  AND NOT EXISTS (SELECT 1 FROM pg_temp.pvt_desired d
                   WHERE d.entity_id = t.entity_id
                     AND t.tag = 'pre_vote_timing');
```

`t.tag = 'pre_vote_timing'` sits **inside** the `EXISTS` as a condition on the
*outer* row. It is not a join key. So for any row in this category whose tag is
something else, the subquery is empty for every `d`, `NOT EXISTS` is true, and
the row is **deleted** — which is precisely what today's unqualified
three-predicate `DELETE` does to it. The population is therefore identical and
no `tag =` filter was added to the outer clause; narrowing it would have been a
reader change (rule 87).

```sql
-- _insert: the anti-join keys on the UNIQUE columns, NOT on generated_by
WHERE NOT EXISTS (SELECT 1 FROM public.entity_tags t
                   WHERE t.entity_type='financial_entity' AND t.entity_id=d.entity_id
                     AND t.tag='pre_vote_timing' AND t.tag_category='internal')
ON CONFLICT (entity_type, entity_id, tag, tag_category) DO NOTHING
```

The omission of `generated_by` is deliberate and load-bearing: it is not in the
unique key, so including it would make the INSERT try to write over a `manual`
row and be silently swallowed by `ON CONFLICT` **every single night**.

### The strand-proof, against those predicates

Let `C` = the rows matching the three-predicate population, `D` = the entity_ids
in `pvt_desired`.

1. `_delete` keeps a row iff `t.tag='pre_vote_timing' AND t.entity_id ∈ D`.
   Call the survivors `C_keep`.
2. After that DELETE the unique key `(financial_entity, d, pre_vote_timing,
   internal)` is occupied exactly for `entities(C_keep)`, plus any non-`rule`
   row the DELETE does not own.
3. `_insert` therefore adds exactly `D ∖ entities(C_keep)`.
4. `Final = C_keep ∪ (D ∖ entities(C_keep)) = {(d,'pre_vote_timing') : d ∈ D}`. ∎

Nothing strands, and a second pass moves nothing because `C = desired` makes
both set differences empty. That last identity is **asserted by the suite**, not
just argued here — see `d2=0 i2=0` below.

### D2, corrected by the tree

The design's `DO UPDATE … WHERE IS DISTINCT FROM` is **moot on the daily**: the
payload is eleven constants and there is no `updated_at` to stamp (read 3). So
the single statement is `DO NOTHING` plus the anti-join. The weekly, where `tag`
crosses thresholds, is where the design's pair will matter — next prompt.

### The shrink guard

`_delete` counts the category and the desired set and `RAISE EXCEPTION`s when
`v_des < v_cur * 0.5`. This closes a wrong-but-green shape the rewrite genuinely
had: on an empty scan it deleted all 868k rows, inserted nothing, and reported
`complete`. The exception lands in the procedure's existing `WHEN OTHERS` →
`action='failed'`, the transaction rolls back, and the old state is intact.

### One thing the design did not claim, measured both directions

A data-writing statement gets **no parallel workers**, so today's fused
`INSERT … SELECT` is serial *by rule* — `EXPLAIN` shows **no Gather node at
all**, cost 2,812,079. `CREATE TABLE AS` is the documented exception, and the
TEMP CTAS keeps a parallel plan: 2 workers launched, cost 1,447,440, **4.64 s**
against 12.96 s for the identical SELECT forced serial. Splitting the scan out
of the INSERT was sold as measurability; it is **also a plan change**, and on
prod (more workers than this clone's two) that headroom is larger.

## 4. Item 2 — FIX-1208's liveness stamp (built; not on Pro)

`run_cron_watchdogs()` gains a `pipeline_state.cron_watchdog_vercel` row,
rewritten on **every** call. The argument is entirely about instrument kind:
`cron_job_budget_action.acted_via` is written only when the wrapper re-labels a
row, and it only re-labels on a cancel, so on a healthy day it is silent and its
silence is indistinguishable from the route never having run. It can prove the
path **acted**; it can never prove the path is **alive** — which is the sentence
FIX-1208 was filed on.

The row is a Vercel receipt **by construction**: pg_cron calls
`enforce_cron_job_budgets()` and `enforce_derived_mvs_unit_budget()` directly by
name in its own two `*/2` commands, and this wrapper's only caller is the route.
The call graph does the work; the instrument does not have to be trusted.

**One decision beyond the prompt, and I think it is the right one.** The stamp
sits in its **own EXCEPTION handler**. The function's existing discipline is
that each inner watchdog runs in its own handler so one failing never blinds the
other; an instrument has to obey that rule *more* strictly than what it
measures, because an unhandled error in the stamp would take down the cancel
path P2-A exists to keep alive. A watchdog that dies because its odometer jammed
is worse than no odometer. A failed stamp surfaces as `stamp_error` and the
watchdogs' results return regardless.

**Dead-tuple math, stated.** 720 updates/day on a 37-row table whose FIX-1003b
reloptions are threshold-led (`trigger = 20 + 0.05 × 37 = 21.85`), so ~33 extra
autovacuum cycles a day of milliseconds each. Prod baseline read 2026-09-22: 37
rows, 16 dead, 1,997 lifetime updates, 97 autovacuums against the 09-15 epoch —
about 307 updates and 15 autovacuums a day. So this roughly triples both, from a
very small base, in the cheapest shape available: one row, rewritten in place.

`at=<iso>` now prints in the route's verdict line (the payload has carried `at`
since FIX-1194), so the Vercel log itself carries the DB clock. A payload without
it prints `at=?` — a missing clock is exactly the reading that matters when the
stamp is also missing.

Receipts §9 gains one line from a new `forker_vercel_liveness` reader key, with
`missing` above 10 minutes (five missed `*/2` firings — the smallest window that
is not cron jitter or a redeploy), and an absent-key branch that says *why* it
might be absent so nobody has to guess between "migration not applied" and
"route not running".

**Local proof, taken through PostgREST rather than psql** because the route's
path is what is under test: two calls 11 s apart returned
`at` `03:45:31.963347` and `03:45:42.444542`, **no `stamp_error` either time**,
and `pipeline_state` held exactly **one** row whose `at` and `updated_at`
advanced together.

## 7. What contradicted the design, the bullets, or this prompt

**The prompt's four stated corrections all held.** The category is `'internal'`;
`entity_tags` has no `updated_at` and no trigger; D2's `DO UPDATE … WHERE IS
DISTINCT FROM` is moot on the daily for exactly the stated reason; and the
desired set is the same order as the current category (720,256 on the clone,
868,167 on prod). Nothing in reads 2–4 forced a fifth.

Six things the design, the bullets or the prompt did not have right:

**1. The split buys parallelism, and nobody claimed it.** A data-writing
statement gets no parallel workers, so the fused `INSERT … SELECT` was serial
*by rule* — its plan has no Gather node at all. `CREATE TABLE AS` is the
documented exception, so the TEMP CTAS runs 2 workers at 4.64 s where the same
SELECT forced serial takes 12.96 s. The design justified the split as
measurability and cc-138 as an instrument; it is also a plan change, and it is
the part of the win that will *grow* on prod, which has more workers than this
clone's two. Worth remembering as a general lever: **moving a scan out of a
writing statement can change its plan class, not just its bookkeeping.**

**2. D5 failed the test nobody wrote.** The prompt built a careful cost gate and
told me to measure before building — good instinct, wrong axis. The cost came
out genuinely ambiguous (2.28 s warm passes the stated `< 12 s`; 17.6 % fails
the stated 10 % ratio; 2.7 % by buffers passes comfortably), and I could have
justified either answer. What is not ambiguous is that the signature would have
been **unequal on all ten of the last ten prod days**, so the gate would never
once have fired. A gate's hit rate is prior to its cost: a free gate that never
fires is still worthless. The weekly sibling's gate *does* fire, which is
presumably why the shape looked transferable — but its signature is over a
different FR predicate.

**3. The GUC question was not close, and the prompt treated it as open.** Design
§4 deferred it and read 5 asked me to file a follow-up if the default plan had
become the faster one. It is 17.6× slower, and the mechanism is structural
rather than statistical — a `BETWEEN` cannot be a hash key, so the date-range
predicate collapses into a Join Filter that discards 586 million rows. This will
not flip with data growth. I filed nothing, and I would treat the question as
settled rather than deferred.

**4. The prompt's R1 gate was unsatisfiable at the time it was written to run.**
The prompt was revised at ~09-22 03:30 UTC and its read 10 says to STOP if the
epoch is younger than 7 days, while its header says the cycle completes at
09-22 15:09:48 UTC. Those cannot both be met by a session starting at 03:00 UTC.
Read literally, read 10's STOP fires and the prompt's own fallback ("ship the
merge without the drop; remove the `DROP INDEX` line") applies — but that
fallback costs an edit to a migration that is already applied, and it discards a
rider whose gate opens the same day. The prompt would have been clearer as
"item 3 runs no earlier than 15:09:48 UTC" than as a STOP condition, because the
condition is a clock, not a discovery. I surfaced the fork rather than resolving
it by reading.

**5. `migrations_pushed` has no way to say "on trunk, not on Pro".** The field
is documented as naming FILES with the Pro side reported `UNCHECKED`, and the
verifier PASSes an empty list with "no schema change claimed". Neither option is
accurate for this run: listing them reads as pushed, and omitting them erases a
real schema change. I listed them and put the Pro status in `stopped_items` so
both facts travel in the same sidecar — but a consumer reading only
`migrations_pushed` will be misled, and the field probably wants a sibling
(`migrations_on_trunk`, or a tri-state) rather than a convention.

**6. `_scan` needed an explicit `DROP TABLE IF EXISTS`, which the design's
`ON COMMIT DROP` implies is unnecessary.** `ON COMMIT DROP` does nothing *within*
a transaction, so the second-pass test — which is the strand-proof, and therefore
the test most worth having — would have failed on `relation "pvt_desired" already
exists`. Small, but it is the kind of thing that turns a designed test into a
skipped one. Relatedly, and not a design issue: `import.meta.dirname` is
`undefined` under tsx's CJS transform, so source-anchor suites in this repo must
use `__dirname`.

**One thing I deliberately did not do.** The `snapshot/route.ts:100` comment
still names `idx_entity_tags_visibility` while explaining the pre-FIX-503
behaviour. It is prose inside a historical note, not a code path, so read 10's
"no code path names the index" condition is met; I left it rather than adding
churn to a file this change has no other business in. It will read as slightly
stale once R1 lands.
