## What contradicted the prompt

1. **The flip edit can land on the wrong variable, and the design had no check between
   the edit and the redeploy.** `ORIGIN_AUTH_MODE` and `ORIGIN_AUTH_SECRET` are both
   `sensitive` type, so the dashboard shows neither value. Craig's 00:58:51Z edit changed
   the secret. My `58f3f696` push re-read it.
   - **What happened:** the IP door still answered `200 miss`, so the mode was still
     report. Per-key `updatedAt` from `GET /v9/projects/{id}/env` (metadata only) showed
     which key had moved. The log showed `miss … cf-ray=yes` from a real visitor at
     01:03:03Z.
   - **The mismatch window:** 01:02:54Z → 02:12:40Z, across five deploys: mine
     (`58f3f696`) and four from the concurrent cc-220 session's pushes (`fe27f936`,
     `e0c5ea1c`, `88a70b8a`, `254d5080`). Every one of them baked in the wrong secret. That gave 13 sampled
     `cf-ray=yes` lines, all served 200.
   - **Recovery:** Craig restored the secret from the Cloudflare rule at 02:08:20Z. Its
     metadata then also showed a MODE re-save at 02:09:30Z, so I asked rather than
     assumed: the answer was "report". The `fcbebefa` deploy (READY 02:12:40Z) then
     served ~50 Cloudflare-forwarded www requests from 02:15:21Z with zero miss lines,
     including the 02:20:10Z platform-snapshot run. An IP-door control probe logged that
     deployment's first miss, `cf-ray=no`, at 02:22:14.793Z, proving the check was live
     there. Only then did MODE go to enforce (02:23:30Z). The metadata confirmed the
     secret's `updatedAt` had not moved.
2. **§9 line 3 is not a fast check for "the site 403s itself" while Under Attack is
   on.** D2 names it the fast check. But a scripted request to civitics.com is
   challenged by Cloudflare and never reaches the origin. So line 3 reads `403
   Cf-Mitigated: challenge` whether the origin serves or refuses. Had both variables
   been wrong in one deploy (a mismatched secret under `enforce`), line 3 would have
   passed while every real visitor got the origin's 403. The checks that do see it are:
   - `vercel logs --query origin-auth` for `refused … cf-ray=yes` lines (instance-first
     sampling surfaces them within seconds);
   - `vercel logs requests` for www 403s to non-probe UAs;
   - platform-snapshot, which passes Under Attack through `Probe skip (FIX-1057)`, but
     only every 10 minutes.
   I used the first two here. `docs/CLOUDFLARE.md` Rotation now carries the procedure.
3. **There are three origin host classes, not two doors.** Vercel cron calls the
   per-deployment URLs (`civitics-civitics-<hash>-civitics-platforms-projects.vercel.app`):
   1,745 requests in 24 h, all `vercel-cron` → `/api/cron/*`, all exempt. A non-cron
   request on one now meets the check (`cf-ray=no` → 403 under enforce). None occurred
   in the 24 h.
4. **Matcher-excluded static paths never reach middleware.** That covers `favicon.ico`,
   `_next/static`, `_next/image` and the image extensions. They stay served on the IP
   door, and on the alias without a 308. One alias `/favicon.ico` 404 was seen. They are
   static and cheap, so they are left out of scope here.
5. **The log read did not need the dashboard.** CLI 64's `vercel logs` takes
   `--since/--until/--query` and a `requests` source. It authenticates with the stored
   `VERCEL_API_TOKEN` and `--scope <team>`. `--next` exits 2 under Git Bash/cmd; time
   slices work around it.
