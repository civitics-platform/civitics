## The Lead

**What the canary watches now.** These are the seven registry rows whose
`unit_call` is `gha-dispatch:<stem>`. Each stem's limit comes from its rule:

| stem | rule | judged by |
|---|---|---|
| nightly | `by 0 21 * * *` | stamp age, limit **25 h** (daily) |
| sync-canary-check | `at 0 5 * * *` | stamp age, limit **25 h** (daily) |
| platform-snapshot | `at */10 * * * *` | stamp age, limit **0.5 h** (three periods) |
| irs990 | `at 0 15 * * 2` | stamp age, limit **169 h** (weekly) |
| audit | `at 0 17 * * 2` | stamp age, limit **169 h** (weekly) |
| crs-summaries | `stale_after 2 hours` | **its request**: the key reaped `missed`; or unconsumed 25 min after `requested_at`; or a dispatch_log `missed` row in the last 24 h newer than its stamp. The stamp's age is carried, not judged |
| bill-details | `stale_after 2 hours` | **its request**, as above. No key means never armed, which is not stale. Absent from the registry (prod before cc-330), it is not listed |

The five slot limits are derived from each cron. They reproduce the old hand
list exactly, and a test pins that against `FALLBACK_DISPATCH_STALE_HOURS`.
Any other rule, or a cron outside the three shapes, reads
`unjudged (<rule>)` in the detail and counts in neither condition. If the
registry read fails or comes back empty, the canary judges on the old
six-stem hand list (crs-summaries at its old 169 h). The stale detail then
begins `registry unread — judged on the fallback list`, and the new
`metadata.gha_dispatch_source` reads `fallback`.

**Read 4 — the request key.** The newest file that defines `dispatch_one_unit`
is `20261126004000`. Its ARM (step 7) writes `{job, requested_at,
dispatch_log_id: null, consumed_at: null, outcome: null, http_status: null,
reaped_at: null}` with `ON CONFLICT DO UPDATE SET value = EXCLUDED.value`. A
re-arm therefore **replaces** the key, and `reaped_at` and `reap` go with it.
`consume_gha_dispatch_request` merges `consumed_at, outcome, http_status`. Step
3b merges `reaped_at` and `reap: "<decision>: <why>"`. A miss reads
`missed: no dispatch by <req_at + 20 min> — the request route did not fire
(N2); idempotent_refire …; the row stays due inside its window`, and fires at
`c_gha_fire_lapse` = 20 min with no route answer. The clone has no
`gha_dispatch*` key (0 rows), so the shape above is quoted from the body.

The clone's own dispatch_log shows the problem. The nightly's `missed` ticked
at 00:57:36.132 and its re-arm at 00:57:36.149, in the same call, because
`missed` never counts toward the cooldown (FIX-1316 I6). So while a walker
stays due, the key at a daily read always shows a fresh request under 20 min
old. That is the STOP row's case: "unconsumed for 25 min" and "reaped missed"
can only be seen when something blocks the re-arm or stops 3b. Hence the third
condition, built on the prompt's named fallback read. The canary reads
`dispatch_log` (service_role SELECT, `ticked_at` index) with `decision =
'missed'`, `armed_jobname IN (the walkers' request keys)` and `ticked_at` in
the last 24 h. A miss with no stamp after it means the route has not answered
since.

**Read 5 — the stamp.** A `gate: "request"` poll that finds no request (or a
consumed, reaped or over-2-hour one) returns `no_request` / `stale_request`
**before** `recordDispatch`. So the stamp is written only on a call that
reached GitHub, whatever GitHub answered. A refusal stamps `status: refused`
and consumes the request with `outcome: refused`. 3b then reaps it `failed:
dispatch refused <http>`, not `missed`. So D4 works unchanged for the walkers,
and a test pins that.

  `stamps.length 6`.
- **D6's hint.** On the registry path the hint now names each stale stem's
  path (`/api/cron/gha-dispatch/nightly-request`, `…/irs990`, …) instead of
  the literal `/<stem>`. The nightly's real path has been `nightly-request`
  since FIX-1350, so the old literal sent a reader to a 400. The fallback
  keeps the literal. The refused text still says "the schedule: fallback is

## The next prompt — FIX-1317

**Not with this read as it stands.** FIX-1317's drift is the
`rollup_watch_overrides.cadence_hours` mirror of the registry rule, which keeps
a returned job `has_override` rather than `orphan`. The orphan verdict is
computed inside `list_scheduled_rollup_pipelines()`
(`20260920160000:161`: driver pg_cron AND NOT has_active_job AND NOT
has_override), and `canary-check.ts:424` only consumes it. A TypeScript
registry read could size a cadence, but it could not clear the RPC's orphan
flag without the canary second-guessing the RPC.

Two pieces would carry over to a SQL-side change. First, one PostgREST
`job_registry` select keyed on `pipeline` rather than `unit_call`. Second,
`slotLimitHours` for `at` / `by` rules. That SQL-side change is a LEFT JOIN of
`job_registry ON pipeline` in `list_scheduled_rollup_pipelines()`, with
`stale_after N hours` → N and a `by` / `at` cron → its period, and
`has_override` true for a registry-backed job. `stale_after`'s duration is not
parsed here (this run reads only its class), so FIX-1317 needs that parser in
SQL. That makes a dial move one write and leaves the canary unchanged.
