## 7. What contradicted the design

1. **The projection named the wrong step.** cc-128 said to watch `FR move` past
   ~45 min because it was 96.3 s of the clone's 155 s. It ran **265.8 s**. The
   cost was `_collision` — **~97 of set 1's 115 transaction minutes** — which is
   untimed on the clone because the whole run there is 2m35s. It drives the join
   from `_manifest` → **survivor** rows, and the survivor side is the large one;
   the read-only equivalent driving from the **stub** side (99,217 rows) returns
   the identical census in minutes. `ANALYZE _manifest` fixes the cardinality
   estimate, not which side is materialised. Filed as **FIX-1192**.

2. **cc-128 was right to refuse a single prod/clone multiplier.** Set 1's merge
   transaction ran ~44× the clone's whole-run wall; its write steps ~3×; set 2's
   `FR move` ~110× under contention.

3. **The clone's colliding/non-colliding split had drifted.** The manifest says
   98,878 + 339; on prod **all 99,217 collide** (the 339 are 2020 IE rows the
   survivor since acquired). Every row count moved — 40,649 rather than 44,872
   — and **the money did not change by a cent**, because the 339 are IE.

4. **The front-door cost lives in the tail, not the transaction.** 3
   cancellations across 120 minutes of merging; ~15 across 94 minutes of rollups.

5. **"Manifest-scoped" is a class, not a magnitude.** 151 manifest rows implied
   **302 affected officials and 430,411 affected donors**, and 94 minutes of
   rollups. The FIX-1183 cost table prints the class and no scale, so a reviewer
   reading "manifest-scoped, 151 rows" cannot anticipate that.

6. **A deferred tail relocates its cost into a window the interlock cannot
   guard** — and that is what stopped set 2. Filed as **FIX-1193**, together with
   the second half: the firings a set defers resume on release and refuse the
   next set's claim, so **two sets cannot run back-to-back**.

7. **`--defer-tails` leaves `financial_relationships` with multi-day visibility
   decay.** Post-apply: **204,091 dead tuples, 82.7% all-visible**. Its owner,
   `fr-vacuum-analyze`, is **weekly (Mon 01:00)**, and autovacuum cannot help —
   the per-table scale factor 0.02 puts the trigger at **289,448** dead tuples.
   So a bulk FR rewrite on any day but Sunday leaves the table degraded for up to
   six days with nothing able to collect it: the FIX-884 shape that FIX-943's
   standing rule exists to prevent, routed around by construction. EC and FE have
   *daily* owners and recovered. Filed as **FIX-1191**.

8. **The prompt's manifest path does not resolve.** `pnpm --filter` runs with cwd
   `packages/data` and `readManifest` is a plain `fs.readFileSync`, so
   `docs/audits/…` points at `packages/data/docs/audits/…` — which holds only the
   FIX-1106 residue TSVs. `../../docs/audits/…` is the form that works, confirmed
   by local dry run before any prod contact.

9. **The interlock takes no per-set label**, so the prompt's `fix1187-set1` /
   `fix1187-set2` naming is not available in the code as written.

10. **The prompt quoted clone figures as prod** for the five survivors' totals.

### On cancelling set 2

The prompt says not to cancel a running merge from outside, and I did. It was
taken with Craig, on his call, after he flagged the error rate — on three
grounds: the front door was at **51.7%**; the **05:45 UTC blackout** was 23
minutes away and set 2 could not have finished inside it; and a cancel of an
**uncommitted** transaction is atomic, so the only thing lost is elapsed time.
The alternative reading — let it commit or fail whole — would have carried a
degraded front door across the blackout boundary with no bound on when it ended.
I think the departure was right, but it is a departure and it is recorded as one.
