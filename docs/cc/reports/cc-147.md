## 9. What contradicted the design, cc-146, or this prompt

- **The stop rule, as I built it, tripped on one watchdog run read twice.** The
  09:06:49 tick and the pre-CALL-2 reading 16 s later both read the 09:06 run.
  The prompt's "two consecutive readings" assumes one reading per run, since
  both cadences are 120 s; a pre-CALL read breaks that. Fixed in 3a8eff87.
  **The walls were real, though:** the op itself drives the watchdog from
  0.014 s to 1.341 s within two windows. That puts the prompt's 1.0 s
  threshold, taken from the Tuesday pre-failure signature of 1–4 s, inside
  this op's own load. Whether that is a stop is a design question, not a bug.
- **Window walls are about 20× the clone's warm figures.** cc-146 rightly
  projected buffer reads (~8× one whole-table pass) and NOT a wall; its warm
  1.5–7.5 s per window would have understated prod ~20×. The clone's COLD
  108.9 s was the honest proxy (the "clone lies both ways" memory, again).
- **FIX-1212's 7-day `c_cycle_max_age` is shorter than two weekly firings.**
  At ~130 s a window, a cycle needs more than one Tuesday, so a weekly cadence
  treadmills. Appended to FIX-1212; it is a design point for whoever next
  touches the procedure. The procedure is out of scope here.
- **Rule 66 under the session pooler.** "Verify by the backend's absence" read
  STILL PRESENT: Supavisor keeps the server backend (pid 53253, idle, last
  query `DISCARD ALL`). The check now asks whether the CALL is still running.
  `DISCARD ALL` also means the claimant GUC cannot leak to the next pooled
  client, a risk the prompt did not raise.
- **The header's timing prediction was wrong in the harmless direction.**
  "ec-vacuum avg 482 s ends ~04:38 → +90 min" did not happen: today's ec run
  was 9.4 s, so only the 10-minute rule applied. The gate still opened at 09:00
  on the blackout, as predicted. The prompt's own fixture expectation ("the
  ec-vacuum 04:30 run") read `fe-vacuum-analyze` instead.
- **pnpm exit codes.** `pnpm -s <key>` collapses non-zero exits to 1;
  `pnpm --filter` and plain `pnpm` pass them through (the prod run returned 4).
  The prompt's `-- --flag` form forwards a literal `--`, which
  `cancellation-census.ts` rejects ("unknown flag --") and the runner used to.
- **`claimProdSession` held 16 guarded pipelines, while `prod_op_gate`'s
  derivation (and `Q_GUARDED_PIPELINES`) counts 17.** Noted, not chased.
- **Known mislabel, out of scope:** the procedure stamps `source: 'pg_cron'` on
  the runner's supervised CALL row (`0e7c8e74`).
