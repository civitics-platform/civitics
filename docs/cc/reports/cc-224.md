## 2. The function as built

**`dispatch_one_unit(p_source)`** — VOLATILE, SECURITY DEFINER, owner
postgres, `SET search_path public, pg_catalog, cron`. EXECUTE is revoked from
PUBLIC/anon/authenticated and granted to service_role. Its steps, each ending
on one `dispatch_log` row:

1. `pg_try_advisory_xact_lock` → `lock_busy`.
2. The dials → `no_dials`, or `paused`.
   - 2b. Retention, 01:45–01:59 UTC: rows older than 14 days.
3. **Reap.** Only when an un-reaped `armed` row exists, one `DISTINCT ON
   (jobid)` read of `job_run_details` for all of them:
   - terminal run → unschedule, drop the budget row, `reaped` with `unit_ms`;
   - non-terminal run → the unit is an occupant;
   - no run row and the job row gone → `reaped`, "job row gone";
   - no run row past `armed_for + 3 × tick` → unschedule, drop the budget
     row, `missed`.
4. Box → `skipped`.
5. The census (below).
6. Pick (below).
7. ARM → `armed`.

Any error in steps 2–7 rolls them back and logs `error` with its SQLSTATE.

**The census's four sources:**

- un-reaped armed one-shots;
- `data_sync_log` running rows younger than 6 h, by pipeline;
- `pg_stat_activity` backends running `CALL|SELECT [public.]<routine>(` for
  registry rows **that have an exclusion_group**;
- `pg_stat_progress_vacuum`, autovacuum included.

Each observation resolves to one representative registry job: an armed job
first, then an active cron job, then the larger cap. `live_units` and caps
count distinct representatives, so one physical unit seen three ways is one
unit. An autovacuum on a table no row names adds 64 MB of caps and no unit.

**Deadline arithmetic:**

- **`stale_after <iv>`** — last complete + iv − now.
  - With a pipeline: max `completed_at` of its complete or partial
    `data_sync_log` rows.
  - Without one: the later of its own cron name's last succeeded run and its
    newest `reaped succeeded…` row.
  - Never completed → −1 s (due now).
- **`by <M H * * *>`** — due iff nothing completed since the most recent slot
  ≤ now; otherwise next slot − now (see §5).
- **`dead_tuples > p% of trigger [+ floor iv]`** — the trigger comes from
  reloptions, falling back to the GUCs. Due when `n_dead_tup ≥ trigger × p`,
  or when the floor has elapsed since the last vacuum.
- **Anything else** → `unsupported_deadline`.
- **Due means ttd ≤ 0.** A positive ttd is reported as `next: <job> in <iv>`.

**The trigger's two flips:** `tick_seconds 240` → `1-59/4 * * * *`, then
`120` → `1-59/2 * * * *`. Each raised a NOTICE naming jobid 377.

## 5. What contradicted the prompt, the spec or the design

**Confirmed as the prompt expected:**

- `cron.schedule` from the SECURITY DEFINER body **recorded `postgres`** as
  the one-shot's owner (read back on jobs 378, 379 and 380; 383 and 384 were armed by the same path).
- `PERFORM` was accepted in the procedure.
- `box_is_saturated()`'s `stale` branch did **not** fire. The probe was
  active on the clone, so no override was passed.

**Contradictions and departures:**

1. **The hard stop is `pause`, not the unschedule.** The prompt's nets name
   `cron.unschedule('dispatcher-tick')` as the hard stop. With the route's
   re-fire, an unscheduled dispatcher whose newest row is > 360 s old gets
   `dispatch_one_unit('vercel')` from Vercel. That writes a fresh row, so it
   arms a unit every ~6–8 min indefinitely. Both paths read `pause` first.
   - The header's NETS and the ROLLBACK now say: pause, then unschedule.
   - The s6 proving's "park the tick 10 min Sat" exercise is exactly this
     path. Keep `pause = false` for it; it is how the re-fire gets seen.
   - After a full ROLLBACK (functions dropped), the route's re-fire gets
     PGRST202 every 2 min. That logs at info until the route is reverted
     too.
2. **`cron.job_run_details` has no usable index.** Only the PK (`runid`).
   There is no `start_time` index either, so the prompt's "filter also on
   `start_time > now() − 1 day`" would not bound the scan. The table is
   owned by `supabase_admin`, so `postgres` cannot add one.
   - Every read is guarded to run only while a one-shot is armed, or when a
     pipeline-less row has a `stale_after`/`by` deadline. Idle ticks (71
     buffers) never touch it.
   - On the clone it is 8.4 MB / 35.6k rows, about 1,050 pages per scan, and
     an armed tick does one or two scans (2,268 hits). Prod retains 42 days
     with the every-minute probe, so expect it several times larger.
   - **For M1:** record a `runid` floor at ARM time (a `dispatch_log`
     column; R2 adds no DDL to R1's tables) and read by `runid > floor`
     through the PK. Not built.
3. **`by <cron>` as written is never due.** `cron_next_daily(<cron>, now) −
   now` is ≥ 0 by construction (it returns the slot at or after now), so a
   `by` row could never reach ttd ≤ 0.
   - **Built instead:** due iff nothing completed since the most recent slot
     ≤ now. Otherwise ttd = next slot − now.
   - Rehearsed with `vote-stats-refresh` `by 30 3 * * *`: completed
     03:30:01Z, so it reported `next` (not due).
   - No daily-form `by` was refused. A non-daily `by` →
     `unsupported_deadline`.
4. **The census excludes rows with no exclusion_group from the
   `pg_stat_activity` source.** Those are the probes and watchdogs, e.g.
   `SELECT public.record_box_health()` every minute. Counting them would
   make `live_units`/`live_caps` flicker with whichever second a tick lands.
   The prompt said "any registry routine".
5. **Shared pipelines and routines collapse to one unit.** Examples: ec
   rebuild ×3, `refresh_derived_mvs` ×2, `financial_entity_totals_refresh`
   ×2. One unit, through a representative; every job sharing it is still
   "live".
6. **Exclusion vocabulary.**
   - Gated, caps-, units- and group-blocked due rows log `nothing_due`, naming
     the would-be top row's reason, e.g. `gated: prod_session (job)`.
   - `skipped` is the box only.
   - The reason names only the top row. Showing caps on a lower-priority row
     needed the higher one not due, which is how #20 was taken.
7. **No backoff for a failing or always-due unit.**
   - A unit that fails, or whose own guard writes `skipped`, stays due and
     re-arms every ~4 min (#26 shows the loop for a too-short interval).
   - Not built. It is a row-author / M1 question (FIX-1137's
     `idempotent_refire` covers only `missed`).
8. **Future vacuum-migration guards trip on armed vacuum one-shots.** The
   fix1239-family guards loop `jobname ILIKE '%vacuum%'` and RAISE on a
   schedule they cannot parse ("cannot check spacing against …"). A
   `disp-*-vacuum-analyze-*` one-shot live at the moment such a migration
   applies would fail it, and `prod_op_gate` reads one as `unparsed`.
   - Today: zero eligible rows, so no `disp-*` exists.
   - **Proposal:** the next guard filters `jobname !~ '^disp-'`.
9. **The route's dispatcher reads race 2 s, not `RPC_TIMEOUT_MS`.** 10 s + 5
   s + 10 s + 2 × 10 s would exceed `maxDuration 30`; 2 s each gives 29 s.
   An abandoned re-fire still completes server-side.
10. **The receipts JSON key is `unit_dispatcher`, not `dispatcher`.**
    `nightly.dispatcher` is already the GHA nightly dispatcher's stamp
    (FIX-1218).
11. **Files beyond the prompt's list:**
    - `app/api/claude/status/core/route.ts` and
      `app/dashboard/useDashboardData.ts`. The client's mount fetch REPLACES
      the SSR status with `/core` + `/quality`, so a key wired only in
      `page.tsx` draws once and vanishes. That is the `ec_crawl_health`
      trap, now pinned by `dispatcher-tile.test.ts`.
    - Nothing enumerated `StatusPayload` keys before, so that test is new.
12. **Smaller choices:**
    - `ticks_60m` counts pg_cron-source final rows only.
    - `expected_ticks_60m` is `floor(58 / N) + 1` from the schedule (30 at
      N = 2, equal to 3600/120). `3600 / tick_seconds` drifts for a
      `tick_seconds` that is not a multiple of 60.
    - The tick job's schedule is derived from `platform_dials.tick_seconds`
      in the fix1239 block, so a re-apply never undoes a dial move.
