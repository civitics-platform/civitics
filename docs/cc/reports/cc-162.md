## 4. What contradicted the design note or this prompt

1. **The pre-CALL gate pre-empts the two-CALL budget.** The pre-CALL reading is the trailing 15 min, and that window holds the CALL that just finished (≈ 4 min) plus the breather, about 2.5 CALLs in all. At the default budget of 3 and a 15-min floor of 3:
   - **One CALL can end the run.** A CALL with 4 renders is over budget (a `would_trip`, one observation), but the next pre-CALL reading also sees ≥ 4 renders > 3 at a ratio above 8. That reading FAILs and stops the run after ONE observation. Rule 117's two-CALL requirement never gets its second look.
   - **The window adds up across CALLs.** Two CALLs of 2 renders each are under budget, yet the pre-CALL window can hold 4 and stop.
   - **Net effect:** the pre-CALL gate is a de-facto **cumulative budget of 3 renders per 15 min**, stricter than the per-CALL budget.
   - **Built as written** (D3 (iii): "pre-CALL unchanged"). cc-151's pre-CALL 6 held exactly 3 and passed by a hair.
   - **The obvious fix** is to exclude CALL spans from the pre-CALL verdict, so it judges only the time outside the paced op (cc-151's pre-CALL 6 would read 0), or to make the pre-CALL floor and the budget one number. That is Craig's call.
2. **`breather_timeout` was never a stop.** The design's D3 table ("on timeout → breather_timeout stop as today") and the prompt ("stays a stop") are both wrong about the tree: cc-148 D2 made the timeout proceed. I kept that behaviour. The census half is therefore advisory at timeout: a breather still losing renders proceeds after `--breather-max-s` and records the pending renders. The CALL budget and the next pre-CALL gate still guard. Making the timeout a stop (when the census held it) is one line, but it is a decision.
3. **D1's predicate had two readings.** "`parsed.sql_state_code = '57014'` (the same population predicate as `sqlCancellationBuckets` — copy it)" names two different predicates: the bucket builder's population is `event_message LIKE '%…statement timeout%'`. `sql_state_code = '57014'` also matches hand cancels ("due to user request" is 57014 too), so it would break rule 116's equality on any window with one. I used the bucket builder's string, now one shared constant. The fixtures agree on both only because `n_user` = 0 everywhere.
4. **`toStartOfSecond` groups the fan-out cleanly** on cc-151's burst: six events from .262 to .790, 528 ms inside one second. A render starting after ~.47 s into a second could straddle two. None did in the three windows.
5. **`anyHeavy(parsed.query)` does not name a page.** It returns the raw ~600-character PostgREST envelope; the first 60 characters are the same `WITH pgrst_source AS (SELECT pgrst_call…` for every RPC. The builder instead uses the attribution builder's `"public"."<name>"` extraction inside `anyHeavy`. A JS `sampleQueryName` reads either shape, so the raw Phase-0 fixtures resolve to the same names.
6. **A second is not a page.** cc-154's pre-claim hour has 1 by-second render: 00:30:44, a HEAD count on `enrichment_queue`, which cc-155 D4 counted as 0 page renders. The design accepts this trade, and the sample makes it visible.
7. **The census no longer reads hand cancels.** Keeping the bucket read would make a gate reading 3 Logs calls on a token four readers share. `user_requests` is now `null` in the JSON and stated in the text; `--by sql_state_code` still sees them.
8. **Logs ingestion lag is unmeasured.** The breather reads at wall-release, 30–120 s after the CALL. A render stamped in the CALL's last seconds could reach the Logs API after that read. The end-of-run re-count (`renders_final`) records any drift per breather, so the first paced op under this rule measures it.
9. **The report-mode meaning changed.** Under cc-152, `report` also demoted a failing pre-CALL reading. The prompt ("the mode's meaning narrows to the CALL-window budget") and design §0.4 ("for the CALL-window reading only") both say it no longer does, so a pre-CALL FAIL now stops in both modes. That is a behaviour change for anyone who launches in report mode to measure.
10. **The binomial pin is wrong.** The design note and prompt both give binomP99(183, 0.002) = **3**. The exact CDF gives **2**. The verdict on 2/183 is unchanged (pass).
11. **Gate (f) is written as the code has it.** The prompt's text ("≤ the Poisson-P99 floor … AND ratio ≤ 2") as a PASS condition would be stricter than D2 (fail only when BOTH are exceeded). I wrote the code's rule.
12. **`docs/ops/prod-holds.md` had no runner section.** One was added under §1, beside FIX-1213's "Running a guarded procedure UNDER the claim".
13. **The watch's no-floor question: no.** `front-door-watch`'s red rule is `n_52x ≥ 3 AND n_52x/requests ≥ 0.5`: a count floor and a ratio, on 52x only. Its 5xx-ratio arm was designed in and removed. It does not share the census's no-floor 1 % shape, so no `front_door_watch` rows were read and nothing was filed. Its header also records healthy-bucket n_5xx p99 = 28 with 544/550 buckets at n_52x = 0, which is input for FIX-1233's p0 definition.

   - The first scratch Logs reader was a `.ts` file in a CJS package; `.mts` and a default import fixed it. It failed before any request, and I caught the clock at 21:15:37, inside the watch's minute.
