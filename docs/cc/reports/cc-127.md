## 5. Read 6 — `transaction_timeout`, and the answer for FIX-1186

`statement_timeout` restored to `6h` first, so the only variable is
`transaction_timeout` as a role default.

**2 s units under a 3 s bound** (jobid 79) — all five ran:
`unit 1 ok … unit 5 ok`, `terminal canceled=f units_done=5`, whole CALL
**10.039 s**, pg_cron `succeeded`.

**4 s units under the same 3 s bound** (jobid 80) — only the start row:

```
 18 | 00:46:00.036 | start statement_timeout=6h transaction_timeout=3s pid=1995
 (1 row)

 2026-09-15 00:46:00.034778+00 | 2026-09-15 00:46:03.047321+00 | 3.013 | failed
   | server closed the connection unexpectedly …
```

**The one-line answer for FIX-1186:** a role-level `transaction_timeout` on
PG 17.6 **re-arms per unit** (5 × 2 s units all completed under a 3 s bound,
CALL 10.039 s, pg_cron `succeeded`), so a per-unit in-backend bound needs no
extra backend — **but a unit that exceeds it TERMINATES the backend rather than
cancelling it**: no unit row, no terminal row, the `query_canceled` handler
never runs, and `cron.job_run_details` reads `failed` / "server closed the
connection unexpectedly" instead of a timeout message, so FIX-1109's
`succeeded` + `'partial'` signal is lost and a reaper would have to write the
terminal row.

Teardown verified: `RESET transaction_timeout`, both probe jobs unscheduled,
procedure and log table dropped, 0 probe objects remaining, role row back to
`{statement_timeout=6h,work_mem=256MB}`.

## 10. What contradicted the design

**`succeeded` is not `healthy`, and the census was built as if it were.** This
is the root of it. A C1 procedure catches `query_canceled`, records, and
returns, so pg_cron logs `succeeded` for a cancelled run — 21,932.5 s of
`succeeded` sits in the table. Sorting on `cron.job_run_details.status` mis-sorts
every C1 procedure in both directions, and that is how "every run anyone would
call healthy is ≤ 7,125.6 s" came to be written while five clean completions
between 3.13 h and 5.16 h sat in the same table.

**A 3 h ceiling would not be a backstop under the watchdog. For two active jobs
it would sit over it.** `donor-rollup-refresh` carries an **active** 14,400 s
budget — a 10,800 s ceiling fires a full hour earlier, so the watchdog would
never cancel it again. `contract-flow-rollups-refresh` carries an **active**
10,800 s budget — *identical* to the proposed ceiling, and since the watchdog is
late by 4.8–973.9 s on a `*/2` cadence, the ceiling wins every time. Two jobs
would quietly move from "bounded by a per-job budget that records what it did"
to "bounded by a global timer that records nothing job-specific," which is the
exact inversion of the design's posture and of D1's framing that the ceiling
"does NOT give per-job numbers (the watchdog does)".

**The census omitted the two jobs that decide the number.**
`entity-connection-stats-rebuild` holds the longest clean completion on prod in
the whole retained window (**18,568.4 s = 5.16 h**) and has **no
`cron_job_budget` row at all** — the role default is the only thing that has
ever bounded it, and it is `active = false` today, so re-enabling it under a 3 h
ceiling cuts both of its measured healthy shapes. `donor-rollup-refresh` has the
largest active budget on prod. Neither is in the design's §2 table.

**The honest counter-argument, stated plainly because it may well win.** All
five gate rows are from July and early August, and that regime is gone: in the
trailing 30 days the longest `complete` run is ~7,201.7 s (2.00 h).
`donor-rollup-refresh`'s weekly max fell from 8,045.9–9,387.9 s to 1,521.2 s in
the week of 09-07 and 646.1 s this week, and FIX-973 cut its in-procedure budget
from 4 h 30 m to two hours (its August rows still carry `budget_seconds: 16200`;
the recent ones carry `7200`). So 3 h survives comfortably on a 30-day basis. It
does not survive on the retained window, and read 4(b) is defined over the
retained window — so the gate fired as specified. The fix is for the next
decision to **state which window the number is sized against** rather than leave
it implicit, and to settle the watchdog inversion, which the window choice does
not touch.

**One smaller thing worth keeping.** FIX-703's own migration header, written in
July 2026, already records the pg_cron implicit-transaction hazard that cc-125
spent a session re-measuring: *"do NOT prefix `SET statement_timeout=…;` — pg_cron
wraps a multi-statement command in one implicit transaction and the procedure's
COMMIT then fails."* The knowledge was never lost, only unlinked from the place
the next author would look.
