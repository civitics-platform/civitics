> #### Drain-and-wait before any second prod op
>
> A supervised landing does not end when its transaction commits. It ends when
> the derived work it created has drained and the box is back where it started.
> So a prompt that lands a second prod op after a first one states these gates,
> and **states each as a number WITH the time it was read** — a gate with no
> timestamp is an assertion, not a reading, and every figure names its
> instrument and its database.
>
> - **(a) Unguarded owners, derived from the database.** A pg_cron job whose
>   command does not reach a procedure referencing `prod_session_state()` is
>   UNGUARDED: it fires inside a supervised session rather than deferring to it.
>   Derive the set (`cron.job` JOIN `pg_proc` — `packages/data/src/lib/cron-job-pipelines.ts`,
>   the `guarded` column); today it is the twelve `*-vacuum-analyze` jobs, both
>   `*/2` watchdogs, `abuse-events-retention` and `platform-counts-daily`. Start
>   **≥ 90 min after the last unguarded VACUUM job's END**, with **none scheduled
>   inside `[start, start + 2 × expected wall]`**.
> - **(b) Autovacuum headroom, not a dead-tuple absolute.**
>   `(trigger − n_dead_tup) / rate > 2 × expected wall` on `entity_connections`,
>   `financial_entities` and `financial_relationships`, with `rate` from **two
>   readings ≥ 30 min apart**. A rate of zero measured at the 03:00 UTC trough is
>   the weakest possible input to a rate gate — re-read it inside the window the
>   op will actually run in.
> - **(c) Crawl arms.** No crawl unit past its own job's interval in the last
>   60 min. `partial` is the crawl arm's DESIGNED terminal status and is
>   ALLOWED; what is not allowed is a unit still `running` at start, or a unit
>   whose wall exceeded its job's interval.
> - **(d) Watchdogs.** Both `*/2` jobs 60/60 in the last 60 min, no
>   `job startup timeout` on any job, and no budgeted job left `running`.
> - **(e) Interlock.** `prod_session_state()` clear, `live_writers` empty.
> - **(f) Front door.** 57014/min over the last 60 min **≤ 2 ×** the 0.033/min

## 3. Item 3 — the census, its SQL, and the smoke reading

### The two SQL strings, exactly as sent

`postgres_logs`, per-minute, both cancellation classes in one query:

```sql
select
  timestamp_seconds(div(unix_seconds(t.timestamp), 60) * 60) as b,
  countif(t.event_message like '%canceling statement due to statement timeout%') as n_timeout,
  countif(t.event_message like '%canceling statement due to user request%') as n_user
from postgres_logs t
group by b
order by b
```

`edge_logs`, 15-minute, copied verbatim from `fetchBuckets()` in
`apps/civitics/app/api/cron/front-door-watch/route.ts` (minus its `n_52x`
column, which this census does not gate on):

```sql
select
  timestamp_seconds(div(unix_seconds(t.timestamp), 900) * 900) as b,
  count(*) as requests,
  countif(r.status_code >= 500) as n_5xx
from edge_logs t
cross join unnest(t.metadata) as m
cross join unnest(m.response) as r
group by b
order by b
```

Both server-side aggregates: a 60-minute window is at most 60 rows, far inside
the ~100-row cap.

### Two design choices in the script worth knowing

- **The edge window is aligned to a bucket boundary and gated on the last bucket
  WITH TRAFFIC, not the last bucket.** The newest bucket is usually still
  filling, so one 5xx arriving into a bucket holding three requests reads as
  33 %. The `22:15` bucket above (34 requests) shows how thin the tail gets.
- **Zero traffic passes the 5xx gate and the note refuses to call it health**
  (`"no traffic in any bucket — nothing to fail, and nothing proved either"`). A
  front door answering nothing at all is the FIX-1130 wedge, and 0/0 having no
  5xx in it is not a clean bill. This is pinned as a test.

## 8. What contradicted the design

**(a) The tail's own `fr-vacuum-analyze (Mon 01:00)` string appears twice, and
the first one is in a comment I wrote.** The parenthetical-stripping pass
replaced the first occurrence of each literal, and for `fr-vacuum-analyze` that
first occurrence was the new docstring explaining what the parentheticals were,
not the `tailStep()` call. The tests caught it immediately (and the two that
caught it are the two that exist for this — "every declared owner is a jobname"
and "no declared owner still carries a parenthetical"), but it is worth naming:
a guard written in the same commit as the change it guards caught the change's
own patch script. The docstring now describes the shape without quoting it.

**(b) An `audit-*` script that says READ-ONLY in its header is not read-only.**
`audit-cross-person-misattribution.ts` line 3 read "READ-ONLY. No writes, no
--apply." It runs a genuine `UPDATE financial_relationships` over the whole
non-colliding population inside `BEGIN … ROLLBACK`, to let the unique index
adjudicate the predicted collision set. Nothing is committed — so it writes no
DATA, and the header is true in the sense its author meant. It is false in the
sense FIX-1174 cares about: an aborted UPDATE still writes one new heap tuple
per row, still takes every row lock for the duration, and still leaves all of
them dead for autovacuum. Against prod that is precisely FIX-1165's rule 1 — the
derivation, not the write, was 80 % of 2026-09-07's front-door damage for a
28-row change. Wrapped, header corrected to say what it does. **The general
lesson: "does it COMMIT" is the wrong question for this interlock; "does it take
locks and make dead tuples" is the right one.**

**(c) Grepping the `.ts` for write verbs misses a writer whose SQL is in a
sibling `.sql` file.** `recategorize-proposal-complexity-tags.ts` shows **zero**
`UPDATE`/`INSERT`/`DELETE`/`CALL`/`.rpc(` in its own source — every statement is
in `sql/recategorize-proposal-complexity-tags.sql`, which the runner reads and
wraps in a transaction. The mechanical census had it as read-only and reading
the header corrected it. This is the reason the shipped test keys on "does the
file contain `runUnderProdSession(`" plus an **explicit** allowlist, rather than
on any attempt to detect writes automatically: a write detector would have to be
right about every indirection, and the one place it was wrong here is the place
nobody would check.

**(d) Three `:prod` entries are a READ and a WRITE sharing one file.**
`donor-rollup-sweep.ts`, `donor-rollup-bulk.ts` and `treemap-global-sweep.ts`
each back a `--status` entry and a `--confirm` entry. Wrapping the file
unconditionally would make the cheapest possible check — "where is the sweep
cursor?" — hold all seventeen guarded pipelines (suppressing every freshness
threshold on them, FIX-1177) and REFUSE outright while another session is up.
That makes the one command you most want during someone else's long run the one
command you cannot run. The wrapper takes a `--status` bypass, and the interlock
test pins both halves: the file must claim the session, and `--status` must
reach `main()` directly.

**(e) `printTailTable`'s third argument is optional, and that is load-bearing
rather than lazy.** `drainFrRewrite` also calls it, and an absent owners map
must NOT render `NOT SCHEDULED` — that would manufacture a dozen orphan signals
out of a `cron.job` nobody queried. It renders `?` instead, with a footer saying
the map was not read. "Not read" and "not scheduled" being spelled differently
is the same distinction FIX-1190 was about one layer down: a visible missing
reading beats an invisible wrong one.

**(f) The prompt's `Fixes: FIX-<printed>` for item 4 resolved to FIX-1197, not a
number in the 119x range that could be guessed.** `fix:add` allocated it after
FIX-1196, so the D5 filing and its closure both ride 518ecd33 and the trailer is
honest. Nothing else was filed — everything the reads surfaced is either already
bulleted (FIX-1191 for the FR vacuum cadence, FIX-1194 for the `fe-vacuum-analyze`
startup timeout) or landed here.

**(g) A bot commit landed mid-run.** `c65599c3 docs(receipts): 2026-09-19` at
23:08 UTC, between `session:check` and the first commit. The rebase was a no-op
because the worktree branch already had it; `head_before` in the front matter is
`c65599c3` rather than the `7191d90b` this session opened on, which is the
honest parent of the first commit.
