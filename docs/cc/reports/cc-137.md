## 1. Read 2 — the parsed shape, and the API's two silent limits

`select p.*` returns `Backend error! Retry your query`; **`select p` returns the
whole struct and works**. 25 fields:

```
application_name  backend_type  command_tag  connection_from  context
database_name     detail        error_severity  hint          internal_query
internal_query_pos  leader_pid  location      process_id      query
query_id          query_pos     session_id    session_line_num
session_start_time  sql_state_code  timestamp  transaction_id  user_name
virtual_transaction_id
```

On a PostgREST `57014` row, `query` carries the full ~600-char `WITH pgrst_source
AS (…)` envelope and is fully populated. `user_name` is populated too — and is
**always `authenticator`**, 38 of 38 over 24 h, because PostgREST logs in as
`authenticator` and then `SET ROLE`s; Postgres logs the login role. There is no
duration field, so the effective role cannot be inferred from the cancel latency
either.

So: **`--by query` can answer "which statement", and nothing here can answer
"which role".** pgss has the opposite blind spot — it records the impersonated
role but only for completions — and the two cannot be joined.

**Retention is 7 days.** A window starting 7 days back returns rows; 8, 9 and 10
days back return zero. 11–13 days were not measured, because the API started
answering `ThrottlerException: Too Many Requests` — it rate-limits, which is why
the attribution mode reads one window per invocation rather than looping.

**The 24-hour clamp**, which is the discovery of this run and the reason D2 could
not be run as written. Each request made at 2026-09-19T03:07Z:

| lookback asked | rows | rows actually covering |
|---|---|---|
| 1 day | 3,790 | 09-18T03:08 → 09-19T03:06 (the whole window) |
| 2 days | 4,824 | 09-17T03:08 → 09-18T03:06 (**oldest day**) |
| 3 days | 3,857 | 09-16T03:08 → 09-17T03:06 (**oldest day**) |
| 4 days | 3,897 | 09-15T03:08 → 09-16T03:06 (**oldest day**) |

No error, no warning, no short result — a full, plausible 24 h that is the

## 2. Item 1 — the attribution mode

`--by <field>` / `--like <substring>`, no verdict, exits 0. The SQL:

```sql
select
  coalesce(regexp_extract(p.query, r'"public"[.]"([a-z0-9_]+)"'),
           substr(regexp_replace(coalesce(p.query, t.event_message), r'\s+', ' '), 1, 60)) as g,
  count(*) as n
from postgres_logs t
cross join unnest(t.metadata) as m
cross join unnest(m.parsed) as p
where p.sql_state_code = '57014'
  and p.query like '%<like>%'      -- only when --like is given
group by g
order by n desc
limit 20
```

Grouping is on the **function name extracted from the envelope**, never the
envelope — PostgREST's wrapper differs per bind shape, so raw text would return
one row per shape and blow the ~100-row cap while saying nothing. `--by` is
allow-listed (it is interpolated into SQL); `--like` is restricted to
`[A-Za-z0-9_. :/-]`.

The two runs:

```
── 57014 attribution ── by user_name
   2026-09-18T03:22:09Z → 2026-09-19T03:22:09Z
   group           count  share
   authenticator      38  100.0 %
                      38  total

── 57014 attribution ── by query · query like %get_official_page%
   2026-09-18T03:22:21Z → 2026-09-19T03:22:21Z
   group               count  share
   get_official_page      10  100.0 %
                          10  total
```

Unfiltered over the same window: **`get_official_page` 10, `enrichment_queue` 9,
`check_senate_reference_cohort` 7**, then a long tail;
`link_officials_to_districts` appears with 1. `get_official_page` is the
single most-cancelled statement on prod.

Nine unit cases plus two structural ones. One of the structural ones exists
because of a bug I introduced and then measured: **the attribution path
originally called `process.exit(0)` and the shell saw 127.** After a single
`fetch`, `process.exit()` aborts the process on Windows with
`Assertion failed: !(handle->flags & UV_HANDLE_CLOSING), src\win\async.c`. The
existing gate path survives the same call because it awaits *two* fetches and is
far enough through undici's teardown by then. The attribution path now sets
`process.exitCode` and returns, and a test pins the asymmetry — a script whose
whole contract is "exit 0" silently exiting 127 is the kind of thing that only
shows up in the prompt that depends on it.

### Where the cost actually is

The prompt's cohort was "the ten heaviest by `official_donor_totals`". Wrong
axis: this RPC has no donor section. Kamala Harris is rank 1 by donations and the
**cheapest** official measured (3,670 buffers); Warnock, Cruz and Kelly at
~1,875 votes each cost 13–15k. Cost tracks **vote count**.

Per-section for Warnock, of 13,272 buffers: `recent_votes` **6,034 (45.5 %)**,
`all_votes` 3,556, `spending` **56**, `vote_count` 24.

`spending` was the obvious suspect — it scans `financial_relationships` with no
official filter at all, identically for every official, and the body says so. It
is not the problem. Measured, not assumed.

`recent_votes` returns 100 rows and costs more than `all_votes`, which returns
500, because `ORDER BY voted_at DESC NULLS LAST` **cannot use the index that
already exists** (`votes_official_voted_at` on `(official_id, voted_at)`) —
scanning it backwards gives `DESC NULLS FIRST`, which is not the same ordering.
So it bitmap-scans all 1,875 of the official's votes, joins every one, and top-N
sorts to 100. `voted_at` has **zero NULLs** — 0 of 969,302 on the clone, 0 of
982,966 on prod — so the `NULLS LAST` buys nothing and costs a full-history scan
per page view.

| `recent_votes` variant | plan | buffers |
|---|---|---|
| today | Bitmap Heap Scan 1,875 rows + top-N heapsort | **6,034** |
| inner `ORDER BY voted_at DESC` | Index Scan Backward | **736** |
| today's text + `(official_id, voted_at DESC NULLS LAST)` | Index Scan | **731** |

Whole-RPC, probe index built and dropped on the clone (16 MB against a 338 MB
heap): Warnock 13,274 → 7,989 (−40 %); worst case on the clone (2,530 votes)
14,882 → 7,702 (**−48 %**). 408 officials have over 1,000 votes.

**D2's outcome: branch (ii), but not the fix shape the prompt assumed.** The
first move is an index, not a materialization. Three options with costs are in
the append and the audit; **(A)** — add the index, exact semantics, no RPC change
— is recommended, because it is the only one that cannot change which rows a page
shows. `all_votes` is the second lever and *is* a materialization question.
**FIX-1180 stays OPEN**; the choice is Craig's and the build was out of scope.

## 8. What contradicted the design

**Five things, and three of them change what the bullets mean.**

**1. FIX-1180's question has no answer because it has no subject.** The prompt
frames the whole run around measuring an anon-vs-authenticated split, and D2
branches on it. There is no authenticated cohort: `createPublicClient()` is the
publishable key with no cookie handling, so every visitor on an official page is
anon whether signed in or not, and pgss shows 366 anon calls against zero
authenticated. The prompt hedged the right way for the wrong reason — it
anticipated that the *instrument* might not be able to see the split (it can't:
`user_name` is `authenticator` on all 38 of 38) and prepared for that. But even a
perfect instrument would have found one cohort, because there is only one.

**2. The bullet's own "candidate" for FIX-1181 cannot exist.** "A pooled
authenticator connection on which something issued a non-`LOCAL` `SET
statement_timeout`" presumes repo code can reach PostgREST's pool. It cannot —
PostgREST is a separate process, and every session-scoped `SET` in the tree is on
a `pg.Client` the code constructs and closes itself. This is worth stating
plainly because the prompt's item 2 would have built a lexical guard against a
pattern that has never occurred and structurally cannot.

**3. The heavy section is the one the code apologises for *not* being the
problem.** `spending` scans `financial_relationships` with no official filter at
all, identically for every page view, and the function body says so in a comment
("faithfully NOT official-filtered"). It is 56 buffers — 0.4 %. I went looking for
it first and was wrong. The real cost is a defensive `NULLS LAST` on a column
with no NULLs, which silently disqualifies an index that already exists and turns
a `LIMIT 100` into a scan of the official's entire voting history. The fix the
prompt's rule 20/32 prescribes (materialize, or split the RPC) is the *second*
move here, not the first.

**4. The prompt's cohort is keyed to the wrong dimension.** "The ten heaviest by
`official_donor_totals`" — but `get_official_page` has no donor section; donors
come from `official_donor_rollup_mv`, read separately by the page. The #1 donor
official in the database is the cheapest of the four measured. Cost tracks vote
count, and the honest cohort is the 408 officials with more than 1,000 votes.

**5. The Logs API lies about long windows, and D2 asked for a long window.**
"Run over the longest window the API keeps" would have returned day 1 of 7 — a
full, plausible 24 h of rows, no error, no warning, no short result. Nothing in
the response distinguishes it from the answer asked for. This is the failure mode
where an instrument is worse than no instrument, and it was one request away from
being quoted in an audit as a seven-day figure. The census now refuses the shape.

**One smaller thing, on the way through.** `pg_stat_statements` does not record a
statement killed by `statement_timeout` — measured, zero rows. That is why
FIX-1128's bounds table marks functions "within" or "unobserved" when their
overruns are in fact being cancelled: the table is built on an instrument that is
blind to exactly the event it is auditing. It is also what makes the `17.9 %`
figure above possible to state at all, since the numerator and denominator come
from two different instruments that see disjoint halves of the same population.
