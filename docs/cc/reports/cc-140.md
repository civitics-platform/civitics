## 2. Item 1 — FIX-560

**Enum.** `20260920040000` — `ALTER TYPE public.notification_event_type ADD VALUE
IF NOT EXISTS 'claim_outcome'` alone in its file, following the
`20260528180300` precedent. The prompt asked which happened: **no split was
needed** — nothing in SQL uses the value, so one file sufficed.

**Where it fires.** Three sites, all best-effort behind try/catch with a logged
error, because the review write has already committed and a notification failure
must not turn a successful action into a 500 the operator retries into the
pending-only 409:

- approve — `admin/grants/[id]/route.ts`, after the `grant_events` insert;
- reject — same file, after its `grant_events` insert;
- auto-approve — `officials/claim/route.ts`, after `event: "auto_approved"`.

**Title/link shape** — pure `buildClaimOutcomeNotification()` in
`apps/civitics/src/lib/claim-notification.ts`:

- title `Your claim was approved` / `Your claim was not approved`;
- body `Your request for official access to <name> was approved and is now
  active.`, degrading to `official access` when the name read failed;
- link `/officials/<target_id>` **only** for an official target;
- `entityType`/`entityId` via `followEntityTypeFor()`.

That mapping is the part that carries the weight. `grant_target_type` and
`follow_entity_type` are different vocabularies and `notifications.entity_type`
is the second one, so `'global'` and `'institution'` get a notification **with no
entity** rather than no notification — they are the grants carrying the most
access. A naive `entityType: grant.target_type` typechecks against the `any`
admin client and fails the enum at insert time.

**Refactor:** the officials read moved out of the approve branch. Approve needed
term dates for expiry; reject now needs `full_name`. Read once, used by both.

**Test:** `claim-notification.test.ts`, 13 cases. It asserts every
`grant_target_type` maps to a `follow_entity_type` member or to `null`, both
no-counterpart targets still notify, a jurisdiction target carries the entity
but **not** an `/officials/` link, and a missing name degrades the body without
emitting `"undefined"`.

**Bonus, found by tsc.** `EntityType` in `notifications.ts` was
`"official" | "agency"` — one value behind `follow_entity_type`, which gained
`jurisdiction` on 2026-05-28. A jurisdiction notification could not be typed
even though the column accepts one. Widened in the same commit.

## 3. Item 2 — FIX-938

**Version scheme.** `packages/db/src/ai-prompt-versions.ts`, beside
`ai-pricing.ts` and for the identical reason: the producers live in
`packages/ai`, `packages/data` and `apps/civitics`, and `packages/db` is the
lowest package in the graph. Format `YYYY-MM-DD`, `.N` if bumped twice in a day.
`legacy` and `unregistered` are reserved and a test asserts no pair uses either.

The version is attached to the **cache key**, not to a prompt — because three
prompt texts write the same keys and a reader cannot tell which produced a row.
Versioning any one would make the other two look stale and the cache would
thrash between producers.

**Writers touched (6):** `packages/ai/src/client.ts:73` ·
`ai-summaries/index.ts:115` · `drain/apply.ts:253` ·
`admin/enrichment/submit:230` · `officials/[id]/summary:254` ·
`proposals/[id]/summary:176`.

**Readers touched (3 generate paths, 6 call sites):** `client.ts:53` ·
`officials/[id]/summary:104` · `proposals/[id]/summary:69` ·
`ai-summaries/index.ts` proposal + official preloads · `seed-backlog.ts:190`.
The preloads decide "already summarized", which must now mean "under the current
prompt" — otherwise a prompt fix reaches nothing already in the table.

**The ten display readers are deliberately untouched.** See §9.

**Also fixed in passing:** the proposals on-demand cache read omitted
`summary_type` while its upsert writes `plain_language`. A proposal with a second
summary type would make `.maybeSingle()` error on multiple rows, be swallowed by
the catch, and regenerate on **every request**. Now pinned.

**`legacy` row count: zero.** 6,888 rows backfilled to `2026-09-20`, on both
environments. The prompt expected `legacy`; §9 explains why not.

**Constraint name decision.** The prompt asked whether the UNIQUE's name had to
be preserved. **Moot** — the key did not change, so the constraint was never
touched. Confirmed on Pro after the push:
`ai_summary_cache_entity_type_entity_id_summary_type_key` is intact, and the
four FK-surface migrations that name it (`20260525234504:408`,
`20260602000000:243`, `20260706020000:281`, `20260919000000:299`) needed no edit.

**Drain coupling made load-bearing.** Both `.md` files gained
`<!-- prompt-version: … -->`. Nothing parses it at runtime, so
`drain-prompt-version.test.ts` is the alarm: reword `summary.md` without bumping
the constant and CI fails. It also asserts the migration's backfill literal
equals what the code stamps — if those drift, all 6,888 rows are stamped with a

## 4. Item 3 — FIX-922

**Key shape.** `fec_committee_id` stays PRIMARY KEY. A uuid-keyed row takes the
synthetic key `'fe:' || financial_entity_id` with the uuid in its own column. The
CHECK makes the two **mutually derivable**, which is stronger than the prompt's
prefix rule — it also rejects `'fe:<some other uuid>'`, a row naming one entity
in its key and another in its column:

```sql
CHECK ((financial_entity_id IS NULL     AND fec_committee_id NOT LIKE 'fe:%')
    OR (financial_entity_id IS NOT NULL AND fec_committee_id = 'fe:' || financial_entity_id::text))
```

Plus `UNIQUE (financial_entity_id) WHERE financial_entity_id IS NOT NULL`.

**Proven on the clone**, all inside one rolled-back transaction: a mismatched
synthetic key rejected; a committee key carrying a uuid rejected; an
`fe:`-prefixed key with a NULL uuid rejected; both escapees inserted; a duplicate
`financial_entity_id` rejected by the partial unique; the reader then resolving
**795 rows, 0 orphans** and naming both new rows correctly. `ROLLBACK`.

**The reader's plan on the clone.** Two `LEFT JOIN`s rather than
`ON a = b OR c = d`, which would plan as a join filter:

```
Nested Loop Left Join  (rows=793) (actual 0.026..4.103)
  -> Nested Loop Left Join   Join Filter: (o.financial_entity_id IS NULL)
     -> Seq Scan on financial_entity_industry_overrides o  (793 rows, 13 buffers)
     -> Index Scan using financial_entities_fec_committee_id_key   Index Cond: (fec_committee_id = o.fec_committee_id)
  -> Index Only Scan using financial_entities_pkey   Index Cond: (id = o.financial_entity_id)   Heap Fetches: 0
Execution Time: 4.886 ms   Buffers: shared hit=3188 (0 read)
```

Both arms are index lookups with the predicate as an **Index Cond**, not a
filter. The seq scan is the 793-row override table itself.

**The two escapees, for Craig's curation** (filed as FIX-1204, not inserted
here):

## 5. Item 4 — FIX-888 (b)

**Copy**, from the pure `sessionScopedSaveNotice()`:

> This view saves the filters, not the hand-picked group "Climate advocates"
> (3 members). Groups you pick by hand live only in this session.

Plural form names the count of groups and the total members. It states what **is**
saved, not only what isn't — "this won't be saved" invites the reader to assume
the graph is what gets saved.

**Affordances**, three surfaces:

1. **BUNDLE AS GROUP dialog** (`ExplorerActionBar`) — a second line before the
   handoff. This matters more than it looks: `/graph` strips the `groupIds`
   params after decoding, so refresh and sharing lose the group too.
2. **Focus list** (`FocusTree`) — a `session only` chip on the group row, with
   the tooltip as its long form.
3. **★ SAVE VIEW** (`SidebarBrowser`) — now a confirm step (`save filters
   anyway` / `cancel`) **when and only when** a hand-picked group is in focus.
   Otherwise it is the one-click save it always was.

The predicate is `isSessionScopedGroup` in `packages/graph/src/types.ts`, beside
FIX-826's `isSelectionGroup`, and covers **both** shapes a saved view cannot
reproduce: `filter.officialIds` (FIX-886) and `memberIds` (FIX-826).

**Test:** 9 cases in `graph-compiler.test.ts`. The one that carries the weight is
the **negative**: a predicate group must **not** trigger the notice, or the
warning appears on every save, becomes noise, stops being read, and lands exactly
where the silent drop did. Also asserted: `buildSavedViewPayload` still carries
neither `officialIds` nor `memberIds` — if (b) ever grew a persistence side it
would be (a), which was declined.

**Declined options, recorded** in `graph-compiler.ts`: (a) snapshotting the ids
drifts as officials leave office or merge; (c) a real membership table is a
feature, not a fix.

**The reader set.** The prompt's read-3 list came from grepping the pipelines. A
repo-wide grep finds **13 readers**, including one inside a **SQL function**
(`get_official_page`, a `LIMIT 1` with no `ORDER BY`) and **four** that do not
filter `summary_type` at all and use `.maybeSingle()`. The moment a second row
per entity can exist, the RPC picks nondeterministically and the four
`.maybeSingle()` sites start erroring on multiple rows — in three of them the
error is swallowed by a catch and becomes a permanent cache miss.

**The display surfaces would have gone blank.** The table is 6,888 rows, **all**
`(proposal, plain_language)`. Under D2, filtering readers to the current version
empties the home page's summaries, the proposals index, proposal detail and
entity search until each of 6,888 proposals is regenerated. Regeneration is gated
by a **$4/month** spend cap and the backlog costs roughly **$11** at Haiku 4.5
rates — so it would not clear, and `generateSummary` throws once the cap binds.
Stale framing is strictly better than no summary.

**The `legacy` backfill would have burned that $11 for nothing.** FIX-938 changes
no prompt text. Those 6,888 rows were produced by the prompts in the tree today.
And the bullet's cited live example — the pre-FIX-931 "Total raised" framing —
**has no rows**: `(official, profile)` is empty on both environments. The
invalidation D2 was designed to force had nothing to invalidate.

**Shipped instead:** one row per entity carrying the version that produced it.
`(entity_type, entity_id, summary_type)` stays unique; the generate paths compare
the version and a mismatch is a miss, so a future prompt edit regenerates and
**replaces in place**. That is the bullet's requirement — "a prompt edit
naturally misses the cache" — delivered exactly, with no reader broken, no
display blanked, no RPC change and no cost event. What it does not buy is D2's
audit retention; that wants an `ai_summary_cache_history` table, not a
polymorphic cache a dozen surfaces read, and it is filed as **FIX-1206** with the
regeneration decision.

### D3's foreign key would have silently deleted curated rows

D3 specified `REFERENCES financial_entities(id) ON DELETE CASCADE`. FIX-916's own
reader comment says the opposite is required: an override whose key no longer
resolves must be *"surfaced and counted rather than silently vanishing"*, because
the likely cause is a FIX-544 entity merge and the fix is to re-point one row.
A cascade does exactly the forbidden thing — a merge deletes the loser entity and
takes a hand-audited assignment with it, with no log line. `RESTRICT` is worse;
it aborts the merge.

Shipped with **no FK**. A dangling uuid then behaves exactly like a dangling
committee id — the `LEFT JOIN` leaves `entity_id` NULL and it lands in the
existing `orphanOverrides` warning. One code path, and it matches the committee
arm, which has never had a FK either.

### D3's TSV column would have churned two closed audits for nothing

D3 said the TSV gains a `financial_entity_id` column, empty for the 792 rows.
There are **two** TSVs (742 + 50), `industry-overrides.test.ts` parses both
**positionally**, and both are dated artifacts of completed audits. Adding an
empty seventh column means a trailing tab on 792 committed lines carrying no
information.

FIX-921 already set the precedent: a new cohort gets **its own file** with its
own drift alarm. A uuid-keyed cohort is a new cohort, and its TSV leads with
`financial_entity_id` in place of `fec_committee_id`. The shape is documented in
the migration header and in FIX-1204, so Craig's rows have a defined form. The
existing TSVs are untouched.

### Smaller things the tree said that the prompt did not

- **`backfill-crs-summaries.ts` is not a writer** of `ai_summary_cache`. The
  prompt lists it as one of four; its own header (`:18`) says summaries live in
  the cache *"not here"*. It writes `proposals`.
- **The admin grants route has a third action.** `revoke` (FIX-928) and a GET
  pre-read (FIX-1167) both postdate the prompt's picture. Revoke withdraws
  **live** access and still says nothing — filed as **FIX-1205**.
- **`EntityType` had drifted from its enum since May.** `follow_entity_type`
  gained `jurisdiction` in `20260528180300`; the TS union never did. Only tsc
  caught it, because FIX-560's mapping is the first caller to pass one.
- **The proposals on-demand cache read omitted `summary_type`** while its upsert
  writes `plain_language` — a latent regenerate-every-request bug, fixed here.
- **`generateSummary` has no callers.** Only comment references from the two
  routes that reimplement it, and its `summary_type` vocabulary
  (`bill`/`regulation`/`official`) matches nothing in the table. Its pairs were
  registered anyway so a future wiring cannot silently write `unregistered` rows
  that no bump could invalidate. Noted in FIX-1206.
- **Prod reads must run from the primary checkout.** The worktree's
  `.env.local.prod` is a stub with no `SUPABASE_DB_PASSWORD`, so
  `db-query.mjs --prod` prints usage and exits from inside a worktree.
