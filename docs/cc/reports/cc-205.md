## §4 What contradicted the design

- **The live body matched.** Prod equalled the 1248 file to the byte, and
  `20261004075000_fix1124` does not redefine the procedure. The migration is
  built on prod's body, the additions are fenced, and the test proves the rest
  byte-equal.
- **The signature lever worked first time.** Any stored sig ≠ computed sig
  passes the `IS DISTINCT FROM` gate. One wrinkle: the clone's own sig count
  moved by one since cc-179, so a "steady state" clone was one row off steady.
- **64MB was the right number, and so would 32MB have been.** Going lower costs
  no wall on the clone, because the spill is cheap sequential I/O and the
  cold-read cost dominates. 64MB is kept because it was ratified and is
  sufficient: every hash ≤ 128 MB, and peak backend memory falls 380 → 126 MB
  (prod ~600+ → ~150 MB). 32MB is a free second step if 10-13 still swaps.
- **D2 is weaker than it reads, in four ways:**
  1. **`box_is_saturated()` does not see memory.** Its memory half is
     REPORT-ONLY, and the gates call it with the watchdog wall OFF (P1-A D2).
     So it trips only on `stale` (probe stamp older than 180 s) or
     `fork_failures` (≥ 3 startup timeouts in 10 min). On 10-06 the probe
     succeeded at 16:04:00Z with the box at 141 MB MemAvailable and swap full.
     A start gate reading at that instant would have said `clear`.
  2. **It reads once, at the start.** The trio is one transaction with no
     COMMIT between phases (by design: it rolls back with the signature). So
     the gate cannot back off between `_delete` and `_insert`, which is where
     10-06 went wrong. Only keyed units with a COMMIT per unit give a
     between-units reading.
  3. **A wait holds a snapshot** for up to 600 s on a saturated box, i.e. an
     xmin horizon. This is the same cost P1-A accepted.
  4. **It is placed differently from the prompt** (stopped_items line 1): P1-A's
     gate → lock → defer, so the FIX-950 claim is read after any wait, and no
     lock is held through one. The P1-A test asserts the same order for its
     three procedures.
- **The clone's weekly job exists.** The prompt expected it might be absent; it
  is jobid 24, parked. D4 fires there, so the job was re-parked, and D5 (5)
  asserts the slot and command rather than `active`.
- **`cron_job_budget` note**: it is not the "Healthy max 2741s" text. 1248 already
  replaced it, and the replacement names 10-06 as an in-band run, which it was
  not. Reported only, per the prompt.
- **Observability gap, not acted on.** A cancelled weekly stamps
  `desired_rows` / `deleted_rows` (PL/pgSQL variables survive the
  subtransaction rollback) but no `phase_seconds`: `v_phase` is only built
  after the INSERT returns. cc-204 had to rebuild the 10-06 phases from
  auto_explain. A per-phase stamp built as each phase finishes would make a
  cancelled run self-describing. Not filed, since this prompt files nothing;
  it is a candidate for Cowork.
- **Concurrency.** cc-206 appended to the same FIX-1284 bullet line, and the
  rebase conflicted on it. I kept both appends, in order. cc-206 landed no
  migration, so the gated push's dry run stayed one file.
