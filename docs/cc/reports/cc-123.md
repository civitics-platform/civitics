## 2. Phase 0 reads 4 and 5

### Read 4 — how a workflow commits to `main` here

**`main` has no branch protection.** `gh api repos/:owner/:repo/branches/main/protection`
→ `404 "Branch not protected"`. The fallback the prompt provisioned for (land on
a `receipts` branch, file the protection change) was **not needed**.

The precedent is `audit.yml`, not the 655 blocklist step. The blocklist workflow
opens a PR via `peter-evans/create-pull-request` because that is what *it* wants;
`audit.yml` has been pushing dated reports **straight to main** since 2026-07
under `github-actions[bot]` — `2d5a65bf` (09-07), `d27093b8` (08-24), `2e017d28`,
`dc72acdb`, `5ace83da`, `e8978781`, `c5ae7d69`, `843adffc`. So: workflow-level
`permissions: contents: write`, bot identity, `git add`, a
`git diff --cached --quiet` guard, commit, push.

Two deliberate departures from `audit.yml`:

- **`permissions` is JOB-scoped, not workflow-scoped.** `audit.yml` has one job
  so the distinction is moot there; `nightly.yml` has five, and the four phase
  jobs must keep `contents: read`.
- **`git pull --rebase origin main` before the push.** `audit.yml` doesn't need
  it (04:00 UTC Monday, nothing racing). The nightly's tail finishes hours after
  the run starts, so main will usually have moved.

`[skip ci]` is unnecessary and is not used: `tests.yml` carries
`paths-ignore: ['docs/**']` so a receipts-only commit skips it, and
`fixes-integrity.yml` has **no path filter** and runs on every push — correct,
and exactly the split FIX-466 made.

### Read 5 — does the 1011 reader count a `skipped` row as a firing?

**No. Neither reader does, and the two consequences are different sizes.**

`check_rollup_freshness` (`20260903060000_fix973b`) derives `last_complete_at`,
`hours_since_complete` and `stale` from one CTE:

```sql
last_good AS (
  SELECT … FROM public.data_sync_log
  WHERE pipeline = p_pipeline AND status = 'complete'
  ORDER BY started_at DESC LIMIT 1
)
```

`list_scheduled_rollup_pipelines` (`20260903000000_fix1135_1059_1011`) measures
cadence over `closures`, `WHERE a.status = 'complete'`, and `closures_any`
likewise.

So a firing the FIX-950 guard turned into a `skipped` row is, to both, identical
to a firing that never happened: the freshness clock keeps climbing and the
cadence median is computed across the gap.

The **census itself is fine** — it is `SELECT DISTINCT pipeline FROM all_runs`,
any status, and the registry does expose `last_row_at` (any status) alongside
`last_status`. So a skipped pipeline stays listed. What is lost is the
*verdict*: anything built on the freshness answer reads a deliberate skip as a
missed cycle.

**Filed as FIX-1177, not fixed here** (Out of scope says file only). The bullet
separates the cosmetic half — which FIX-1176 sidesteps by reading
`data_sync_log` directly, so `skipped(reason)` is its own verdict and outranks
`missing` — from the real half: a hold spanning `escalate_after_hours`
(cadence × 2.5 — 60 h for a daily rollup) makes the canary **escalate on a
deliberate operator action**. Latent today; FIX-950's holds are minutes.

### The nominal-day rule, as stated at the top of every file

> The date is the nightly's NOMINAL day, not the wall clock. `nightly.yml`'s
> cron fires at 21:00 UTC on the day *before* the run it names, and each phase
> carries `NIGHTLY_SLOT_OFFSET_HOURS` so the run gates on `now + offset`
> (FIX-1163). This file used offset **3h**, so it is named for the same day the
> run itself gated on.

The window that maps to nominal day `d` is exactly `[d − offset, d + 24h − offset)`.
The sample is dated **2026-09-12** because the run it describes started
2026-09-11T22:54:15Z and `22:54 + 3h` is 09-12 01:54 UTC.

**Two deliberate divergences from `weekly-gate.ts`**, both commented at the
definition and tabulated in `docs/receipts/README.md`:

1. **Default offset 3, not 0.** `weekly-gate` defaults to 0 because a plain
   `workflow_dispatch` wants wall-clock semantics. This file always describes a
   scheduled nightly, and offset 0 on a hand run at 06:00 UTC puts last night's
   22:5x start one day outside the window and renders section 1 empty. The
   workflow sets the env explicitly, mirroring the phase jobs' expression, so
   the default only ever governs a hand run.
2. **UTC projection, not local `getDay()`.** Correct there (it mirrors
   production's own gate, and runners are UTC), wrong here — a file *name* must
   not move with the machine's zone. Covered by a test.

## 7. What contradicted the design

**Four things, three of them caught by actually running it against prod.**

### (a) D2's verdict vocabulary has no word for a firing with no duration — and the obvious ordering is wrong

D2 specifies `in-band | above | below | missing | skipped(reason)`. That set
assumes every firing yields a duration to compare. `cron.job_run_details.status`
does not: it also carries `failed`, and the non-terminal `starting`,
`connecting`, `sending`, `running`. A crash that died in 3 s would render
`in-band`.

I added `failed` and `running`. But the **first prod read caught a real bug in
my own precedence**, which is the part worth recording. I had checked "no
`end_time` ⇒ in flight" *before* `failed`. pg_cron leaves `end_time` NULL on a
job that never got to run at all — the FIX-1073/FIX-1137 `job startup timeout`
class — so `donor-party-rollup-refresh`'s **09-08 failure rendered as `running`**:
a four-day-old dead job displayed as healthy work in progress. Exactly the
failure mode the file exists to prevent, shipped inside the file itself.

Fixed (`failed` is now checked first, the non-terminal statuses are enumerated
rather than inferred), covered by two tests, and the same prod read now shows
`**failed** (server restarted)`.

### (b) Reading "the latest run row" erases the measurement when the last firing was a skip

Section 3 read the most recent `refresh_derived_mvs` row. On the local clone —
whose most recent row is a FIX-950 verification skip — every unit timing, the
whole `vm_before` reading and the search-unit band all went blank, and the band
read `missing`.

This is **FIX-1177's asymmetry one layer down, in my code**: a deliberate hold
rendering as a lost measurement. Section 3 now carries both — the last firing
(what happened, with its `skip_reason`) and the last **completion** (the
numbers, labelled with when they were taken). They are the same row on a normal
day and the split costs nothing; on the day it matters it is the difference
between a receipt and a blank.

### (c) `pnpm --filter` would have written the file where nothing reads it

`--out docs/receipts` resolved against `process.cwd()`. `pnpm --filter
@civitics/data …` runs with cwd at `packages/data`, so the first local run
looked for `packages/data/docs/receipts/bands.json`, didn't find it, and
rendered **every job `no-band`** — while the run reported success. That is the
same trap CLAUDE.md records for the drain's `--output` ("claims 12 batches then
fails to write the files"). Relative paths now resolve against the repo root,
found by walking up to `pnpm-workspace.yaml`, and the fallback warns loudly
rather than writing somewhere surprising. `bfb18c10` then replaced my hand-rolled
`URL.pathname` drive-letter strip with `fileURLToPath`.

### (d) D3's example and D3's schema disagree

In one sentence D3 specifies `{ job_name: { lo_s, hi_s, source } }` and gives
`donor-rollup-refresh` two different expectations — `09:00 firing ≤ 400 / 12:00
≈ 0`. One band per job name cannot hold two. I kept the stated schema and used
the looser ceiling (so the 12:00 firing is trivially in-band), said so in the
entry's own `source` string, and gave `README.md` a "Known limitation" section.
Extending the schema is a real option; it did not seem worth doing before
anything has actually been missed by the loose ceiling.

09-02  857.9    09-06  806.9    09-10  891.2  ← above
