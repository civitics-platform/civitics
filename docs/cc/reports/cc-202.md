## 4. What contradicted the design

**4.1 D4 cannot be built on a 24 h ring. This is the main finding.** The slot window `[slot − 24 h, slot)` and rule (c), "never a partial window", cannot both hold, because the receipts job writes after the slot:

| nominal day | write | ring at write |
|---|---|---|
| 10-08 | 21:12:53Z | starts 21:12Z 10-06 |
| 10-06 | 21:52Z | starts 21:52Z 10-04 |

A Sunday drop night writes about 100 min late. The 720-sample ring therefore never holds the first 12–100 min of the slot window.
- **Strict (c):** every run banks `available: false`.
- **Lenient:** every banked day silently drops `[slot_{N−1}, slot_{N−1} + wall)`, which is the previous nightly's own burst. On 10-07, 21:02–21:14Z read 590.5–946.7 pages/s, the largest burst of the day after the 02:04–02:12Z event and 06:02Z. Day N cuts it off its end, and the ring has rolled it out before day N+1 writes, so it would sit in neither day.
- **Today's write-time window at least keeps it once.**
- **The prompt's own example shows the gap.** "At 01:37Z the slot window's start is 28.6 h back" is true, but at 21:52Z it is already 24.9 h back.

I stopped the build ("strike the build if you disagree") and filed **FIX-1289** with the corrected shape:
- **(1) Write-once.** A later run keeps the committed `memory_day` + `mem_day`. This half is independent and safe to build now.
- **(2) Tiling, either way:**
  - **(a) recommended:** `BOX_HEALTH_RING_LEN` 720 → 900 (30 h). It is still 2 Upstash commands per sample, with storage +25 %. Then bank exactly `[slot − 24 h, slot)`, add `window: {from, to}`, and refuse a window the ring does not hold. Within ~6 h of deploy the ring would hold the first full slot window.
  - **(b)** chained `[previous window.to, this write)` windows. These tile on a 24 h ring but vary about ±1.5 h in width.
