## What contradicted the prompt

1. **There is no per-night cap on the gap pass.** D2 says "inside the walk's
   existing per-night cap", and the STOP row reads "bypasses the cap". Pass B in
   `roll-probe.ts:364–379` fetches every gap below the frontier. Only `blocked`
   stops it; the bounds are pacing and `BLOCKED_LIMIT`. The STOP is about how
   many rolls get re-fetched. That count is fixed by the record's size: 13 on
   prod, plus session 1's re-walked tail. It is under the 60 and the ~20
   expected, so D2 landed. The cap the prompt assumed does not exist. If the
   record ever grows large, a version move would re-fetch all of it in one
   night, limited only by pacing and the block limit.
2. **A version move re-fetches more than the parser-reason records.** The whole
   record goes, including retry-window reasons and `tail_closed`. On prod today
   that only adds session 1's 3-GET tail walk.
3. **No roll has been held as `unknown_cast`.** The premise, "since
   `f9e3564a` a roll containing one is held back whole", is the mechanism.
   Neither 11-17's nor 11-18's nightly hit it. The FIX-1430 receipt will read
   "none were held", not "N now stored".
4. **D1's "the way the other casts are (… whitespace collapsed)".** The other
   casts were only trimmed and lowercased. I added the collapse to the shared
   normalisation, so `Not  Voting` with an inner double space now maps too. No
   new cast string is mapped; `""`, `"   "` and partial strings still throw.
5. **D3's literal `origin main`.** The step uses `${GITHUB_REF_NAME}`, which is
   `main` on the Vercel dispatch, so behaviour there is exactly D3. Taken
   literally, a hand dispatch on another ref would rebase that ref onto `main`
   and push it to `main`. The bare `git push` it replaces pushed to the
   dispatched ref, so this keeps that. This was the conservative branch,
   unattended; flagging it for Craig.
6. **Read 5's STOP row (a path that already exists on `main`).** A second run on
   the same UTC date rewrites `docs/audits/<date>.md` / `.json`, which already
   exist. The concurrency group queues it, so it checks out after the first
   run's push and its rebase replays a modification on the same base: no
   conflict. A conflict needs a third writer to change that same file on `main`
   inside the run's minutes. Then the rebase stops and is aborted, is retried
   once after 20 s, and the step fails with the `::error::` line. The report
   exists only in that run's workspace. D3 kept.
7. **Read 3 expected a real fixture to show the live pair; none does.** The
   spelling rests on cc-291's report. Any other spelling LIS uses stays
   `unknown_cast` and shows up in the record line as `N unknown cast`.
