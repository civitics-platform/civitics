## What contradicted the prompt

- **The management API's counter lags by ~3 h steps, not ≤ a tick (filed
  FIX-1313).** On 10-12 `total_monthly_requests` read:
  - 241,414 on every tick from 16:01Z to 18:31Z;
  - 375,889 from 19:01Z to 21:31Z;
  - 499,669 at 22:01Z.

  Over the same window `daily_net_commands` moved on every tick, from 49,167
  at 16:01Z to 307,388 at 21:01Z. The crawl ran ~57k/hr between 17:00Z and
  18:30Z. Writes stopped at ~20:30Z (cc-229), when the monthly counter still
  read 75 %.

  D1's "≥ 4 h of the worst crawl against a ≤ 30-min probe lag" is therefore
  optimistic. At 57k/hr, 3.5 h of lag is ~200k commands, more than the 150k
  headroom. On 10-12 itself the 19:01Z step would have engaged the hold at a
  true ~389k, with ~110k left, so the design would have held, narrowly. I kept
  D1 as written and filed the fix: hold on an estimate that adds
  `daily_commands` growth, or add a daily trigger.
- **The prompt's "used read 500,001" is the data plane, not the management
  API.** The API never read above 499,774 in the window I checked. The
  500,001 is the refusal's own `Usage:` (cc-220's ring read, and the flag
  `SET` above). The FIX-1089 append says so.
- **FIX-1089's anchor is wrong in code, not only in prose (filed FIX-1314).**
  `platform-snapshot.ts` builds `cycles.upstash` with
  `anniversaryCycle(creation_time)`, which rolls on the 13th. Two readings
  contradict it: the only observed reset was 09-01T00:01:16Z, and 10-13 07:51Z
  passed with used 499,693. So the card answers "when does the limiter come
  back" ~12 days late.

  That is two filings against §7's "Files: none" plus one conditional. The
  FIX-1089 bullet is archived (`docs/archive/fixes-archive.md`), where an
  append is not actionable, so the code defect got its own open bullet. The
  FIX-1089 append went into the archive file, because that is where the
  bullet lives.
- **The 200-call rule degenerates under a hold, as specified.** D3 counts
  "Upstash-spending limiter calls". A held instance spends nothing, so its
  count would never reach 200 and it would never see the flag DELeted. It
  would stay in memory for its lifetime, past the reset. Calls served from
  the hold therefore count toward the 200 too. The rule otherwise stands as
  written: both gates, and a cold read before the first `limit()`.

  I added **single-flight**: a cold burst shares one in-flight GET (test (f):
  20 concurrent cold calls, 1 GET). Without it, a cold isolate taking a burst
  issues one GET per concurrent request.
- **State precedence: D4 and Item 2 disagree at one cell.** D4 says
  `budget_hold` is recorded "when … the PINGs say healthy". Item 2's table
  puts `budget_hold` above `unreachable`. I implemented the table, and it is
  pinned in the table test.

  Two consequences of the table:
  - A non-quota flag-write failure does not change the state; its error rides
    in `budget.flag_error` and the `budget_hold` detail.
  - **`budget_hold` counts as `limiter_degraded = 1`.** The existing
    critical-threshold alert will therefore email at the 70 % hold, not only
    at exhaustion. I left it that way because the limiter IS on memory while
    it holds, and an early alarm is what FIX-1038 wanted. Say if you'd rather
    it were quiet.
- **TTL.** 2 h is rewritten every 30 min, so the hold survives three missed
  ticks and lapses on the fourth. That matches D2. Nothing contradicted it.
- **Edge module state.** `getLimiterHealth()` cannot be read from outside an
  isolate, so I could not measure the GET rate directly. The logs give an
  indirect reading: over 02:31–03:04Z, four cold-read lines in four regions,
  each the instance's first error.

  If module state did not persist, every bucketed request would be a cold
  instance that logs its own "1 on this instance" line. At cc-229's measured
  baseline of ~140 limiter commands per 30 min, that would be dozens of lines,
  not four. Module state persists. The 200-call rule does not degenerate on
  that account, and the GET rate is about one per instance start plus one per
  200 calls.

  Vercel reports the middleware's `runtime` as `nodejs24.x` in these log
  records, not `edge`. `budget_reads` in `getLimiterHealth()` is the
  per-instance count, for whenever that object gets a reader.

  touch", but Items 1 and 4 and §7 edit `docs/FIXES.md` and the playbook,
  which those branches also edit.
  - FIXES.md is the shared append ledger, and §7 asks for appends to it, so I
