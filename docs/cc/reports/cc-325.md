## Decisions that changed, and why

- **D2 (b) loads proposals differently from the prompt's text.** Plain (b) came out *over* the old body for one clone official (4,657 vs 4,166), because the cost depends on how often bills repeat among the 500 rows. The real cost driver is not `spending` but the `bill_details` scalar subplan, which ran once per vote: 2,000 of `all_votes`' 3,722 buffers.
  - Both vote lists now load each proposal in a `LEFT JOIN LATERAL (… OFFSET 0)`. Memoize then caches the proposal together with its `bill_number` (195 hits and 307 misses on 502 rows).
  - The payload is unchanged: (b) and the built body returned equal jsonb for 30 of 30 officials, and every other key is byte-identical.
  - Without this, step 4 would have been a coin flip.
- **`all_votes` also gains `voted_at`** (D3 named `roll_call_id`, the question, the chamber and the class). The page uses it to tell the new ordered rows from the old unordered ones. Against the old body the caption reads "A sample of 500 votes", never "Last". The test uses it to check the order.
- **Read 5 deviated.** The prompt asked for an individual in the top thousand by `total_donated_cents`. No index covers individuals; on the clone that query is a 3.45M-row seq scan of 180K buffers and 4.3 s, which I would not run on prod. I took Schiff's rank-18 individual from `official_donor_rollup_mv` instead, which cost 13 buffers on the clone. That donor gave $520,123, but I did not check whether that is in the top thousand.
- **The step-4 STOP row** was ambiguous with two readings each. I ran a read-only A/B and Craig ruled proceed (above).
- **The wording module covers shape (b) and the old body only.** Shape (a)'s wording was not built, because shape (a) was not built.
- **D4.** The roll's question now sits on the row, so `VotesTab`'s expander holds only "View proposal →". An expanded "Question:" would repeat the row.

## What contradicted the prompt

- "Latest body in fix665": the body is in `20260621060000_fix646`. fix665 and fix1128 only set and reset an inert `statement_timeout`.
- "Removing `spending` is the credit (a) spends": the credit is 52 buffers on the clone, about 2 % of the ~2,100–2,550 buffers that (a)'s full pass needs. (a) could never have paid for itself from it.
- Two function-level runs on prod cannot carry a STOP rule. The old body's own pair spread 8,051 → 5,577, because each `db-query` is a fresh connection whose catalog and planning load lands in the function's buffers. Running both bodies in one session is the comparison that holds still.
- **The new body is slower in wall time while reading fewer buffers.**
  - Warm: 18 → 37 ms at the function level, and 14 → 23 ms in the A/B. That is `vote_roll_class` (a regex and a lowercase/normalise) on 600 rows, plus the extra jsonb.

  - Both are well inside anon's 3 s and the page's 5 s cap. I did not file this as a FIX; it is an observation for the next whale-page census.
