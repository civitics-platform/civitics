## 3. Item 3 — the procedure's new shape, and D2's proofs

The migration is `20260920100000_fix1212_donor_party_full_rebuild_windowed.sql`.
The full and bootstrap branch now runs **sixteen donor-id windows**. Each one:

1. `EXECUTE format(…)` builds `CREATE TEMP TABLE dpr_stage_w`, with literal
   bounds on **`fr.from_id`, `et.entity_id` and `fe.id`**.
2. `DELETE` the window from the MV, then `INSERT` from the stage.
3. `DROP` the stage.
4. Upsert the cursor with `windows_done || i`.
5. Update the local arrays last, since PL/pgSQL variables are not rolled back.
6. `COMMIT`.

The rest of the design:
- **Budget guard:** before every window after the first, stop cleanly if
  `elapsed + longest window this call` would reach `unit_budget_seconds`, or if
  `max_units` windows have run.
- **Completion:** at 16, the watermark goes to the cycle target (never
  backwards), and the cursor is deleted in the same transaction.
- **Mode decision:** a live cursor always wins; one older than 7 days is
  discarded and logged as `cursor_discarded`.
- **Session settings:** `SET max_parallel_workers_per_gather = 0` sits beside
  `SET work_mem = '256MB'`. work_mem stays at 256 MB because no window's
  HashAgg spilled (`Batches: 1`, 30.7 MB).
- **Handlers:** `query_canceled` is named first; `OTHERS` records the failure
  and moves on to the next window.
- **Metadata:** `windows_total`, `windows_done`, `windows_run`,
  `stage_seconds[]`, `apply_seconds[]`, `resumed`, `cycle_started_at`,
  `cycle_target`.
- The FIX-1112 "cost is independent of the lag" comment is rewritten.
- No SET clause and no `statement_timeout`; grants restated.

## 7. What contradicted FIX-1212's bullet, cc-145, the FIX-1112 header, or this prompt

1. **The prompt's D3 cannot run as written.** Claiming the session makes the
   procedure's own FIX-950 guard skip the CALL, since `defer = held` whichever
   backend holds the lock. The interlock built to protect supervised runs
   forbids supervised runs of every guarded procedure. That is FIX-1213; it
   never came up before because no cc run had CALLed a guarded procedure under
   a claim.
2. **The prompt's D1(b) shape, windowing only `fr.from_id`, still builds the
   whole-table memory peak in every window.** The planner Seq Scans all of
   financial_entities into a 305,720 kB hash per window (variant A). The prompt
   assumed the `ind` and `fe` joins "are per-donor and shrink with it"; they
   don't unless they are bounded explicitly. So the bound is on all three
   sources, which is semantics-preserving because each joins on `donor_id`, and
   the anchor test pins it.
3. **The windowed rebuild buys memory with I/O.** No FR index covers the
   aggregate (it needs `to_id` and `to_type`), so each window touches ~34 % of
   FR's heap, and sixteen windows read ~7× (clone) to ~8× (prod projection) one
   pass. On a box that fails on memory that is the right trade. It is not free,
   though, and nothing in FIX-1212's bullet or the prompt said so.
4. **The FIX-1212 bullet's "14.46M rows, 12 GB"** is all of
   financial_relationships (reltuples 14,457,357), not the donations the stage
   aggregates. Those are ~6.2M on prod, estimated from the index size ratio.
5. **The budget guard is stricter than D1(b).** It projects the next window
   from the longest this call has run, so a CALL stops *at* its budget rather
   than up to one window past it; under a pg_cron firing the 1,800 s watchdog
   would otherwise axe a window started at 1,499 s. `max_units` also caps
   windows per call, which is what made D2 (ii) testable under the 60 s budget
   floor.
6. **The FIX-1112 header.** "Cost is independent of the lag: ~350–420 s … the
   next firing redoes the same ~350 s" was false at scale: 21,628.6 s and
   11,278 s, with nothing banked. The lag only picks the mode; cost scales with
   FR and FE. Corrected in the new body.
7. **cc-145 §3d / the FIX-1208 bullet's "against it"** (platform-snapshot's
   RPCs reach the gateway, so caching isn't proven): explained, not
   contradicted. platform-snapshot does a `no-store` fetch first
   (`supabase-prometheus.ts:629`), which flips the route's `revalidate` to 0
   before its RPC. Next's docs claim `force-dynamic` equals
   `fetchCache = 'force-no-store'`, and that is false for a GET Route Handler in
   14.2.35. The stale-chord memory from FIX-878 attributed its staleness to a
   sibling's `revalidate`; this mechanism alone would explain it.
8. **The prompt's posture** listed `session:claim-prod … --minutes 90` as a
   sanctioned write. It was never used.
