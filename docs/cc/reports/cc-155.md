## 2. D2 — the endpoint, probe by probe (the durable record)

The full table, with the SQL for every call, is in
`docs/audits/2026-09-25-fix1219-logs-endpoint-port.md` §2. The schema map is
in the helper's header. What follows is the map and the probes that decided
each line.

**Schema map (as measured, 2026-09-25 01:35–01:55 UTC):**
- **Table.** `logs` has these columns:
  - `id` UUID;
  - `timestamp` DateTime64(9);
  - `source` String;
  - `event_message` String;
  - `log_attributes` Map(String, String);
  - `project`;
  - `severity_text`.

  `SELECT *` and `DESCRIBE TABLE logs` both answer "Backend error!". Unknown columns answer `Field "x" does not exist.` (`source_name`, `metadata`, `body`).
- **Sources seen:** edge_logs, postgres_logs, postgrest_logs, supavisor_logs.
- **Edge keys:**
  - `response.status_code`, a string such as "200" or "500";
  - `request.method`, `request.path`, `request.search`, `request.url`;
  - `request.headers.user_agent`, which is `node` on a Vercel render;
  - `request.headers.x_client_info`, `response.origin_time`.
- **Postgres keys:** `parsed.sql_state_code`, `parsed.query`, `parsed.application_name`, `parsed.user_name` (still `authenticator`), `parsed.backend_type`, `parsed.command_tag`, `parsed.database_name`, `parsed.connection_from`, `parsed.error_severity`, `parsed.session_id`, `parsed.timestamp`.
- **Values:** every value is a String, and a missing key reads `''`, not NULL.
- **Timestamp unit:**
  - it comes back as a naive UTC ISO string with microseconds, `"2026-09-24T09:30:26.262000"`;
  - a raw `toStartOfInterval` comes back as `"2026-09-24T08:30:00"`;
  - `toUnixTimestamp(...)` comes back as epoch **seconds**, a JSON number (`1790238600`);
  - the builders return seconds, and the helper returns ms. The old endpoint returned µs.
- **Time-range mechanism:**
  - The query string is **required**: the range only in SQL, with no query string, gives "Backend error!".
  - It is honoured to the **sub-second**, not to the minute. Start 09:15:08 excluded a row at 09:15:07.861, and end 09:29:55 excluded one at 09:29:55.368.
  - The **end is inclusive**: an end of 09:29:55.368 kept the 09:29:55.368 row.
  - So the helper sends the range in the query string (widened to whole minutes when that stays ≤ 24 h) **and** a half-open SQL bound `timestamp >= toDateTime64(start,3,'UTC') AND timestamp < toDateTime64(end,3,'UTC')`. The `TIME_FILTER` token is filled by `queryLogs` and never by a caller.
- **Max window: 24 h, silently clamped to the OLDEST 24 h**, exactly as the old endpoint did (rule 147 re-measured):

  | Request | Hourly rows | First row |
  |---|---|---|
  | 24 h | 24 | 09-23 00:00 |
  | 25 h | 24 | 09-22 23:00 |
  | 48 h | 18 | 09-22 00:00 |
  | 7 d | 24 | 09-18 03:00 |

  - The 48 h answer is 18 rows because it holds the cc-145 postgres_logs dark hole.
  - `MAX_ATTRIBUTION_MINUTES` stays 1440 (now the helper's `MAX_LOGS_RANGE_MINUTES`). The helper refuses to send a longer range, and the census refuses it in **both** modes.
- **Row cap: 1000, silent.** `LIMIT 5000` over 6 h of edge rows returned 1000; no LIMIT over 1 h returned all 966. The helper treats an answer of 1000 rows as dark.
- **Rate limit: 10 requests / 60 s per token.** The headers are `x-ratelimit-limit: 10` and `retry-after: <s>`. My probing hit it once, on the 11th call inside about 5 min. It reset after 47 s.
- **Wall:**
  - 0.4–2.4 s for a 15–60 min read;
  - 7.7–9.8 s for 24 h of hourly postgres buckets;
  - 8.3–11.7 s for the 1440-min attributions. The old endpoint timed out twice at 20 s.

**The builders' ClickHouse text:**

```sql
-- sqlEdgeBuckets(900) — the route (4 closed buckets) and the census edge half

  toUnixTimestamp(toStartOfInterval(timestamp, INTERVAL 900 SECOND)) AS b,
  count() AS requests,
  countIf(toInt32OrZero(log_attributes['response.status_code']) >= 500) AS n_5xx,
  countIf(toInt32OrZero(log_attributes['response.status_code']) BETWEEN 520 AND 526) AS n_52x

-- sqlCancellationBuckets()
SELECT
  toUnixTimestamp(toStartOfInterval(timestamp, INTERVAL 60 SECOND)) AS b,
  countIf(event_message LIKE '%canceling statement due to statement timeout%') AS n_timeout,
  countIf(event_message LIKE '%canceling statement due to user request%') AS n_user
FROM logs
WHERE source = 'postgres_logs'
  AND event_message LIKE '%canceling statement due to%'
  AND {{time_filter}}
GROUP BY b
ORDER BY b

-- sqlAttribution('query', null)
SELECT
  if(extract(log_attributes['parsed.query'], '"public"[.]"([a-z0-9_]+)"') != '',
```

## 6. What contradicted the design or this prompt

1. **The filter column is `source`, not `source_name`.** The changelog, the
   FIX-1219 bullet and this prompt all say `source_name`. That column does not
   exist, and the API reference's `source` is right. cc-152's "source_name does
   not exist" was the endpoint telling the truth.
2. **"Rounded to the nearest minute" is not what the endpoint does.** It honours
   the range to the sub-second, and its **end is inclusive**. Left alone, a row
   on a 15-min boundary would be counted in two adjacent windows. The helper
   bounds the SQL half-open, and the query-string range is still required (D1's
   "else interpolated into the SQL" turned out to be *both*, not either).
3. **The 24-hour clamp survived the migration unchanged.** The endpoint answers
   the oldest 24 h, silently, over 25 h / 48 h / 7 d. It did not start honouring
   long windows. The slicer is left as it was (out of scope). The refusal now
   also covers **gate mode**, which could have read the oldest day under a
   `--minutes` over 1440. That is the one CLI change.
4. **There is a rate limit, and the two consumers share it:** 10 requests / 60 s
   per token. My own probing hit it once. The route makes 1 call per 15 min and
   the census 2 per reading, so steady state is far inside it. A burst of hand
   reads within the minute of a route firing would blind that tick
   (`corroborator_unavailable`, `dark (Logs API 429 …)`), which is honest but
   avoidable. Candidate rule: pace hand Logs reads, and keep them clear of
   :00/:15/:30/:45 +0–1 min.
5. **The row cap is 1000, not "~100".** The route's old comment read its
   2026-09-04 measurement (a 280-bucket range returning 93 rows over the newest
   ~24 h) as a row cap. It was the 24 h clamp. The real cap is 1000 and silent.
   The cancellation builder now keeps only cancellation rows (the old query
   returned one 0/0 row per minute). Every consumer already read only non-zero
   minutes, and this keeps a 1440-min gate read under the cap.
