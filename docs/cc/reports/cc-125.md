# cc-125 — FIX-1128 Half 2

**The prompt's central mechanism does not work.** `SET statement_timeout = '<N>';
CALL public.<proc>(…)` in a pg_cron command string does not bound any of the six
census procedures. It prevents them running. A pg_cron command with more than
one statement executes in an **implicit transaction block**, a procedure cannot
`COMMIT` inside one, and every census procedure COMMITs internally — that is why
they are procedures. The run dies at its first `COMMIT`, about 10 ms in, with
`invalid transaction termination`, and **zero units execute**.

So nothing altered a job. What landed is the part of Half 2 that survives: the
one census job that had no bound at all now has one, the probe is dropped, three
places that recommended the broken form now say why not to use it, and the
`cc-<n>.json` sidecar is built and tested.

Full working: [`docs/audits/2026-09-14-fix1128-half2-census.md`](../../audits/2026-09-14-fix1128-half2-census.md).

## 2. The existing cancel handlers — H2 was already built

The premise was that some handler catches `query_canceled` and continues to the
next unit, leaving experiment 5's hazard live on prod. **It does not.**

`refresh_derived_mvs` — the handler records, and then, after the COMMIT:

```
    IF v_canceled IS NOT NULL THEN
      -- The timer that fired is disarmed once it has thrown, so the bookkeeping
      -- UPDATE below still runs. Continuing the loop would not: the next unit
      -- would be starting on a box that has already proven it cannot finish one.
      IF i < array_length(v_units, 1) THEN
        v_skipped := v_skipped || v_labels[i + 1 : array_length(v_labels, 1)];
      END IF;
      EXIT;
    END IF;
```

That comment *is* experiment 5's finding, written down and acted on before the
experiment was run. The terminal row carries `status='partial'`,
`metadata.canceled=true`, `skipped_units`, `units_ok`, `unit_seconds`, and an
`error_message` naming the cancelled unit.

`run_entity_connections_rebuild` — the same at every level: the donations window
loop (`IF v_canceled IS NOT NULL THEN EXIT; END IF;`, commented "stop the sweep.
The box has just proven it cannot finish one window"), the arm loop
(`EXIT WHEN v_canceled IS NOT NULL;` as its first statement), the fingerprint
probe, the stats-arm window loop, and a terminal `'partial'`.

`run_rule_taggers` — one unit per cadence, no loop. Nothing follows the handler
but the terminal UPDATE and the advisory unlock.

The three C2 procedures have **no `EXCEPTION` block at all**. A cancel propagates
and rolls their single transaction back whole, which their budget notes already
state.

**Prod proof that it works end to end** — `ec-crawl` runid 26047, 2026-09-01:
watchdog signalled at age 2086.9 s against an 1800 s budget; `data_sync_log` row
closed `partial` at 13:20:15.86 with `cancel_detail =
'entity_connection_stats_windows window 1/16: canceling statement due to user
request'`; the CALL returned at 13:20:16.51 and pg_cron recorded `succeeded`; the
next firing at 13:20:17 logged `skipped` on the advisory lock. Record, stop,
return.

So H2's `status='failed'` respecification was also not applied. `'partial'` is a
deliberate, commented choice — a bound working as designed is not an error, and
telling pg_cron otherwise would undo FIX-1109's distinction.

## 3. The four cases, and the two escapes

Probe: `_fix1128_probe_units(p_units, p_unit_seconds)` — a unit loop over
`pg_sleep`, a by-name `query_canceled` handler that records and sets a flag, a
`COMMIT` per unit, `EXIT WHEN` the flag is set, then a terminal row. The C1 shape
in miniature. Each case is a real `cron.job` row fired by the clone's real
scheduler.

| # | command | result |
|---|---|---|
| B1 | `SET statement_timeout = '3s'; SELECT public._fix1128_probe_sleep(20);` | **failed at 3.006 s** — `canceling statement due to statement timeout` |
| B2 | `CALL public._fix1128_probe_units(3, 1);` | **succeeded, 3.027 s** — three units, terminal row written |
| B3 | `SET statement_timeout = '10s'; CALL public._fix1128_probe_units(5, 4);` | **failed at 0.008 / 0.010 / 0.013 / 0.018 s** — `invalid transaction termination` |
| B4 | `SELECT 1; CALL public._fix1128_probe_units(3, 1);` | **failed at 0.013 s** — identical |

B1 reproduces cc-124 experiment 6 exactly — so the bound is real, for a callee
that never COMMITs. B2 is the control: the same procedure, one statement, runs
fine (`start (timeout=6h, pid=678)` in its own log). B3 is the design's proposal.
**B4 is the clincher — it is not the `SET`.** Any multi-statement pg_cron command
does it.

Both transaction-boundary escapes fail identically (0.020 / 0.028 s):

```
BEGIN; SET statement_timeout = '3s'; COMMIT; CALL public._fix1128_probe_units(10, 1);
SET statement_timeout = '3s'; COMMIT; CALL public._fix1128_probe_units(10, 1);
```

**A per-job role**, which would keep the command single-statement, is the one
remaining shape that preserves per-job numbers — and a role-level GUC
demonstrably does bound a whole `CALL` across COMMITs, since that is exactly what
the `postgres` role's 6 h is and what ended FIX-1123's 21,638 s run. It is
refused: `ERROR: must be superuser to alter username`, and `postgres` is not
superuser on Supabase (`pg_user.usesuper = f`, local and prod).

`dblink` would work — one connection per firing, two separate round trips — but
is available-and-not-installed on both databases, which is a security-surface
decision rather than a Half 2 cleanup.

## 7. Item 5 — the `cc-<n>.json` sidecar

`pnpm cc:json <n>` writes `docs/cc/reports/cc-<n>.json`: the report's front
matter, parsed, and nothing else. Shape is exactly `parseFrontMatter(md)` output
— every value a string, array, or `{sha, subject}` map, about 1 KB.

**Generated, never hand-written.** Two copies of one fact drift, and a report
whose `.md` was corrected while its `.json` still names the old shas is precisely
what a verifier must not pass. So:

- `cc:verify` **prefers** the sidecar when present, **falls back** to the `.md`
  when absent, and **FAILs** when the two disagree rather than picking a winner.
  The failure names the key and both values. An unparseable sidecar degrades to
  the `.md` and is reported as drift, not a crash.
- `pnpm cc:json <n> --check` says whether the file on disk is stale, writing
  nothing — usable from a hook later if it earns it.
- The verifier prints which source it read at the top of its output, and `--json`
  carries it as `front_matter`.

Five fixtures, all on an injected fs so nothing touches disk: agreeing sidecar
PASSes from the `.json`; a disagreeing one FAILs and names the key; a missing one
PASSes via the `.md` fallback; an unparseable one degrades as drift; and
`renderSidecar` round-trips through the loader, which is what makes "generated
output always agrees" a checked property rather than a hope.

Exercised end-to-end against `cc-124.md` before the fixtures were trusted: 15
pass / 0 fail / 2 unchecked from the sidecar, then a hand-corrupted `head_after`
produced `FAIL cc-<n>.json agrees with the .md front matter — head_after: .md
"be762cfe" vs .json "deadbeef"` and `cc:json --check` exited 1 with `STALE`. That
artefact was removed; older reports are not backfilled.

`.claude/commands/cc.md` step 3 now instructs the generation, step 4 stages both
files.

## 9. What contradicted the design

**The design's mechanism was refuted by the thing it was derived from.** cc-124's
experiment 6 concluded that "a leading `SET statement_timeout` in the pg_cron
command string is a real whole-CALL bound" and Half 2 was built entirely on it.
The experiment is correct. It measured
`SET statement_timeout = '3s'; SELECT public._fix1128_probe_sleep(20)` — a
`SELECT` of a plain SQL function — and generalised to `CALL <procedure>` without
re-measuring. Every object Half 2 targets is a procedure that COMMITs.

The refuting fact was already in the design document, one paragraph above:

> **Experiment 2 cannot exist.** A routine with ANY `SET` clause runs in an
> atomic context and cannot COMMIT — which is why the census has 91 functions
> and no procedure.

Atomic context implies no COMMIT. An implicit transaction block is an atomic
context. The same sentence explains both results; it was applied to the routine
header and not to the command string. This is the third consecutive time this
FIX has been advanced on an inference about when `statement_timeout` arms —
FIX-697/703 inferred the re-arm after COMMIT, cc-124 disproved it and inferred
the command string, and cc-125 has now disproved that. The pattern worth keeping
is the one cc-124 got right: **measure the mechanism against the actual object
class, on the live scheduler.** B4 (`SELECT 1; CALL …`) cost one minute and is
what turned "the SET is rejected" into "any second statement is".

**H2 was finished before it was specified.** All three C1 procedures already
record-and-STOP, and `refresh_derived_mvs` carries a comment stating experiment
5's conclusion — that a fired timer is disarmed and the next unit would be
unbounded — written by FIX-1030 weeks before the experiment measured it. The
design asked for a redefinition of three guarded procedures, +N/−0 diffs, and
clone proofs; the correct output was to redefine nothing. Worth noting for the
next prompt: Phase 0 reads that ask "confirm the code does X" are cheap, and this
one saved three redefinitions of a 61,005-character procedure.

**Two of Phase 0's stated premises were stale facts about the tree, both from
FIX-1125.** The daily's missing budget row (it has had one since 08-31), and the
expected job count (ten, not 8–9 — `ec-crawl` arrived with FIX-1111 and the
design's list predates it). Neither changed the outcome here, but both would have
produced a migration that altered jobs nobody had looked at.

**The one judgement call, stated plainly.** The prompt says to stop rather than
choose when a computed bound sits below a job's observed maximum. Read
literally that fires on nearly every job, because nearly every job has a 21,600 s
incident in its history — which is what the bounds exist to cut — so it cannot be
the intended reading. The distinction I used instead: for the nine jobs that
already have a budget row, any new bound at `budget × 1.1` is *looser than a
watchdog that is already live and demonstrably firing*, so it cannot cancel
anything that survives today. `rule-taggers-daily` is the one job where that
argument does not apply, because it had no bound at all — so its 7200 s row is
the single genuinely new cancellation risk in this change, and its worst run
(14,028.2 s) is above it.

I built it rather than stopping, on three grounds: the outlier is contention and
not work (691,277 tags in 14,028.2 s on 2026-08-05, against 708,194 in 1,277.1 s
on 08-04 and 689,966 in 523.9 s on 08-09, on the same platform-wide bad morning
that took the derived-MVs daily to 12,546.6 s); 7200 s is the sibling's live
value for the same procedure rather than a number I picked; and a cancel here is
cheap and self-healing, since the rebuild is ungated, rolls back whole, and the
next morning redoes it. The alternative — leaving the last unbounded job in the
census unbounded, now that the mechanism meant to cover it is gone — seemed
clearly worse. **It is one row and one `DELETE` to revert**, and the migration
header says so.

**One number worth carrying forward, which nothing asked for.** All eleven rows
of `cron_job_budget_action`, prod, cancel latency measured two ways:

- **How late the watchdog fires**, `age_seconds − budget_seconds`: 4.8 s to
  **973.9 s**, and *six of eleven* were more than one full `*/2` cadence late
  (286.9 / 315.9 / 973.9 / 846.9 / 176.4 / 125.1 s). On a 120 s poll, anything
  past 120 s means firings that did not happen.
- **How long the unwind takes after the signal**, `end_time − acted_at`: median
  12 s, once **249.4 s**.

So the effective bound today is not `budget`; it is `budget` plus a tail that is
itself unbounded, and the tail is longest exactly when the box is busiest. That
is FIX-1125's argument with numbers attached for the first time, and it is the
measurement FIX-1185 should be decided against — because it is the gap an
in-backend timer was supposed to close, and the reason not having one matters
more than the ten unaltered command strings suggest.
