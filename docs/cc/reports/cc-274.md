## Decisions changed and why

1. **The current session is walked first.** D2 is per session, but the sessions
   loop ran 1 then 2. On a night with an empty record, session 1's ~122 gaps
   would spend the allowance before session 2's tail, which is where new rolls
   are. Fri 11-13 is exactly that night. The loop now sorts by year descending,
   Senate only.
   - Side effect: within one run, a vote-minted bill first seen in session 2
     takes its placeholder `introducedAt` from that roll. Vote-minted bills are
     rare. The House order is unchanged.
2. **D3 is stricter.** A tail closes only when pass A ended past the end with no
   blocked or transient roll in it (`tail.unsure === 0`). A blocked roll 660
   followed by three non-rolls would otherwise close session 1 and lose roll 660
   for good: it sits above the frontier, so pass B never covers it.
3. **A version bump drops the whole record**, not only the parser-reason
   entries, so the `tail_closed` flags go with it. If seen rolls hold a frontier
   up, emptying them under a closed tail would orphan the rolls between the
   stored frontier and the old one.
4. **A new `recheck` option on `probeSessionRolls`**, beyond the prompt's list.
   A lapsed guard-absent roll leaves `seen`, yet it must still hold the frontier
   up and be fetched in pass B. Without this, a lapsed roll at the top of a
   closed session would never be fetched again.
5. **The reason vocabulary is split.** "no proposal reference" in the log covers
   two cases. A null bill key is the parser's case, kept as
   `no_proposal_reference`. A key that resolved to nothing is a failed resolve,
   recorded as `bill_unresolved` and retried. `no_matchable_records` is also
   retried, since a member-map fix can change it.
6. **`seen_at` is the last date the roll was fetched and found unstored.** A
   re-fetched roll gets today's date. I read "seen_at kept on an unchanged roll"
   as "a roll not fetched this run". Otherwise a guard-absent roll would be
   fetched every night once it passed day 7, instead of once a week.
7. **A run whose read failed still writes**, merging from an empty record. With
   nothing skipped, that night fetches every unstored roll, so the rebuilt
   record is complete apart from rolls a block stopped it reaching.
8. **Pacing is per walk.** `paceMs` never sleeps before a walk's first GET, so
   the boundary between the session 2 and session 1 walks is one unpaced gap a
   night. It disappears once session 1 is closed and filled (0 GETs).
9. **In pass B, a 404 counts as a miss** (`HTTP 404`). It is a hole in the
   session, not its end.
