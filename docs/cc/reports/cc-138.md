### FIX-1201's sites, and where cc-132 §9g was wrong about the tree

### The design deviation I made in FIX-1201, and why

D1 says the four callers "read `owners` once (they already do for
`printTailTable` — pass the same map)". **They cannot, on the paths that
matter.** `main()` reads the owners at line 2130 of
`merge-same-person-official-dupes.ts`, but `runVacuum` is called at 1760,
1766, 1800 and 1803 on other branches — earlier than the read — as well as at
2687/2692 after it. Threading an optional `owners` parameter would have meant
touching ~20 call sites, most of which would only pass it through, and would
still have left the early branches with nothing to pass.

So I added `readOwnerSchedulesOnce(client)` — `readOwnerSchedules` memoised per
client in a `WeakMap`, caching the *promise* so two concurrent callers share
one query, and dropping the entry on rejection so a failed read degrades the
banner to `?` rather than failing a remediation run. `printDeferredTail(kind,
owners?)` keeps D1's exact signature and stays a pure function of its
arguments, which is what makes it testable with stubbed rows. All five call
sites that previously used `readOwnerSchedules` now use the memoised one, so
it really is one `cron.job` query per run.

### The trunk-reachability predicate (FIX-1200)

**Chosen: `git rev-parse --is-shallow-repository`.** Not "`rev-list --count
origin/main` ≥ the oldest done.log SHA's distance".

The count test needs the history it is trying to prove it has. In the failing
shape `rev-list --count origin/main` is **1**, so any distance derived from it
is not merely small — it is meaningless. And the case the count test would
genuinely cover (trunk truncated *before* that SHA, so the object is absent)
is already covered by the per-SHA `cat-file -e` escape, which I kept for the
non-shallow path. `--is-shallow-repository` is one cheap call that answers the
actual question, and it cannot be fooled by a deep sibling fetch — which is
precisely the shape that caused the bug.

The predicate is computed **once per run** (memoised, with a `_reset` test
seam) and prints one line:
`[fixes-sync] trunk not judgeable here (shallow clone) — ancestry skipped, drift still checked`.

### The repro test, and two harness bugs it exposed

The fixture had to be cc-136's exact shape, and getting there surfaced two
ways the harness had been lying:

1. **`git clone --depth` is silently ignored for a local-path source.** Git
   hardlinks the object store instead. The first version of the fixture was a
   *full* clone wearing a shallow label, and four assertions passed vacuously.
   It needs a `file://` URL — with **three** slashes on Windows, because
   `file://C:/x` parses `C:` as a host.
2. **A `--depth` deeper than the whole history un-shallows the repo.** The
   prompt's `--depth 11` against a four-commit fixture made git decide the
   repository was complete and delete `.git/shallow`. The sibling now branches
   from `HEAD~2` and is fetched at `--depth 2`.
3. **`runScript` threw stderr away on a *successful* run.** `execFileSync`
   returns stdout and discards stderr unless the process throws, so a warning
   printed by a script that exits 0 was invisible to every assertion — which
   is exactly the shape of FIX-1200's "say why, once" line. Swapped to
   `spawnSync`.

The test asserts **both halves** of the trap — the clone really is shallow and
`origin/main` really is one commit, *and* an on-trunk SHA's object really is
present — because without the second, the case would pass against the old code
via the `cat-file` escape. Paired with the inverse: a full clone with a real
off-trunk SHA (the sibling tip) must still accuse, and does.

## 2. Item 3 — the two halves, the proconfig decision, the local reading

`run_rule_taggers`'s prod body was pulled with `pg_get_functiondef` and
**diffed byte-identical** to `20260911000200:1612–1759` (only a trailing
newline differed). Neither later migration that mentions the procedure
(`20260914000000`, `20260916000000`) redefines it. **The STOP condition did
not fire.**

Both rebuild functions are clean `DELETE` + `INSERT … SELECT` shapes, so both
split:

| function | DELETE half | INSERT half |
|---|---|---|
| `rebuild_pre_vote_timing_tags` | `search_path` only | `search_path` + `enable_hashjoin=off` + `enable_mergejoin=off` |
| `rebuild_financial_entity_size_tags` | `search_path` only | `search_path` only |

**The proconfig decision.** The planner GUCs went to the INSERT half only.
They exist for the correlated `EXISTS` over `votes` — the only join in either
half. The DELETE is `DELETE FROM entity_tags WHERE entity_type = … AND
generated_by = … AND tag_category = …`: three equality predicates on one table
and no join at all, so `enable_hashjoin`/`enable_mergejoin` cannot change its
plan. Giving it GUCs it cannot use would be noise that reads as meaningful.
Size-tags gained none because the original had none.

Each original name is kept as a two-line wrapper calling both halves, so
`heavy-rebuild.ts`, the FIX-1028 sweeps and `database.ts` are untouched and
keep their exact contract including the return value (still the INSERT's
`ROW_COUNT`). The procedure calls the halves directly **inside the same
transaction, no COMMIT between** — atomicity is exactly what it was. No `SET`
clause was added to the procedure; `pg_proc.proconfig` for `run_rule_taggers`
on prod reads `(none)`, so it can still COMMIT.

`EXECUTE` is revoked from `PUBLIC`/`anon`/`authenticated` and granted to
`service_role` on all four new functions, matching the FIX-834 posture the
originals carry. Verified on prod after the push: all eight functions read
`{postgres=X/postgres,service_role=X/postgres}`.

**The local reading** — `CALL public.run_rule_taggers('daily')` on the clone:

```
NOTICE:  [rule-taggers] pre-vote timing — rebuilt (720256 tags, phases={"delete": 7.5, "insert": 124.3})

 status  | rows_inserted | metadata
----------+---------------+------------------------------
 complete |        720256 | "phase_seconds": {
          |               |     "delete": 7.5,
          |               |     "insert": 124.3
          |               | },
          |               | "elapsed_seconds": 132
```

**The INSERT is 94.3 % of the run.** That is the number FIX-1178 (a) needed:
the temp-table restructure should aim at the `INSERT … SELECT`, not at the
authoritative clear.

One deviation from D3's letter: `phase_seconds` values are seconds to **one
decimal** (`round(…::numeric, 1)`) rather than `arm_timings`' `::int`. The
shape is the sibling's — a flat jsonb object keyed by phase name — but an
integer would report `0` for both halves on a clone whose delete is 7.5 s and
whose sub-second cases are the ones you most want to see. Stated here rather
than buried.

The stamp is **absent, not null**, when nothing was timed (the gated weekly
branch skipping as `skipped_unchanged`), and degrades to `{"delete": n}` if a
cancel lands mid-INSERT — PL/pgSQL variable assignments are not transactional,
so the half that completed is still reported.

39.7 % of its buffers in the same run is what makes that trade payable now; it
