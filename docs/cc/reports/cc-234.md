## D-d as built: a wrapper, not the role

`ALTER ROLE postgres SET civitics.donor_rollup_latest_start_hour = '24'` fails
on Supabase with `permission denied to set parameter`. Measured on the clone
(PG 17.6, postgres `rolsuper f`) for all three forms. On prod,
`has_parameter_privilege(... 'SET') = f`, and
`supautils.privileged_role_allowed_configs` does not list `civitics.*`.

Craig chose the wrapper:
`donor_rollup_rebuild_bulk_dispatched()` does
`set_config('civitics.donor_rollup_latest_start_hour', '24', false)` and then
`CALL public.donor_rollup_rebuild_bulk()`. It has no SET clause and is not
SECURITY DEFINER, and it restores the previous session value afterwards. The
registry's `unit_call` names it.

The prompt had rejected a wrapper as "unmeasured", so it was measured before
writing:

- **Nested CALL + COMMIT** (a probe pair on the clone): the GUC reaches the
  inner procedure before and after its COMMIT (`cfg=24 cutoff=24`), and a
  `SET work_mem` after the COMMIT works.
- **The window proof** (clone, one session, `SET … = '0'`). The bare bulk logs
  `skipped · start window closed — 03:03 UTC is at or past the 0:00 cutoff`.
  The wrapper in the same session runs (`complete`, the caught-up exit). `SHOW`
  then reads `0` again.
- **As a pg_cron one-shot** (the clone's dispatched firing, below): it ran,
  COMMITted and logged.

The wrapper also carries `c_pipeline text := 'donor_rollup_refresh'` and a
`prod_session_state` mention. The `cron-job-pipelines` derivation reads only
the routine a command names, so while a `disp-` one-shot exists it reads
guarded, with its pipeline.

It is narrower than the role GUC would have been: only the dispatched path
loses the window, and a break-glass `CALL donor_rollup_rebuild_bulk()` keeps
it. The revert payload sets `unit_call` back, and there is no RESET.

## What contradicted the prompt / cc-224 / the v1.3 note

1. **D-d's mechanism does not exist on Supabase.** No `civitics.*` default can
   be written by postgres at any scope. The prompt also called it "the FIX-1185
   shape (rolconfig already carries statement_timeout + work_mem)". Those two
   are `IN DATABASE postgres` settings, which `pg_roles.rolconfig` does not
   show. Built as the wrapper (Craig).
2. **The status call was not bounded by the floor.** In 20261015230000's shape
   the NOT EXISTS anti-join sits above the LATERAL. So the LATERAL ran once per
   armed row in `dispatch_log` (14-day retention), and each reaped row scanned
   back to its own old run. The floor bounds only a never-started row. Fixed by
   selecting live rows first (Craig). Prod had 0 armed rows, so tonight would
   have been cheap either way. By E1 it would not have been.
3. **The reap's floored plan is a Bitmap Index Scan, not "Index Scan Backward /
   ~15 buffers".** The floor is an InitPlan, unknown at plan time, so the
   planner prices `runid > $` at the default ⅓ selectivity. On the clone the
   bitmap path beat a Seq Scan by about 13 % on estimated cost (1,664 vs 1,919).
   It reads 11 buffers against 1,039, but that is a near-tie on estimates.
   Watch pgss on the reap's tick: 88 ms on prod tonight, so it holds for now.
4. **The STOP on `box_is_saturated()`** fires on the default-args reading, which
   includes the watchdog wall that D2 excludes from every dispatcher decision. A
   1.58 s wall 60 s before the run tripped it. The prompt's STOP should read
   `box_is_saturated(p_include_watchdog_wall := false)`, the dispatcher's own
   reading.
5. **D-f's revert sequence cannot complete** ("set pause = true, wait for its
   reaped row"): a paused tick exits at step 2, before the step-3 reap. The
   payload's header gives the working order: pause, wait for the run row to be
   terminal, run the payload, un-pause, and the next tick reaps.
6. **`held N`:** neither claim printed a held or cleared line, so held 0 /
   cleared 0, as predicted.
