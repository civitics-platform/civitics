## FIX-1325 — the snapshot and the check

**The snapshot.** It sits at top-level `job_registry` in
`docs/receipts/<day>.json`. Its shape is
`{snapshot_at, rows: [{job, deadline_rule, unit_shape, priority, cost_class,
cap_mb, exclusion_group, budget_seconds, gates, phase_lock,
by_window_minutes, yield_to, anchor_cadence}]}`.

- It carries every row, sorted by `job` in code-unit order. The database
  collation ignores hyphens, so it would put `ecs-…` before `ec-crawl`.
- `gates` and `yield_to` are arrays.
- A failed read becomes `{not_capturable}`, so it never reads as an empty
  registry.
- The `.md` is byte-identical with or without the snapshot (tested).
- **Local proof.** `pnpm --filter @civitics/data data:receipts:daily` ran
  against the clone and wrote `docs/receipts/local/2026-11-02.json` (ignored)
  with 55 rows, `snapshot_at 2026-11-02T01:55:15.476Z`. The `job_registry`
  query took 2 ms.

**How the check compares the snapshot to the fences.** It reads the newest
`docs/receipts/<day>.json` that carries the snapshot. A newest file whose read
failed is skipped, and the check says so. It then compares each job:

| fence vs live | prints | exit |
|---|---|---|
| `at …` → `by` / `stale_after` / `dead_tuples` | `RETURNED: <job> <fence> → <live> (<migration>)` | green |
| any other column differs, and a migration at or after the fence UPDATEs `public.job_registry`, SETs that column and names the job | `UPDATED: <job> <col> <a> → <b> (<newest such migration>)` | green |
| a column differs and no migration explains it | `live drift: <job> <col> is <b> live, <a> in its fence, and no migration UPDATEs it` | **red** |
| a live row with no fence | `live job_registry row with no fence: <job>` | **red** |
| a fence with no live row | `WARN fence row <job> has no row in the live snapshot` | green (warn) |
| no file carries a snapshot | `no live snapshot yet — … comparing the fences alone` | as before |

Two more behaviours:

- The two older `deadline_rule`-vs-schedule warnings now read the **live**
  rule. A RETURNed row is no longer compared against a stale fence `at`.
- Columns added after the fences are compared with their ADD COLUMN
  defaults: `phase_lock` false, `by_window_minutes` NULL, `yield_to` `{}`,
  `anchor_cadence` NULL.

`--fences-only` keeps the old mode.

## What contradicted the prompt

1. **"Any OTHER column differing … is red" would have made the check red
   on its first real snapshot.** The fences are seeds. Against the clone,
   40 jobs differ from their fence in a non-rule column, and every one of
   them was made by a migration. Most are FIX-1357's 33-row cap
   re-derivation, plus the blackout retirement, the vacuum MOVEs'
   `{prod_session}`, `phase_lock`, `anchor_cadence` and `by_window_minutes`.

   `tests.yml` runs the check on every code push. Main would have gone red
   at the first code push after the 11-03 receipts landed, and the only
   ways to turn it green would be editing applied migrations or deleting
   the check. So red now means **drift no migration explains**. The
   attribution finds an `UPDATE public.job_registry` statement whose SET
   list assigns the column and which names the job. If the statement names
   no job (`WHERE job = r.job` off a VALUES list), it takes every job the
   file names. A hand `UPDATE` on prod is still red.

   The attribution is coarse. A later migration that sets the column for
   the job explains ANY live value, not the specific one it set. It is
   tested both ways: a wrong-job UPDATE stays red.

2. **"A fence with no snapshot row is red" would fail every PR that seeds a
   job.** The snapshot is prod's, a day behind the tree, so the new row is
   absent until the migration is pushed and the next receipts run. It is a
   WARN, like the existing "seeded ahead of its landing" (vi). A live row
   with no fence stays red.

3. **"Four rows now read a non-`at` rule live" (the bullet) → 20 (the
   prompt) → 21 lines.** The prompt's twenty are the dispatched pg_cron
   rows. `nightly` (GHA, N2) is a fence `at` → live `by` too.

4. **The ledger's six hygiene claims:**
   - (a) held, and it is wider than the playbook line: 8 live code sites
     plus the 2 GB claim.
   - (b) held, and the ledger missed three `usaspending-bulk` sites.

   - (d) held, and was worse than stated: holds were set and then cleared

     clone-gated suite.
   - (f) half-held: a cosmetic display path only. The `--dry-run` itself

5. **The census window had already closed when `/cc` started.** The
   prompt's own owed `after` for FIX-1325 (`2026-11-02T01:00Z`) had also
   passed. Both owed entries are restated for the 11-03 receipts and the
