## 8. What contradicted the design

**The tree moved under the manifest while the prompt was being written, and
nothing in the design could have caught it.** cc-129 verified the five against
prod on 2026-09-16 and left them correct. The prompt was written 2026-09-17 PDT.
Between those two facts, a *scheduled nightly job* deleted one of the five
survivors. Read 2h caught it only because the prompt insisted on re-reading the
five at apply time rather than trusting cc-129's verification — that instruction
is the entire reason this run wrote a diagnosis instead of a `PGRST` error or,
worse, a partial apply against a stale manifest.

**The deeper contradiction: a remediation set armed the thing that broke it.**
The design treats set 1 and set 2 as independent applications of one manifest
pair, ordered only because `_manifest` is 1:1. They are not independent. Set 1
changed the *input to a different pipeline* — it retired stub CAND_IDs, which is
precisely the condition `promote-candidates` uses to decide a match is
unambiguous. Set 1 did not merely precede set 2; it reached sideways into the
nightly and caused three deletions, one of which was set 2's own survivor. No
part of the cost table, the tail-deferral machinery, or the drain-and-wait rule
models "what does this landing make some *other* job start doing?" FIX-1074's
convention — a landing owns the derived work its rewrite creates — turns out to
be narrower than it needs to be: this landing's derived work included a
*promotion*, not just rollups and edges.

**A silent data-destroying bug sat behind a comment asserting the opposite.**
`(c.source_ids || e.source_ids)` with a comment saying the candidate's id is
preserved. It has presumably been doing this on every promotion since FIX-248.
Three CAND_IDs are gone from every binding surface with no audit row anywhere;
the only reason they are named in this report is that the local clone predates
tonight. An identity merge that can destroy an identifier should not be able to
do it without writing the loser to `merged_fec_candidate_ids`, and the shape for
that already exists on the same rows.

**Two of the prompt's own preconditions could not be met by any wait.** 2a asks
for a status the crawl arm never reports, and 2c asks for a dead-tuple figure the
vacuum schedule makes unreachable inside the permitted windows. Both were written
from cc-129's post-vacuum snapshot — a genuinely clean moment — and generalised
into a gate. A precondition derived from one good reading needs checking against
the *schedule that produces* such readings, or it silently becomes a rule that
blocks forever.

**cc-129's rehearsal held everywhere it was tested.** The four untouched rows
matched to the row, the interlock behaved, the stale label self-described as dead,
and the 57014 baseline and front-door numbers were exactly as predicted. The
failure was not in anything cc-129 measured — it was in the assumption that a
verified prod read stays true across a nightly.
