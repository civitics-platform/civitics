## What contradicted cc-224 / cc-227 / this prompt

1. **The re-fire cadence.** D-a expected "one every ~2 min until un-park".
   The route re-fires off the newest row of any source, so a `vercel` row
   restarts the 360 s clock. The re-fire cadence while the tick is dead is
   therefore every ~8 min (the first stale even-minute run after each row),
   not every 2. The first-row latency (7 m 23 s) is exactly what the code
   predicts: the route runs at even-minute + ~22 s and needs an age over 360 s.
   If the dispatcher ever relies on the route as its only path, its effective
   tick is ~8 min. M1's `stale_after 12 h` does not care; a crawl with a
   10-min floor would.
2. **The route's log shape.** The re-fire line is `[cron/box-health]
   dispatcher re-fired (<reason>): <decision> <job|-> — <reason>` at `info`.
   The prompt guessed `[dispatcher] re-fire`. The memory line is logged at
   `error` on every run because of the Upstash quota, so filtering on level
   would bury the re-fire line.
3. **The box-health `elapsed_ms` comparison measures nothing about R2.**
   `runBoxHealth()` prints the memory line, and its `elapsed_ms`, before the
   route's `dispatch_log` read. cc-227's 578 → 570 and this run's 603 → 704 are
   both blind to the dispatcher's cost. The route's real added cost is in the
   JSON response's `elapsed_ms`, which is not logged. The
   `box-health:dispatch` timeout line (01:00:30Z) is the one place the
   dispatcher read shows up.
4. **The tick's max.** cc-227's first hour had a 76 ms max. Over 23 h it is
   2.92 s, from one run during the nightly launched 0.94 s late. The mean
   barely moved (32.9 → 35.2 ms).
5. **The status ms is rising** with no cost in the function: 144 at the first
   roll, then 283–659. It is wire and pool time; the function is 0.95 ms
   in-DB. Worth watching, not acting on (D-c).
6. **The canary is red for a held pipeline** (FIX-1315). cc-232 read 3 said
   the hold suppresses the canary's reaction. That is true for freshness and
   false for the FIX-978 rate check.
7. **`pipeline_state.prod_session`** does not exist between claims. A release
   deletes the row, so "unchanged" reads as "absent", not as a stale value.
