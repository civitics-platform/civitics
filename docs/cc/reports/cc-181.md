**Rule** (`proposal_status_advances(from, to)` = TS `statusAdvances`). It advances when `to ≠ from` and any of these holds:
- (a) `rank(to) > rank(from)`;
- (b) `to` is terminal (vetoed, failed, withdrawn, tabled) and `from` is not a higher terminal;
- (c) `from` is failed / withdrawn / tabled and `to` is signed, veto_overridden or enacted. Craig added this one.

A null `to` never advances. SQL and TS agree on all 256 pairs on the clone (0 mismatches, 133 advance). `status-rank.test.ts` parses the migration's CASE and the rule's three IN-lists, so the two copies cannot drift. It also has a "the parser sees a one-arm edit" case and the rule as a 33-row table, plus property checks over the 256 pairs.

**RPC** `proposals_advance_status(p_ids uuid[], p_statuses proposal_status[]) RETURNS TABLE (id, from_status, to_status)`:
- plpgsql, `SECURITY DEFINER`, `SET search_path = public`;
- a cardinality mismatch raises 22023;
- duplicate ids keep the highest rank;
- it takes `FOR UPDATE` row locks and re-evaluates the rule against the locked row.
