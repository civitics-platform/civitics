## What contradicted the design

- **Census names drifted, but not the premise.** The canary's regression type
  is `RateFinding`, not `RateRegression`. `rateRegressions` sits at
  :1747-1748, not :1752-1754, and the `declared` line at :2068-2073. None of
  this changed the design.
- **`push()`'s level vocabulary** is the tier union `"escalate" | "report"`. A
  `report` condition lands in `reportOnly`. It is written to the meta row's
  `conditions`, printed on the `report-only (N)` stdout line, and never fails
  the run. One thing the design did not cover: `sendAlert`'s subject and body
  are still built from the full `rateRegressions`. When some OTHER transition
  sends an email, the demoted pipeline is still listed under "Pipeline
  throughput regressed". Report-tier rollups (`staleRollups`) are treated the
  same way, so it is consistent, but the email does not mark it as demoted. Out
  of scope here; worth a line if FIX-1317 touches the email.
- **compareToBand's detail format.** Test (ii) in the prompt expected `450.0 s
  > 400 s`. `fmtSeconds` appends minutes at ≥ 60 s, so the real string is
  `450.0 s (7m 30s) > 400 s`. The test asserts the real string, because D-c
  says to reuse compareToBand unchanged.
- **The receipts local-run flag.** The command is `pnpm receipts:daily --
  --local` (root) or `pnpm run data:receipts:daily -- --local` (package). A
  LOCAL run without `--out` writes to the gitignored `docs/receipts/local/`
  (FIX-1209). An explicit `--out` also moves the **bands.json lookup** to that
  directory: `resolveReceiptPaths` uses `bandsDir = resolveOutDir(args.outDir)`.
  The first scratch run therefore read every job `no-band`, until bands.json
  was copied in. This is by design ("bands live in the canonical dir, and
  `--out` names it"), but it surprises anyone pointing `--out` at a scratch
  dir.
- **`landed` guards the new queries cleanly on the clone.**
  `get_dispatcher_status()` and `dispatch_log` are both present there. Both
  queries ran (1 ms each), and a failed read degrades to `not_capturable`, not
  to "none". The Reader swallows errors into `[]`, so the code asks the query
  record whether the statement threw.
- **The `DispatchedFiring` shape gained `band: Band | null`**, which is not in
  D-c's field list. The §9 line prints `(lo–hi s)` purely from `ReceiptsData`,
  as `JobVerdict.band` already does for §2.
- **The line format departs slightly from D-c.** It is a lead line
  `Dispatched (24 h, FIX-1318): N reaped, band-judged by registry job name[;
  **missed N**].` followed by one bullet per firing, rather than a
  `Dispatched (24 h):` prefix on every row. A `no-band` verdict drops the
  redundant `(no band)` parenthetical; any other verdict keeps its band or
  `(no band)`. The owed FIX-1318 line quotes the prompt's wording
  `'Dispatched (24 h)'`, and the rendered label carries `, FIX-1318` after
  `24 h`.
- **README has no separate §9 prose.** Its §9 description is the sections-table
  row. That row is the hunk edited here, and it now also names the FIX-1308
  dispatcher line, which it never did.
- **"CI on the branch" has no trigger.** `tests.yml` runs on push to `main` and
  on `pull_request` only, so a feature-branch push runs nothing. The branch was
  verified by running the same nine checks locally, and CI ran on main after
  `:main`.
