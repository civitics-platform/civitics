- **"Reaching the success tail ⇔ the watermark moved": true in practice, with two edges worth knowing.**
  - On a RESUMED sweep, `v_watermark` is NULL. The tail writes `COALESCE(v_sweep_tgt, horizon)`, where `v_sweep_tgt` is the target the ORIGINAL staging run stored, and that run only got past the caught-up check because the target was above the watermark then. So a resumed tail still moves it.
  - (a) When the watermark row is absent (`v_watermark` NULL at staging, the very first run), the tail "moves" it from nothing.
  - (b) `v_sweep_tgt` comes from `MAX(updated_at)` over donation/IE rows of ANY `to_type`, but targets are `to_type='official'` only. So a drop that touched only non-official recipients moves the watermark with 0 official targets, and the hook refreshes an MV whose inputs did not change. Harmless: the refresh costs about 2.6k buffers. The test anchors the placement, not "rollup changed".
- **`REFRESH … CONCURRENTLY` after the final COMMIT ran in the CALL's trailing transaction as expected.** No "cannot run inside a transaction block", and the advisory unlock after it ran. Measured on the clone in all three paths.
