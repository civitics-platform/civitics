### The fresh-session check read `6h`, and why that was not a failed push

`SELECT current_setting('statement_timeout')` through `db-query --prod` returned
**`6h`**, repeatedly, after a push whose own NOTICE had just printed `3h`.

The cause is connection reuse, not the migration. Supavisor's session pooler was
handing back one warm backend — pid 73477, `backend_start` **03:23:52, eleven
seconds before the migration committed** — and a role default applies to NEW
sessions only. Five sequential queries all landed on that same pid. Opening a
second *concurrent* connection forced a fresh backend: **pid 73490,
`backend_start` 03:25:12, `statement_timeout` = `3h`.**

So the ceiling is armed for every new session, and pg_cron opens its own
connection per firing rather than going through the pooler, so every job run
from here is under 3 h. The transferable lesson: **the fresh-session check
through the pooler can report the old value indefinitely** — force concurrency
before concluding anything about a role-GUC change.

## 10. What contradicted the design

**The collision-direction premise is false as stated, and the gate it guards is
met by a different and stronger fact.** This is the finding of the run.

The design premised that "the stubs are frozen July snapshots; the survivor's
rows are the ones every run since July refreshes", and asked me to STOP if the
direction was not ≥ 99 % survivor-fresher. Measured on **prod**: 58,568 of 99,217
survivor-fresher, **59.0 %**. On the clone, 55.0 %. Not an artefact — the whole
dup-fresher population is one cell (2026 `fec_bulk_indiv`), where the survivor
rows span 2026-07-13…2026-09-01 and the stub rows 2026-05-17…2026-07-27, so for
40,551 of 46,561 the stub's July stamp genuinely is the later one.

The reason is worth keeping: **`updated_at` moves only when a row's VALUE
changes.** A survivor row that the last emit re-confirmed unchanged keeps an old
stamp. So in this class `updated_at` is a proxy for "when was this row last
physically rewritten", not for "which binding is live" — and the design read it
as the second.

So I measured the thing the gate is actually for, on both databases:

> In **every** cycle × source cell, the number of collisions where the two
> amounts **DIFFER** and the dup is fresher is **ZERO**.

On prod the amounts differ on 8,456 collisions; in all 8,456 the survivor is the
fresher row and already wins. Where the dup wins (40,649) the amounts are
identical and the outcome is the same either way. Where they differ, the survivor
is larger in 8,431 of 8,456 — $11.21 M of survivor excess against $54,850 of dup
excess, which is cycle-to-date growth on the live binding, the binding story the
design told. The set-1 dry run then confirmed it end-to-end and independently:
**all 151 survivors' donation totals are unchanged**, every stub goes to $0, and
conservation is exactly $0.

I stopped set 1's claim to readiness as instructed, and did not weaken the gate
to make it pass. What I did instead was write both facts into the manifest header
and name the check cc-129 must re-run on prod immediately before applying
(`diff_and_dup_fresher = 0`). The ≥ 99 % line should probably be *replaced* by
that check rather than kept alongside it — it is the proposition anyone actually
cares about, and it is directly measurable.

**Two smaller contradictions, both already in the sections above:**

`fec-orphan-classify`'s `twin_fec_id` was on the wrong side of the design's
reader list — it is decoded for a seat, not read as a claim (§6). And the two
stubs of one Senator cannot share a set, because `_manifest` is `(survivor
PRIMARY KEY, dup UNIQUE)` and both stubs' colliding rows would violate
`financial_relationships_relcycle_unique` (§7). The second cost nothing to fix:
each House stub is **already** an ordinary shape-A pair today, since the
survivor's live `fec_candidate_id` IS the House id — which is exactly why all
five turn up among the 151. So the House stubs ride set 1, set 2 takes only the
Senate stubs, and **set 1 must run before set 2**. A structural test locks the
partition so it cannot be quietly undone.

**One thing Block A does not fix, stated so it is not discovered later:** the two
INACTIVE `rebuild-ec-incremental` rows keep an 18,000 s budget, now **above** the
10,800 s ceiling. Nothing is demoted today because they are inactive, but
re-enabling either one has to revisit its number first — the same class of
inversion cc-127 §3.1 caught for the two active jobs.
