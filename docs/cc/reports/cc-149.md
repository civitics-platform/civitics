## 5. What contradicted the design, FIX-1125, cc-147, or this prompt

1. **The probe changes FIX-1073's escalating tiers.** The design called the
   probe's staleness the signal. It did not say that the probe's own startup
   timeouts feed `check_cron_job_health()`'s tiers: the per-job streak (6
   consecutive, escalate) and the hourly burst (10 across all jobs,
   escalate). A per-minute job fails about as often per hour as both `*/2`
   watchdogs combined. Against the retained history on prod, from 07-26:
   - **Burst:** 110 hours had startup timeouts and 64 already reached 10.
     The probe's likely failures would have pushed **9 more** over, 73 in
     all.
   - **Streak:** the budget watchdog had 30 streaks of 6 or more, and **53
     streaks of 3–5** (6–10 minute stalls). Over the same minutes a
     per-minute job would likely have streaked 6 or more. So
     `cron_startup_streak:53` **will escalate on a fork stall of about 6
     minutes**, which a `*/2` job would have had to sustain for 12.

   This is a calibration change to a paging alert that nobody chose. FIX-1073
   is archived, so the note rides on FIX-1194. The cheapest fix is to exclude
   `box-health-probe` from `per_job`, since it has its own report-only key and
   is P1-A's input. Alternatively, key the streak on minutes (`span_minutes`
   is already computed). This prompt files nothing, so I recommend a filing.
2. **`cron.job_run_details` has no retention and no `start_time` index.** The
   probe adds 1,440 rows/day to about 1,610/day, roughly doubling growth.
   Every seq-scan reader grows with the table: this probe, `prod_op_gate()`,
   `check_cron_job_health()` and the receipts' forker queries. The probe's
   scan scales with the table. 22 ms at 62k rows extrapolates to 100 ms at
   about 280k rows. At about 3,050 rows/day that is **about 72 days out
   (early December)**. A purge (for example, DELETE rows older than 30 days,
   batched and vacuumed) is the durable fix. It is not built here, and it is
   worth a filing before then.
3. **Read 4's STOP was one written query away from firing.** The three reads
   in the design, each written the way `prod_op_gate()` writes the predicate,
   cost about 103 ms. That is not because the predicate is expensive. The
   planner evaluates the ILIKE before the `start_time` filter, on every row.
   The single `MATERIALIZED` scan keeps the predicate byte-identical (rule 93,
   asserted by a test) and measures 22 ms. `prod_op_gate()`'s (d) and
   receipts §9 still pay the 75 ms form on every read.
4. **Grants: the probe is not "postgres only" in the ACL.** `REVOKE ALL …
   FROM PUBLIC, anon, authenticated` leaves Supabase's default service_role
   EXECUTE on `record_box_health`. Prod shows
   `postgres=X/postgres,service_role=X/postgres`. It is **inert**:
   SECURITY INVOKER plus service_role's missing USAGE on schema `cron` means a
   call errors. But it contradicts D1's "executes as postgres under pg_cron
   only". P1-A's migration should add `REVOKE EXECUTE … FROM service_role`.
   Posture was one migration, so it is not fixed here.
5. **Memory on this box is a swap story, not only a MemAvailable story.** The
   design took `MemAvailable` as the series. On a 904 MB box with 545–664 MB
   of 1 GiB swap already in use at a quiet hour, the kernel reclaims by
   swapping. The 02:12 sample shows MemAvailable *rising* 120 MB during a
   248.7 pages/s swap-out. A threshold on MemAvailable alone would read that
   as relief. The ring carries the `pswpin`/`pswpout` counters and D3 prints
   their rates, so that week of data can size a threshold on swap-in rate,
   probably the better leading indicator. PSI, the direct signal, is not
   exported. `Committed_AS` (1.82 GB) is already above `CommitLimit` (1.55
   GB).
6. **The prompt's 9 % Upstash share assumed 2 commands.** D2's LPUSH + LTRIM
   + SET is 3, so the share is 13 % (§2). `SET latest` duplicates `LINDEX
   ring 0`. Dropping it would save 21,600 commands/month if the allotment
   ever gets tight.
7. **"ONE Vercel deploy":** every push to main deploys. The docs record,
   appends and report pushes are deploys 2 and 3. All three landed before
   02:30 UTC, far outside cc-151's 60-min census windows, which start about
   09:00.
8. **Environment.**
   - `../civitics-worktrees/fix-1194` already existed as a de-registered
     orphan from a 09-21 teardown. `pnpm session:worktree:done 1194` removed
     it by the contained fs.rm, and `session:worktree 1194` then created the
     worktree cleanly.
   - Prod reads ran from the worktree using the primary checkout's
     `db-query.mjs` and `db-push-prod.mjs` by absolute path, the documented
     worktree pattern. That runs no process in, and writes nothing to, the
     primary tree. The primary saw only `git pull --ff-only`.
9. **For FIX-1214 (noted, not fixed).** `platform-snapshot`'s
   `get_supabase_cpu_max` identical-body POST is the 1208 shape. It escapes
   the Data Cache only because `supabase-prometheus.ts`'s no-store metrics
   fetch runs earlier in the same request and drops the store's revalidate
   to 0. That protection depends on call order and is not declared.
10. **The tree moved under the prompt twice, harmlessly.** FIX-1218 landed
    (01:44) before the first push; the branch rebased cleanly. FIX-1073 is
    archived, not live. Read 5's third `*/2` job no longer exists.
