## 9. What contradicted the bullets or this prompt

**Four premise errors, one of which is a live bug the prompt did not know it had.**

1. **`p_limit: 200` was already truncating Pennsylvania, and PA has no floterials.**
   FIX-914's header and this prompt both frame the 200 cap as a hazard the NH overlay
   *would* create (164 to 203). It was already a live bug in a state with no floterial
   within a thousand miles: **PA's lower chamber is 203 base districts**, so three
   Pennsylvania districts have been silently missing from the choropleth since
   FIX-217 — always the same three, because `query_districts` has a deterministic
   `ORDER BY state_abbr, chamber, district_id`. The fix is the same edit, but the
   justification is stronger than "headroom for NH", and the reader test now pins the
   measurement rather than the state.

2. **`DebateMap.tsx:74` does not call `query_districts`.** Cited twice (reads 2 and 4)
   as the browser-side caller motivating the `anon, authenticated` grant.
   `DebateMap.tsx` is a comment-opinion scatterplot that fetches `/api/comments/map`;
   line 74 is a `useEffect` opening and the file contains no reference to districts or
   PostGIS. The real consumers are `/api/districts/route.ts`,
   `/api/graph/voting-divergence/route.ts` and `/districts/[id]/page.tsx`, all
   server-side route handlers on a cookie-scoped `createServerClient`. The grant is
   still correct — it just is not justified by that file.

3. **The choropleth is not in `GraphPage.tsx` and is not per-state.** It is
   `packages/graph/src/ChoroplethGraph.tsx`, one nationwide `geoAlbersUsa` map;
   `GraphPage.tsx` only mounts it. So the prompt's smoke target ("the NH SLD lower
   view: 164 fill polygons + 39 overlay outlines") does not exist as a view — the
   equivalent is the nationwide `sld_l` band at 4,833 base fills + 39 overlay
   outlines, which is what section 3 reports. The prompt anticipated this case and
   asked for the file; recorded here.

4. **`date -u` at creation time would have produced a migration `db push` silently
   skips.** The prompt's naming note asserts a creation timestamp "sorts after
   cc-133's `20260919010000`". At 00:35 UTC `date -u +%Y%m%d%H%M%S` gives
   `20260919003528`, which is **less** than the remote's applied head `20260919010000`
   — and `supabase db push` only applies migrations newer than that, so the file
   would have sat pending-but-older forever with no error. The prompt's own remedy
   (rename to a fresh timestamp, report it) is what I applied, just triggered by
   cc-133 rather than the cc-132 case it anticipated: named `20260919011000` and
   `20260919011500`, strictly after the applied head and before cc-132's reserved
   `20260920000000` slot. Both showed as pending in the dry run and both applied.
