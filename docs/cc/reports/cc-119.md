## 8. What contradicted the design

**The prompt's central number was not a measurement of the thing it was
compared against, and the shape of the error says so more clearly than the size
does.** Item 4 was written around "≈ 3,416 recipients / 209,017 rows /
$1,481,928,516 (2,736 FE + 680 officials)" with a ±5 % gate — a gate that
assumes the two instruments are looking at the same population and differ only
by drift. They are not. The slice contains 2,718 recipients, all officials, zero
financial entities. You cannot be 96 % off on recipients *and* have the expected
value exceed the entire population's; that combination is not drift, it is a
category error, and it was visible the moment the manifest header printed
`slice 1,107,506 rows / $1,388,174,001` next to a harness expectation of
$1,481,928,516. **A tolerance band cannot catch a units mismatch — it can only
tell you the two numbers disagree, and by then you have to look anyway.** The
useful gate would have been the cheap structural one: does the population the
harness describes exist in the slice being audited?

**The instrument was ready before there was anything to compare it to.** The
audit's design is careful — two guards, a refusal rather than a `--force`, a
manifest that is "an AUTHORISATION, not a description", a keyed re-check that
skips anything that grew. All of that protects against the emit set being
*wrong*. None of it protects against the emit set being *first*. With exactly
one complete run in `fec_emit_runs`, "not emitted by this run" is a fact, and
"stopped being emitted" is an inference that needs two. The word DROPPED-OUT
does the smuggling: it names a transition, and the data supports only a state.
The tell was there in the manifest — no DROPPED-OUT recipient had a September
write, which is what a cohort that was *never* emitted looks like, and not what
a cohort that *stopped* being emitted looks like.

**Susan Collins is the reason the numeric gate was not enough.** Had the
manifest come in at 3,400 recipients and $1.4 B, it would have passed the ±5 %
check and the apply would have been the correct next step by every rule the
prompt states — and it would still have deleted $6,033,338 of a sitting
senator's individual contributions, because that row's problem is not the
manifest's size. Rule 68 calls the dry run "a SECOND premise test". It is, but
only for premises expressed as totals. The premise that actually mattered here
was semantic, and the thing that surfaced it was reading six rows of the
manifest and recognising a name.

**Two smaller ones.** D5(b) says the dry run "prints each tail step's cost class
and what `--defer-tails` skips (rule 62)"; this script's dry run prints no such
table, because its only inherited `printTailTable` call sits inside
`drainFrRewrite` on the `--apply` path — i.e. it would print after the delete
commits, which is precisely the timing FIX-1165(c) exists to prevent. Three of
the four sibling scripts do it correctly, and three-of-four is how it shipped
(FIX-1183). And D5(c)'s label — "`FIX-1106 residue apply cc-119`, expected
≤ 45 min" — is not something the operator can pass: `runUnderProdSession` builds
the reason from the script name plus argv and hard-codes
`expectedMinutes: 120`. The wrapper takes no label from the caller. Harmless
here, but a prompt that specifies a label for a hold is specifying something the
interlock does not accept.

**One thing the design got exactly right, worth saying because it is why the
stop was cheap.** `--manifest` forced the derivation onto a separate, read-only
script whose output is a committed file. The whole disagreement surfaced in a
252-second keyed read and a 5-second dry run, with the interlock held for
seconds and not one row written. Under the pre-FIX-1165 shape this would have
been discovered partway through an apply.
