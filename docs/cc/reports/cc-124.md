## 1. The six experiments

Ran on the **clone**, throwaway schema `fix1128_exp`, dropped at the end. Full
verbatim output in `docs/audits/2026-09-13-fix1128-experiments.md`; SQL alongside
it in the `.sql`.

**Case 1 — is a function-level proconfig inert?** `SET statement_timeout = '1s'`,
body sleeps 3 s, session 60 s.

```
NOTICE:  c1 inside fn, current_setting = 1s
 c1 COMPLETED a 3s sleep under a 1s proconfig
Time: 3004.778 ms (00:03.005)
```

*Yes.* `current_setting()` reads `1s` inside the body and nothing bounds it. The
mechanism the FIX rests on, re-proved on the tree of record.

**Case 2 — does a procedure's post-COMMIT unit arm from its own proconfig?**

```
NOTICE:  c2 before COMMIT, current_setting = 1s
ERROR:  invalid transaction termination
CONTEXT:  PL/pgSQL function fix1128_exp.c2_proc() line 4 at COMMIT
```

*The question has no answer — the object cannot exist.* A routine carrying **any**
`SET` clause runs in an atomic context and cannot execute transaction control at
all. This is also why the census found 91 functions and **zero** procedures: the
pattern and a COMMITting procedure are mutually exclusive by construction.

**Case 3 — does `set_config(…, is_local => false)` inside a procedure arm the next
unit?** This is the design's C1 fix.

```
NOTICE:  c3 before COMMIT, current_setting = 1s
NOTICE:  c3 after  COMMIT, current_setting = 1s
NOTICE:  c3 COMPLETED the post-COMMIT 3s sleep
Time: 3004.668 ms (00:03.005)
```

*No — and this refutes D2.* The value survives the `COMMIT` (still `1s` after it,
and still `1s` back in the caller's session). It arms nothing. The only armed
timer is the one the server started when the top-level `CALL` began, from the
session value at *that* moment.

**Case 4 — the `LOCAL` form.** Reverts at `COMMIT` (`1s` → `1min`) exactly as
expected, and the sleep completed anyway — for case 3's reason, not because the
value reverted. Recorded so nobody "simplifies" case 3's form to `SET LOCAL`.

**Case 5 — after a caught 57014, does the next unit get a fresh timer?** As the
design specified it, the case **cannot answer its own question**: nothing is
cancelled (case 3's mechanism), so 6.5 s of sleeping completed with the session
reading `1s`. Two variants were added to get an actual cancel, with the bound
coming from where it can — the top-level statement:

```
-- 5b: session 4s, units 3s / 3s / 0.5s
NOTICE:  c5b unit1 (3s)   COMPLETED
NOTICE:  c5b unit2 (3s)   CANCELLED 57014
NOTICE:  c5b unit3 (0.5s) COMPLETED
Time: 4501.632 ms          ← past the 4s deadline

-- 5c: session 4s, units 6s then 10s
NOTICE:  c5c unit1 (6s) CANCELLED 57014
NOTICE:  c5c unit2 (10s) COMPLETED — post-cancel units are UNBOUNDED
Time: 14008.147 ms (00:14.008)
```

*FIX-703's failure mode did not reproduce, and the truth is worse.* There is no
"instant re-timeout after a caught cancel" on PG 17. When `statement_timeout`
fires, the server disarms it and nothing inside the procedure re-arms it — so a
procedure that catches `query_canceled` and carries on runs **every remaining
unit with no bound at all**. 14.0 s of work completed under a 4 s timeout.

**Case 6 — pg_cron multi-statement command. Ran on the clone.** Read 7 measured
the clone's scheduler live (38 jobs, 405 runs in 24 h, latest firing two minutes
before the read), so the prod cron probe the prompt sanctioned as a fallback was
**not needed and not run**. `cron.schedule('fix1128-probe', '* * * * *', $$SET
statement_timeout='1s'; SELECT pg_sleep(3)$$)` → jobid 74, one firing:

```
 jobid | runid | status |             return_message              |          start_time           |     elapsed
-------+-------+--------+-----------------------------------------+-------------------------------+-----------------
    74 | 12472 | failed | ERROR:  canceling statement due to ...  | 2026-09-13 03:14:00.040133+00 | 00:00:01.004564
```

Then `cron.unschedule('fix1128-probe')` in the same session (`unscheduled = t`,
`remaining = 0`).

*pg_cron runs a multi-statement command and the leading `SET` is a real bound* —
cancelled at 1.0046 s. Given case 3, this is not merely "C2's cheapest option":
it is the **only** mechanism in the whole set that bounds a pg_cron procedure,
and it applies to C1 as much as to C2.

### One extra experiment the prompt did not ask for

Case 1 proves a proconfig cannot **tighten**. The prod evidence (below) made it
urgent to know whether it can **loosen** — because if it could, stripping 91
functions would be a behaviour change on the request path, not a neutral one.

```
-- session 2s, proconfig 30s, body sleeps 5s
ERROR:  canceling statement due to statement timeout   Time: 2001.659 ms
-- same body, NO proconfig, session 2s
ERROR:  canceling statement due to statement timeout   Time: 2000.980 ms
```

Identical to the millisecond. **The proconfig is inert in both directions**, so
the strip is behaviour-neutral by measurement rather than by argument.

## 5. The guard

`pnpm check:proconfig` → `scripts/check-proconfig-timeouts.mjs`. Text scan over
`supabase/migrations`, no DB, no secrets.

- **Flags** `SET statement_timeout` inside a `CREATE [OR REPLACE]
  FUNCTION|PROCEDURE` header, and the `ALTER FUNCTION|PROCEDURE … SET` form.
- **Does not flag** a standalone `SET` statement, `set_config()`, `RESET`,
  `ALTER ROLE … SET`, or anything inside a routine body — those are the real
  mechanisms.
- **Baseline constant** `BASELINE_MIGRATION =
  20260913000000_fix1128_reset_inert_statement_timeout.sql`. Only files sorting
  after it are scanned. `--all` audits history and reports **183 undeclared hits
  across 448 migrations** — append-only history, which is exactly why the
  baseline exists. `--since` overrides it.
- **Escape hatch** `-- fix1128: <reason>` on the line or the line above; the
  reason is printed so it stays attached to the value.

**18 fixture assertions**, all passing: the pattern fails / the annotated form
passes (and the reason is carried) / standalone `SET`, `set_config`, `RESET` and
`ALTER ROLE` all pass / a procedure fails / the `ALTER` form fails / a `SET` in a
body, in a comment and in a quoted string are each not a hit / masking preserves
byte offsets / the baseline exists and the tree after it is clean / history is
dirty, so the baseline is load bearing.

`tests.yml` now runs **seven** blocking checks, confirmed in the green run:
Typecheck · Lint · Silent-read guard · Render-timeout guard · Workflow
resource-parity guard · **Inert statement_timeout guard** · the three unit suites.

## 8. What contradicted the design

**The C1 fix does not work.** D2 is the heart of Half 2 — arm each unit from
inside the procedure with `PERFORM set_config('statement_timeout', <budget>,
false)` before the call. Experiment 3 says the value survives the `COMMIT`,
reports correctly through `current_setting()`, and **arms nothing**. Written
inside a procedure it is the same class of decoration Half 1 is removing, one
level up. Half 2 cannot be built as designed.

**Experiment 2's object cannot exist.** The design treated "does a procedure's
post-COMMIT unit arm from its own proconfig?" as an open question with a
plausible yes, and made that hypothetical the *only legitimate case* for the
guard's escape hatch. A routine carrying any `SET` clause cannot `COMMIT` at all.
So the hatch shipped with no known legitimate use, and the script header says so
rather than implying otherwise. It also explains a census fact the design noted
without explaining: 91 functions, zero procedures.

**FIX-703's failure mode is not what carries forward — the opposite is.** The
design (and FIX-1112's handler shape) assumed a caught cancel might leave the
next statement instantly re-timing-out. On PG 17 the timer is *disarmed* by
firing and never re-armed, so a handler that catches and continues runs the rest
of the procedure **unbounded** — 14.0 s of work under a 4 s bound. "Catch the
cancel and carry on" is not degraded-but-bounded; it is the removal of the bound.

**Case 6 was framed as a fallback and is actually the whole answer.** The design
scoped it to C2 and made it conditional on prod access. It ran on the clone, and
given case 3 it is the only mechanism measured here that bounds a pg_cron
procedure at all — for C1 as much as C2. It bounds the whole `CALL`, though, not
a unit, so a per-unit budget needs the procedure to time itself and stop (the
`cron_job_budget` shape, FIX-1063/1125).

**The count is 91, not 90.** Minor, but the design states 90 while its own prose
implies 91, and the bullet says 89. `pg_proc` says 91 on both databases.

**A methodological finding that changes how every "observed" number reads.**
`pg_stat_statements` does **not** record statements cancelled by
`statement_timeout` — proved directly: the probe's cancelled 10 s call left no
row, its 2 s control did. So `max_exec_time` is a maximum over *completions*.
An EXCEEDS verdict is therefore strong evidence, and a `within` verdict is silent
about cancellations, which live only in the Logs API. Any future bounds audit
that reads pgss as "the slowest it ever got" will be wrong in the direction that
matters.

**The prod evidence forced an experiment the design did not plan.** Two
`service_role` statements completed past 8 s while the probe was being cancelled
at 8 s. The obvious suspect was the proconfig extending the bound — which would
have made this migration a behaviour change on the request path rather than a
neutral one. Measured on the clone: it cannot loosen either (2 s session, 30 s
proconfig, cancelled at 2.001 s, identical to no proconfig). The strip is safe;
the contradiction is real and is FIX-1181, with a pooled `authenticator`
connection carrying a non-`LOCAL` `SET` as the leading candidate.

**Two documentation homes the design named do not exist.** D3 called for a
sentence in the root `CLAUDE.md`'s "SQL conventions" section and a seven-check
list in its "CI" section. `CLAUDE.md` has neither section. The rule went in as a
new subsection under *Database Safety Rules*, where the surrounding SQL guidance
already lives, and the seven-check list went into
`docs/cc/PROMPT_TEMPLATE.md`'s verification checklist, which is the list a
prompt actually reads.

**Two smaller census corrections.** `get_financial_entity_naics` is class D, not
B — it is a direct-pg call, and its 107.0 s prod maximum could not have come
through an 8 s role. And only two of the four `_full` functions are called from a
pg_cron procedure, not all four.

**A prompt-hygiene note.** The prompt's Phase 0 read 7 was framed as "the memory
says `cron.job` is unreadable from the clone — establish which of unreadable /
readable-but-not-running / functional is true". It is fully functional: 38 jobs,
405 runs in 24 h. The memory it refers to is about the clone's cron *data* not
being evidence about prod (FIX-946), which is a different claim from the
scheduler being unusable. Worth not conflating next time — it was the difference
between one prod write and none.
